## The five elements

Event Modeling is built from a small closed vocabulary. The kit's element types, as they appear in board API calls (`node:created` with an `elementType`), are:

| Element | Type string | Gloss | Colour |
|---|---|---|---|
| Event | `EVENT` | An immutable domain fact — a completed state change, named in past tense | **Green** |
| Command | `COMMAND` | An intent to change state, issued by a role or a processor | **Blue** |
| Read Model / View | `READMODEL` | A derived projection of events, optimised for a query | **Orange** |
| Screen / UI | `SCREEN` | What a human sees and interacts with at one moment | *(not specified in corpus)* |
| Automation / Processor | `AUTOMATION` | A reactive system actor that reads state and issues commands | *(not specified in corpus)* |

**Colour caveat.** The green/blue/orange convention appears in exactly one place in the assigned corpus — the workshop reference's sticky-note conventions:

> Green = Event, Blue = Command, Orange = View
> — `eventmodeling-brainstorming-events/references/facilitating-event-modeling-workshops.md` (lines 556-580)

That reference covers only three of the five. **No colour is given anywhere in the seven step skills for `SCREEN` or `AUTOMATION`**, and the classic Event Modeling colour scheme beyond green/blue/orange is **absent from the corpus**. Do not invent the missing two.

### Exact glosses

**Event.** "Every event is past tense and names a completed state change (e.g., `OrderPlaced`, not `PlaceOrder`)" (`eventmodeling-brainstorming-events/SKILL.md`). Validation restates the test per element: "**For each event:** Uses past tense (Created, Confirmed, etc.); Contains **only facts** (no computed fields); All data is **immutable**; Unique semantics (no duplicates)" (`eventmodeling-validating-event-models/SKILL.md` lines 52-67).

**Command.** Present-tense verb phrase. The only explicit naming rule in the validation corpus: "Commands: Verb present (CreateOrder, ConfirmPayment); Events: Verb past tense (OrderCreated, PaymentConfirmed)" (`eventmodeling-validating-event-models/SKILL.md` lines 70-77). A command must be attributed to a named role or system actor, never to a generic "User".

**Read Model.** "Calculated/aggregated state / Recalculates when source events change / Derived from other events / Query optimization / Can be regenerated from events" (`eventmodeling-identifying-outputs/SKILL.md` lines 87-170).

**Screen.** Belongs to human roles only: "Human roles get SCREEN nodes. System actors and processors get AUTOMATION nodes. Place both types during storyboarding — do not defer automations to a later step" (`eventmodeling-storyboarding-events/SKILL.md` lines 464-500).

**Automation.** The processor. Its behavioural model is the todo list (see *The four patterns*).

### Mandatory field metadata

Every element type carries `meta.fields`, and every field must set `cardinality` (`"Single"` unless genuinely a list; default `"Single"` when unsure).

- `COMMAND`, `SCREEN`, `READMODEL` fields each additionally require a **`mapping`** — the field's provenance.
- `EVENT` fields are the **exception**: no `mapping` required, and "no fields" is acceptable for a simple state transition.

"An event without fields is an opaque label — it cannot be used to validate completeness, write scenarios, or generate code" (`eventmodeling-brainstorming-events/SKILL.md` lines 189-216). But equally: "Do not pad events with fields just to reach a count."

**Mapping forms by element type:**

*Command* (`eventmodeling-identifying-inputs/SKILL.md` lines 306-338):
- `"user-input"` — `generated: false`
- `"session:<fieldName>"` — false
- `"<EventTitle>.<fieldName>"` — false
- `"derived:<expression>"` — **true** (e.g. `derived:uuid4()`, `derived:now()`)
- `"webhook:<payloadField>"` — false

*Screen* (`eventmodeling-storyboarding-events/SKILL.md` lines 309-384) — command screens: `"<CommandTitle>.<fieldName>"`, `"session:<fieldName>"`, `"<EventTitle>.<fieldName>"`, `"derived:<expression>"`. View screens: `"<ReadModelTitle>.<fieldName>"`, `"<EventTitle>.<fieldName>"`, `"derived:<expression>"`.

*Read model* (`eventmodeling-identifying-outputs/SKILL.md` lines 385-419):
- `"<EventTitle>.<fieldName>"` — projected directly, `generated: false`
- `"latest:<EventTitle>.<fieldName>"` — most recent event of this type, false
- `"aggregate:<EventTitle>.<fieldName>"` — aggregated across events, **true**
- `"derived:<expression>"` — calculated from other read model fields, **true**

"Fields projected directly from events are not generated — they carry a real domain value. Fields that are aggregated or calculated by the system are generated."

**The connected-element rule** applies to `SCREEN`, `COMMAND` and `READMODEL` alike: a field's `mapping` may only reference an element joined to it by a board connection arrow. When it cannot:

> When you encounter a mapping that cannot resolve to a connected element, write the mapping as-is but flag it as a gap in the completeness notes. Do not invent connections that don't exist.
> — `eventmodeling-storyboarding-events/SKILL.md`

This is the single strongest procedural rule in the kit.

## The four patterns

Event Modeling composes four — and only four — flow shapes, all reading strictly **left to right** along the timeline.

**1. State change (command pattern)**

```
SCREEN / Processor  →  COMMAND  →  EVENT(s)
```

Slice type string: `state-change`.

**2. State view (read model pattern)**

```
EVENT(s)  →  READMODEL  →  SCREEN / Processor
```

Slice type string: `state-view`.

**3. Automation (processor pattern)**

```
EVENT(s)  →  AUTOMATION  →  COMMAND  →  EVENT(s)
```

Slice type string: `automation`. This is the only shape with events on **both** ends.

**4. Translation (external → internal)**

Named by the orchestrator as a follow-on concern, delegated to `eventmodeling-translating-external-events`. **The translation pattern is not defined in the seven step skills.** If you need to translate an inbound external/protocol event into a domain event, that guidance is not in the seven-step spine.

(The literal arrow forms for 1-3 are quoted verbatim from `eventmodeling-slicing-event-models/SKILL.md` lines 27-31. The strings `state-change`, `state-view`, `automation` are the platform's slice `type` values, not prose labels.)

### The composite slice pattern

Step 5 states the standard screen shape as a fusion of patterns 2 and 1:

> READ MODEL → SCREEN → COMMAND → EVENT
> — `eventmodeling-identifying-outputs/SKILL.md` lines 351-383

with the strong claim: "**Most screens need a read model on their left** — not only view/status screens, but also command/input screens that show current state before the user acts." And: "Treat any screen or automation without an incoming read model as a gap unless it provably needs no prior state at all (e.g., a blank registration form)."

For automations the equivalent is `READMODEL → AUTOMATION → COMMAND`.

### The Processor "Todo List" pattern

The kit's model of how automation actually works:

> Processors don't directly process events—they maintain a todo list driven by events.

Mechanics (`eventmodeling-identifying-inputs/SKILL.md` lines 125-159):
1. A triggering event arrives → an item is added to the todo list.
2. The processor loop, **for each** todo item: checks state; on success issues a command producing an event and marks the todo done; on business failure produces a failure event and marks failed; **"If error: Keep in todo for retry."**

> **Key insight**: Processors are reactive. They listen for events and create todo items, then execute those todos by issuing commands that produce new events.

Step 3 shows the same pattern from the UI side, as an internal todo-list screen. Step 4's quality checklist demands: "Processor todo list pattern explained for each automation"; "Event-to-todo triggering mechanism documented"; "Automation marked with `[AUTO]` to distinguish from user actions `[USER]`"; "Processor failure/retry handling specified."

Resolution used here: treat **1-7 as the modeling method proper** (this is what Event Modeling classically is), **8 as the completeness check**, and **9 (Validate) and 10 (Slice)** as the kit's own tooling extensions. ### Cross-cutting rules for all seven steps

**(a)** Every one of the seven SKILL.md files opens with the identical mandatory preamble: "**Before doing anything else**, invoke the `connect` skill to resolve `TOKEN`, `BOARD_ID`, `ORG_ID`, and `BASE_URL`. ### Step 1 — `eventmodeling-brainstorming-events`

> Step 1 of Event Modeling - Brainstorm all domain events from requirements. Extract every state-changing event the system could have.

**Input:** domain requirements, optionally preceded by a 4-question Interview Phase (requirements completeness, domain expertise, known complexity areas, explicit business rules).

**Output:** "Event list + Role Catalog + dedicated timelines (one chapter per workflow / bounded context) with events already placed in their correct timeline."

**Gate:** "Do not proceed until the Role Catalog exists, events cover all known business processes, and every event is placed into a named chapter."

**Six numbered sub-steps:** 1. Identify User Roles & Actors (MANDATORY); 2. Identify Event Streams (Stream Roots); 3. Identify Business Processes; 4. Extract State Changes; 5. Document Business Rules & Constraints; 6. Create Analysis Document.

**Workshop timing:** 15-20 minutes total — Phase 1 Understand Goals 5-10 min, Phase 2 Free Brainstorm 15-20 min, Phase 3 Gentle Filtering 10-15 min. (The sub-timings exceed the headline figure; the corpus does not reconcile this.)

**Explicit scope boundary:**

> Do not use for: arranging events in sequence (use eventmodeling-plotting-events), designing commands or read models (use eventmodeling-designing-event-models), or when a complete event list already exists.

#### The Role Catalog (mandatory)

> Every event model needs an explicit role catalog — without it, downstream steps (storyboarding, commands, scenarios) lack clarity on who does what.

Two categories: **Human roles** (Customer, Seller, Admin, Support Agent, Reviewer) and **System actors** (Payment Gateway, Inventory System, Notification Service, Scheduler). Each entry documents: Name (domain language); Description (1-2 sentences); Key actions ("What state changes can this role initiate?"); **Permissions boundary** ("What can this role NOT do?").

The catalog feeds four later steps, and the cross-references confirm the canonical 1-8 numbering:

- **Step 3 (Storyboarding)**: one swimlane per human role
- **Step 4 (Inputs)**: every command attributed to a specific role/actor
- **Step 7 (Scenarios)**: scenarios reference roles by name
- **Step 8 (Completeness)**: verify every role has at least one command path

(`eventmodeling-brainstorming-events/SKILL.md` lines 372-420)

#### Timeline (chapter) discovery — before any event is placed

> Brainstorming is where timelines are discovered. **Every event must be placed into its dedicated timeline — never into a generic or unnamed chapter.**

1. **Group events by workflow / bounded context.** Each group "Represents a single, coherent business process", "Can be understood as a standalone narrative on its own", "Would be naturally owned by one team or one domain expert". Critically: "If all events belong to a single flow, one timeline is correct — do not split artificially."
2. **Create one chapter per group before placing any events**, title it immediately with the workflow/bounded-context name, stack chapters vertically at `y = index * 1200`, `x = 0`.
3. **Place each event into its chapter.** "No event may be placed without a `chapterId`."

Two modes: **Mode A** (chapter exists — include `cellId` in `node:created`); **Mode B** (free-form, no chapter yet — valid during open discovery, but "all events MUST be assigned to a named chapter before Step 2 (Plotting) can begin").

> An event left without a chapter and cell reference will never appear in any timeline column and cannot be sequenced, storyboarded, or used in scenarios.
> — lines 133-279

#### The Core Architectural Rule — the kit's strongest DON'T

> **NEVER use DDD Aggregate pattern for state design.** Every command handler must have its own minimal state projection derived from events. This is non-negotiable.

Anti-pattern: a fat `OrderAggregate` used by `ConfirmOrder` / `ShipOrder` / `CancelOrder` / `ApproveReturn` — "Loads unused data, couples unrelated commands, violates minimal state principle."

Correct: `ConfirmOrderState { status, orderId }`, `ShipOrderState { status, orderId, paymentId }`, `CancelOrderState { status, orderId, createdAt }` — "Each command loads ONLY what it needs."

Reinforced in Key Principles: "**Event Sourcing Mindset**: Think in terms of immutable events and stream roots, NOT DDD aggregates. The stream root is just a logical grouping of events"; "**Defer State Design**"; "**Command State Isolation**: Each command handler has its own state shape. Different commands = different state interfaces." Stream roots are explicitly "NOT DDD aggregates—they're simply the logical roots of events", each with a Name and an Identity key. (lines 423-432, 515-543)

#### Step 1 DON'Ts

- No CRUD events (`UserUpdated`, `RecordDeleted`) — "events describe business moments, not database operations"
- "No overlapping event semantics"
- "No empty columns left in the timeline"
- Do not include computed or derived values in event fields — "those belong in read models"
- Use domain names, not technical names (`memberId` not `userId`, `dueDate` not `due_at`)
- Enrichment of fields is deferred to `/attributes`

### Step 3 — `eventmodeling-storyboarding-events`

> Step 3 of Event Modeling - Create UI storyboards/mockups showing what users see at each step. Capture all data fields needed from user perspective.

**Input:** Event timeline + Role Catalog. **Output:** "UI mockups/wireframes with one swimlane per human role, showing what data each screen displays and collects." **Gate:** "Every human role from the Role Catalog has at least one screen."

**Seven sub-steps:** 1. Identify UI Screens/Views; 2. Show State Transitions Between Screens; 3. Document All Data Fields; 4. Show Data Flow Through Screens; 5. Organize Screens by Swimlane (Actor/System) — MANDATORY, using the Step 1 Role Catalog as the source of swimlanes; 6. Show Processor "Todo List" Pattern; 7. Identify Missing Data.

**Validation rule:** "If a role from the catalog has zero screens, either: The role is missing screens (add them), or The role doesn't belong in the catalog (remove it in Step 1)."

#### SCREEN vs AUTOMATION

> Human roles get SCREEN nodes. System actors and processors get AUTOMATION nodes.

A column is an automation column when: "The action is triggered by the system, not a user gesture"; "No human sees or interacts with the UI at this step"; "The pattern is `READMODEL → AUTOMATION → COMMAND`."

#### The one-screen-per-column hard rule

> **Never place more than one SCREEN node in the same column**, even across different actor lanes. Each column represents a single moment in the timeline. Two screens in the same column means two different interactions at the same moment — that breaks the visual narrative and always signals a design error.

Fix: insert a new column immediately after via `POST /timelines/:tl/columns` with `{"index": N}`.

Placement table: input/command screen → actor row, **same column** as the COMMAND and EVENT; view/output screen → actor row, **one column to the RIGHT** of the READ MODEL (but see the discrepancy below). Explicit DON'T: "Do not create standalone screen columns that are disconnected from commands or read models." (lines 464-500)

#### Mandatory sketch rendering

> Every SCREEN node requires a wireframe sketch.

Order: Step A compute `cellId` (`actorRow.id + "-" + columnId`); Step B create the SCREEN node with `cellId`; Step C render the wireframe immediately via `POST /images/$NODE_ID/sketch`.

> **CRITICAL: NEVER pass `"elements": []`. An empty elements array produces a blank, invisible screen and is always wrong.**

Grid language: 50×40 grid, 1 unit = 20 px; element types rectangle / text / headline / button / input / line / circle; 14 named colours. Every sketch must include at minimum a full white background rectangle, a colored header bar with the title, real UI elements, field labels matching the actual event/command fields, and at least one primary action for command screens.

> A screen node without a wireframe sketch is an empty placeholder. It must not be left unrendered.
> — lines 386-462, 596

### Step 4 — `eventmodeling-identifying-inputs`

> Step 4 of Event Modeling - Identify Commands/Inputs from UI and Processor actions. Map user actions to commands and data.

**Input:** Storyboards + Role Catalog. **Output:** "Command definitions, each attributed to a specific role or system processor." **Gate:** "Every UI action in the storyboards maps to a named command."

**Stated prerequisite:** "The **Role Catalog** from Step 1 must exist. Every command identified below MUST be attributed to a specific role or system actor from that catalog."

> Every command MUST have a role/actor attribution. If a command says `[ User]` instead of a specific role name, it's incomplete — go back to the Role Catalog and assign the correct role.

**Sub-steps:** 1. Extract Commands from UI Actions; 2. Identify Processor Triggers; 2b. Understand the Processor "Todo List" Pattern; 2c. Document Processor Automation (Gears Symbol); 3. Document Command Specifics (Source / Input / Validation rules / Preconditions from stream state / Success result / Failure results); 4. Create Command Catalog (split into UI-Issued and Processor-Issued); 5. Map Data Sources; 6. Identify Implicit Context.

Commands go in the **`interaction` lane**, same column as their resulting event.

#### Field provenance and traceability

> **CRITICAL: Every COMMAND node MUST include `meta.fields` with a `mapping` on every field.** A command without fields — or with fields that lack `mapping` — is an incomplete model that cannot be traced, validated, or turned into code.

> **If you cannot write a mapping for a field, that field has an unknown origin — treat it as a gap and resolve it.**

Event traceability: every field in the resulting EVENT must either appear in the command's `fields` (direct mapping, same name or documented rename) or be derivable from command fields + system state; otherwise "that is a gap". And: "**If a mapping cannot be defined at all, it hints at missing data in the model or a modeling error**". Do not add speculative fields.

#### The mandatory pre-placement check against backward arrows

> A `SCREEN → COMMAND` connection must always go downward within the same column (actor row → interaction row). A `COMMAND → EVENT` connection must also be within the same column.

Before placing a command: (1) confirm the screen is in the **same column** as the event it produces; (2) if the screen is in an earlier column, move it to the event's column before wiring; (3) if later, insert a new column at the correct index or move the screen.

> The timeline must always read left-to-right: SCREEN and COMMAND belong in the same column as the EVENT they produce.

`cellId = interactionRow.id + "-" + columnId`, where `columnId` is extracted from the target EVENT node's existing `meta.cellId`. (lines 365-461)

### Step 5 — `eventmodeling-identifying-outputs`

> Step 5 of Event Modeling - Identify Outputs/Read Models from events. Show what data flows back to UI and Processors.

**Input:** Event list + Commands from Step 4. **Output:** "Read model definitions — projections of events optimized for UI and processor queries." **Gate:** "Every screen data need from the storyboards is satisfied by a read model."

**Sub-steps:** 1. Map Event Data to UI Screens; 2. Define Read Models; 3. Document Event → Data Mapping; 4. Create Output Catalog; 5. Identify Missing Data; 6. Processor Outputs.

Read models go in the `interaction` lane. This step also places any AUTOMATION nodes that turn out to be missing: "Automations are placed here when analysis reveals a processor that reads state and issues commands but is not yet on the board." Screens from Step 3 are not re-placed "unless one is clearly missing".

#### The CRITICAL Events vs Read Models distinction

> **This is the most important distinction in event sourcing.** Many architectures fail because this line gets blurred.

**Events = Immutable Domain Facts:** "Represents an action someone took / Immutable once recorded / Can be replayed to rebuild state / Provides audit trail / Independent of other events."

**Read Models = Derived Projections:** "Calculated/aggregated state / Recalculates when source events change / Derived from other events / Query optimization / Can be regenerated from events."

**The Test** (six rows):

| Signal | Verdict |
|---|---|
| An actor performed an action | EVENT |
| Pure calculation | READ MODEL |
| Immutable once created | EVENT |
| Recalculates multiple times | READ MODEL |
| Independent (causes no other events) | EVENT |
| Derived FROM other events | READ MODEL |

> **DON'T model these as EVENTS**: Inventory level totals; Inventory totals (sum of transactions); Account balances; Search indexes; Aggregated metrics (sums, counts, averages); Scheduled calculations (processor outputs that are pure calculation).

Rationale: "Events should capture facts (what happened); Calculations should be projections (how we view the facts); Otherwise you end up with circular dependencies and replay issues."

Checklist: "No recalculated state modeled as events: (if value changes multiple times, it's a read model)"; "**History tracking is clear**: Derived state keeps history in read model `history[]`, not as separate events." (lines 87-170, 653-661)

#### The read-model-must-have-a-consumer rule

> **Before designing any read model, enumerate every SCREEN and AUTOMATION already placed on the board.**

After the step: "**every SCREEN and every AUTOMATION on the board must be connected to at least one read model**."

Placement DON'Ts: "A read model must be placed in a column that already contains a SCREEN or AUTOMATION it serves. Do not place read models in columns with no screen or automation — doing so creates orphaned read models that will never have a consumer." And: "Do not append read model columns to the end of the timeline — doing so severs the visual left→right flow." (lines 351-383, 423)

#### Read model field traceability

Every read model field must trace back to at least one source event; otherwise it is either a documented derivation or "A missing event field — add it to the source event before proceeding." Mappings may only reference EVENTs connected via an `EVENT → READMODEL` arrow. "**If a mapping cannot be defined for a field, it signals missing data in the model, a missing event, or a modeling error.** Do not leave unmapped fields without a note." Include only fields the consuming SCREEN or AUTOMATION actually displays or needs.

### Step 6 — `eventmodeling-applying-conways-law`

> Step 6 of Event Modeling - Apply Conway's Law with swimlanes. Organize events into autonomous system parts that different teams can independently own.

**Input:** Full event model so far (events, commands, read models). **Output:** "System swimlanes mapping events and commands to team boundaries." **Gate:** "Each boundary can be independently owned by a team."

> Skip this step if Conway's Law boundaries are not relevant to the project.

It is the **only one of the seven the orchestrator marks skippable**.

**Six sub-steps:** 1. Identify System Boundaries; 2. Create Swimlane Diagram; 3. Map Team Responsibilities (per team: Commands they handle / Events they produce / Read Models they maintain / Systems they call or depend on); 4. Identify Inter-System Communication; 5. Define System Interfaces (commands accepted, events produced, read models provided); 6. Identify Processors vs Systems (per processor: Triggered by / Logic / Produces / Lives in).

**Principle:** "**System architecture mirrors team structure**: Separate teams → Separate systems; Each system owns events; Communication through events; Independent development possible; Aligns with org chart."

## Slices

Slicing is **Step 10** in the orchestrator's numbering, handled by `eventmodeling-slicing-event-models`. It is **not among the seven**, and the term "vertical slice" does not appear in the seven step skills.

### Definition

> A **Feature Slice** is the thinnest possible vertical cut through the model — exactly one decision or one query

Section heading, which is itself the definition: "**Core Concept: A Slice Is One Command, One Read Model, or One Automation — Never Combined**".

Key characteristics:
- "Exactly one COMMAND (state-change), exactly one READMODEL (state-view), or one AUTOMATION's command — never combined"
- "Named after that command, read model, or automation"
- "Independently deployable"
- "Communicates with other slices via events only"

(`eventmodeling-slicing-event-models/SKILL.md` lines 23-40)

### The three slice types

```
state-change slice = SCREEN/Processor → COMMAND → EVENT(s)
state-view slice   = EVENT(s) → READMODEL → SCREEN/Processor
automation slice   = EVENT(s) → AUTOMATION → COMMAND → EVENT(s)
```

These strings are the platform's slice `type` values.

### Never mix a COMMAND and a READMODEL

> A slice never mixes a COMMAND and a READMODEL — the platform models these as two distinct slice types (`state-change` and `state-view`). If a "feature" needs both a command and a read model (e.g. "place an order" needs the `PlaceOrder` command *and* an `OrderDetailView` read model), that's **two slices**, not one.

`references/patterns.md` (lines 66-77) restates as the WRONG case: "Slice: 'Order Management' containing the PlaceOrder command AND the OrderDetailView read model / Problem: mixes a state-change and a state-view in one slice — the API models these as different slice types for a reason."

This **contradicts the common informal reading** of a "vertical slice" as a user-facing feature.

### Slices are discovered, not invented

> Slices Already Exist in the Timeline

> By the time an event model is complete, the slices are already implied by the timeline's structure. This skill's job is to make them explicit on the board — not to invent broader groupings.

The derivation rule is mechanical: "Walk the timeline column by column: Every **COMMAND** → one `state-change` slice, named after the command; Every **READMODEL** → one `state-view` slice, named after the read model; Every **AUTOMATION** → one `automation` slice, named after the automation (or the command it issues)."

The skill explicitly forbids using it "for planning before the event model is complete". (lines 43-51)

### How slices map to columns

One slice per timeline column. `spec-info` returns `{ timelineId, elements: [{ id, title, type }] }` but "doesn't include the column each element sits in", so the chapter node is fetched for `meta.timelineData.columns: [{ id, index }]` and `meta.timelineData.cells: [{ id: "<rowId>-<columnId>", nodeId }]`.

> For each filtered element, find the cell whose `nodeId` matches the element's `id` — the `columnId` is the cell `id` with the leading `<rowId>-` (36 chars + hyphen) stripped off. Record `{ elementId, elementType, title, columnId }`

> mark that **existing** column as a slice via the **slice-definitions** endpoint

Creating the slice "only adds a `SLICE_BORDER` node to the column you already resolved". A slice is literally a **vertical column boundary** on the timeline. Rows (swimlanes) run horizontally across columns and are **not** the slice unit. (lines 77-111)

### INTERNAL CONTRADICTION — `slice-definitions` vs `slices`

SKILL.md line 111 is emphatic:

> Use **`slice-definitions`**, never the plain **`slices`** endpoint here — `slices` creates a brand-new column with its own swimlane/content nodes, which would duplicate the element already placed on the timeline.

But its own `references/examples.md` (lines 51-65), under "Creating These Slices via the API", uses exactly the forbidden endpoint **three times**: `POST .../timelines/$TL/slices` with `-d '{"type":"state-change","nodes":{"swimlane":{"title":"PlaceOrder"}}}'`.

The two files disagree. SKILL.md's prohibition is the more specific and more recently-reasoned statement, but **the conflict is unresolved in the source**.

Also note: `title` "always comes from the request body — it is never derived automatically from the command/read model/automation node".

### Naming

> Name the Slice After Its Element

"Slice name matches the command/read model/automation title exactly." And: "Use the exact command, read model, or automation title as the slice title — don't invent a broader 'feature' name that spans multiple elements."

Per type: COMMAND column → title = command name (`state-change`); READMODEL column → title = read model name (`state-view`); AUTOMATION column → title = automation name, **or** the command it issues (`automation`). The automation type is the only one with naming latitude.

### Cross-slice dependencies — events only

> Express Dependencies as Events, Never as Shared State

> Slices depend on each other only through events — never directly.

Two cases: "**Event dependency** — slice B's command or read model needs an event that slice A produces"; "**No dependency** — slices work off entirely separate events."

`patterns.md`: "Slices never call each other directly and never share a state class. If slice B needs something from slice A, it's because slice B's command or read model projects an event that slice A produces — not because they're coupled at the code level."

`examples.md` requires dependencies be recorded as "depends on events from X", **not** "depends on slice X".

Two named cross-slice patterns exist: "Command Slice → Event → Command Slice" and "Command Slice → Event → Read Model Slice", the latter described as "the most common dependency: nearly every state-view slice depends on the events produced by one or more state-change slices".

### Slicing quality checklist

SKILL.md (lines 124-129) — four rules:

- [ ] Every slice contains exactly one COMMAND (state-change), one READMODEL (state-view), or one AUTOMATION — never a COMMAND and a READMODEL together
- [ ] Slice name matches the command/read model/automation title exactly
- [ ] No slice was created for an element that already has one
- [ ] Dependencies are expressed as events only, never as direct slice-to-slice calls or shared state

`references/examples.md` (lines 69-78) adds a fifth: "Slice type matches the element type (state-change / state-view / automation)."

Duplicate prevention is explicit: "A column already has a slice if its element's title matches an existing slice's title."

### Slicing excludes estimation and team allocation

> Slicing itself does not require planning team allocation, sprint sizing, or effort estimates — that's a separate concern from defining the slices.

Team structure is delegated: do not use this skill "for organizational team structure based on Conway's Law (use eventmodeling-applying-conways-law)".

**Slices are not work-estimation units in this corpus** — contrary to how vertical slices are commonly used in agile planning.

### The one link between slicing and validation

`eventmodeling-validating-event-models-checklist/SKILL.md` line ~160: "**Each handler is a micro-slice.**" This equates one command handler with one slice, consistent with the slicing skill's definition.

## Scenarios and GWT

### Step 7 — `eventmodeling-elaborating-scenarios`

> Each spec tied to exactly one command or view.

### The central rule — no good-case/bad-case pairs

> **Do not reduce scenarios to a simple good-case / bad-case pair.** For each command, ask the questions below and write a scenario for every answer that the business case supports. Which types apply and how many scenarios each type generates is always determined by the domain — not by a fixed count or a static rule.

### The seven scenario types

| # | Type | Question |
|---|---|---|
| 1 | Happy Path | What is the normal success case? |
| 2 | Validation Failure | What invalid or missing inputs should be rejected? |
| 3 | State Violation | What if the system is in a state that makes this command invalid? |
| 4 | Duplicate Action | What if this command is issued again after it already succeeded? |
| 5 | Alternative Path | Are there different valid outcomes depending on context? |
| 6 | External Failure | What if an external system or scheduler fails during this command? |
| 7 | Compensation | Can this be undone or reversed? What triggers the cleanup? |

> If the answer is "that situation cannot occur in this business" then no scenario is needed for that type — but that judgment must come from the domain, not from a desire to write fewer scenarios.

**Checklist gate:** "**No command has only 2 scenarios unless all other types were reviewed and found inapplicable.**"

**Workshop target:** "3-5 scenarios per command, 10-20 minutes per command" (Step 7 body). Note the workshop reference gives a *different* figure for the same step: "5-7 min per command/view, don't perfect". The corpus does not reconcile these.

(`eventmodeling-elaborating-scenarios/SKILL.md` lines 199-213, 713-724; orchestrator lines 240-260.)

### Server-enforced structural rules

> **Rules enforced by the server (do not pre-validate — let the server reject):**
> `given`: EVENTs only; `when`: at most one COMMAND; empty when `then` contains a READMODEL; `then`: EVENTs only OR exactly one READMODEL — never mixed; All step node IDs must belong to the same timeline.

### The two special flag families

**List-type read models** (`listElement: true`) require two scenario-level fields:
- `examples` — one object per expected row, keyed by the readmodel's **snake_case** field names. "Without this the spec node renders with no expected output and the scenario is unverifiable."
- `expectEmptyList: true` when the expected result is empty. "Do not leave `examples: []` without this flag — an empty array alone is ambiguous."

**Rejection scenarios** require `expectError: true` plus a non-empty `errorDescription`. When `expectError` is true:
- "`then` must be `[]` — no events are produced on rejection"
- `when` contains the COMMAND being rejected
- `given` contains prerequisite EVENTs establishing the wrong state (may be empty for pure input-validation rejections)
- "Do **not** set `expectEmptyList` — that flag is only for list READMODELs"

**Consequence worth naming:** under this rule a rejection produces **no event at all** in the model, unless you deliberately model the rejection itself as a fact with its own event.

### Posting flow

`GET /timelines/$TL/spec-info` to build a `title (lowercase) → {id, type}` lookup, then `POST /timelines/$TL/columns/$COL/scenarios` with all scenarios for a column in **one array call**; the SCENARIO spec node is created automatically. On ambiguous/unmatched step titles: "log it and skip that step item rather than failing."

(lines 568-702)

### Gherkin best practices — Good vs Bad

**Bad:** "Given order / When stuff happens / Then it works"; "And an event is produced"; "Then there's an error".

**Good:** explicit state ("Given an order in \"Draft\" state"); named event with a field/value table; named rejection reason.

### Common workshop mistakes to avoid

- **Perfectionism**: "Don't spend 30 minutes on one scenario"
- **Missing roles**: "One person can't represent all perspectives"
- **Too technical**: "Use domain language, not code"
- **Incomplete givens**: "'Given an order' is too vague. Specify state."
- **Unclear events**: "Every scenario must show what event is produced (or why not)."

### Key principles

One Scenario = One Test; Explicit Preconditions; Clear Actions; Verifiable Outcomes; Event-Centric; Business Language.

(lines 183-197, 737-784)

## The completeness check

**Step 8 — `eventmodeling-checking-completeness`:**

> Step 8 of Event Modeling - Completeness Check. Verify every field has origin and destination. Ensure complete event model before code generation. Use after all scenarios defined.
> — `eventmodeling-checking-completeness/SKILL.md` line 3

The check is **bidirectional**. This is its defining property, and it is stated in the frontmatter itself: *origin* **and** *destination*.

- **Origin** — where did this field come from? Every field must have a resolvable `mapping` back to a connected element: a command field back to user input / session / an event / a derivation / a webhook payload; a read model field back to a source event; a screen field back to a command, event, read model, or derivation.
- **Destination** — where does this field go? A field that enters the model and never reaches an event or a read model is a dead end. The mirror rule appears in the checklist skill's Phase 5: "**Input → Event → Read Model traceability is complete**", with the anti-pattern "Command inputs that disappear or read model fields without source."

The Step 1 Role Catalog explicitly names Step 8 as one of its four consumers: "**Step 8 (Completeness)**: Verify every role has at least one command path."

Gap discipline governs the whole check: an unresolvable mapping is recorded as a **gap**, never invented away.

### Where the completeness check fits — run it twice

The orchestrator's recommended timing places the checklist run at two points, not one: after Step 2 (The Plot / Sequence), and again after the model is complete. Running it only at the end catches structural problems too late to fix cheaply.

### The three Final Questions

> Question 1: Could an architect unfamiliar with this domain understand the model in 15 minutes?
> Question 2: Could you change your core algorithm/calculation without changing event history?
> Question 3: Could this be implemented in your target technology stack (e.g., TypeScript + PostgreSQL)?

Q2 is the sharpest: if you cannot change an algorithm without rewriting event history, the algorithm's output has leaked into the events.

### Verdict vocabulary and the redesign threshold

Final Verdict is "**PASS** (or **PASS WITH WARNINGS** or **FAIL**)" plus "Implementation Ready: YES (or NO - fix issues first)" and "Confidence: [percentage]".

- **Validated when:** all checks pass (or have documented workarounds); no critical anti-patterns identified; all 3 final questions answer YES.
- **Needs fixes when:** any check fails with clear evidence; fixes are straightforward and targeted.
- **Should be REDESIGNED when:** "Multiple phases fail; Architectural assumptions are fundamentally flawed; Anti-patterns are systemic and pervasive; Would require rewriting core event structure."

So there are three verdict tiers plus a distinct **fourth outcome (redesign)**. Quality checklist: "Final verdict is one of: PASS / PASS WITH WARNINGS / FAIL — no ambiguous outcomes"; "Any FAIL result has a recommended fix, not just a problem statement." Every FAIL must name "the specific event, handler, or stream that violated the check."

## The four anti-patterns

`eventmodeling-validating-event-models-checklist/SKILL.md` lines 127-194 names exactly four:

### 1. Calculation Events

**ANTI-PATTERN:** `CalculationPerformed { metric: 4.5 ← Mutable/recalculated }`

**CORRECT:** "Event: SomeActionOccurred (immutable fact) / ReadModel: MetricView (recalculated from events)"

**Why:** "Calculations change multiple times as source data changes. Events are immutable."

### 2. Shared vs Handler-Owned State

**ANTI-PATTERN:** "One shared 'OrderAggregate' class used by all handlers... Result: Tight coupling, hard to parallelize"

**CORRECT:** "Each handler owns its own `[CommandHandler]State` class... All reconstruct state from same events, but independently"

**Why:** "**Each handler is a micro-slice.**"

### 3. Circular Dependencies

**ANTI-PATTERN:** StreamA → EventA → affects StreamB → EventB → affects StreamA

**CORRECT:** "ReadModels ← consume (one-way only) / No feedback loops"

### 4. Persistent State vs Ephemeral State

**ANTI-PATTERN:** "Save SubmitReviewState to database after command, load it again next time. Result: Duplicates event sourcing, loses audit trail"

**CORRECT:** "Load events from stream / Replay via `evolve()` to rebuild state / Process command, emit outcome events / **Discard state (it's ephemeral, not persisted)**"

### The domain-agnostic discriminator

The checklist gives per-domain lists of what are **not** events:

- E-commerce — NOT events: `OrderTotal`, `InventoryLevel`, `ShippingCost`
- Banking — NOT events: `AccountBalance`, `InterestCalculated`
- SaaS — NOT events: `MonthlyRecurringRevenue`, `ChurnRate`
- Healthcare — NOT events: `PatientAge`, `AverageCost`

> The principle is the same across all domains: **immutable facts as events, calculated results as read models**.

**The diagnostic heuristic:**

> When you see something like "CalculationDone" or "ReviewRatingUpdated": Ask: "Is this immutable and caused by a user/system action?" If NO → It's a read model, not an event.

(lines 245-270, 296-316)

## Stream design

### Stream roots are not aggregates

> The stream root is just a logical grouping of events.

Stream roots are "NOT DDD aggregates—they're simply the logical roots of events", each with a **Name** and an **Identity key**. Identifying them is sub-step 2 of Step 1 ("Identify Event Streams (Stream Roots)").

### The non-negotiable rule

> **NEVER use DDD Aggregate pattern for state design.** Every command handler must have its own minimal state projection derived from events. This is non-negotiable.

Per-command minimal state, named `[CommandName]State` / `[CommandHandler]State`:

```
ConfirmOrderState { status, orderId }
ShipOrderState    { status, orderId, paymentId }
CancelOrderState  { status, orderId, createdAt }
```

"Each command loads ONLY what it needs." Different commands = different state interfaces.

### Stream constraints from validation

- **Each event belongs to exactly one stream / exactly one lane** (Phase 1.1; Consistency check "Event-Stream Mapping"). An event may not appear in two streams.
- **Each stream needs a named initial event** — "Initial event (what creates the stream)" (Section 1, Swimlane Completeness).
- **Stream independence** — Phase 7.1: "each stream can be versioned/restored independently"; anti-pattern "Hard dependencies between streams".
- **No hard dependencies between command handlers** — Phase 1.3: orchestration happens via events only.
- **No circular dependencies** — "Projection A depends on B, B on A → Redesign stream boundaries."
- **State is ephemeral** — rebuild by replay through `evolve()`, then discard. Never persist and reload command state.
- **Projections must be deterministic and pure** — no external API calls during replay, no database queries to load state.

### What stream design guidance is ABSENT

The seven step skills do **not** cover:
- **Stream identity / partitioning design** — deferred to the optional follow-on `eventmodeling-designing-event-models`
- **Event versioning / upcasting** — absent entirely
- **Snapshotting** — deferred to `eventmodeling-optimizing-stream-design`
- **External-event translation** — deferred to `eventmodeling-translating-external-events`

(Orchestrator lines 324-336 names these three follow-on skills.)

## Notation extensions

These are elements of the board notation beyond the five core elements. Coverage in the corpus is uneven; gaps are marked.

### Chapters (timelines)

The primary structural extension, and fully specified.

- A **chapter** is a named timeline. One chapter per workflow or bounded context.
- Chapters are **discovered and created in Step 1**, before any event is placed. No later step may create one: "**No new chapters created here** — chapter structure was fixed in Step 1."
- Layout: stacked vertically at `x = 0`, `y = index * 1200`.
- Every event carries a `chapterId`. "No event may be placed without a `chapterId`."
- Criteria for a chapter: "Represents a single, coherent business process"; "Can be understood as a standalone narrative on its own"; "Would be naturally owned by one team or one domain expert."
- Anti-proliferation rule: "If all events belong to a single flow, one timeline is correct — do not split artificially."
- Chapter data lives at `meta.timelineData` with `columns: [{ id, index }]` and `cells: [{ id: "<rowId>-<columnId>", nodeId }]`.

### Actor lanes (rows)

Three row types exist: `actor`, `interaction`, `swimlane`. Cells are addressed as `cellId = rowId + "-" + columnId`.

- `actor` row — SCREEN and AUTOMATION nodes
- `interaction` row — COMMAND and READMODEL nodes
- `swimlane` row — EVENT nodes

An **"automation lane"** is referenced once (`eventmodeling-identifying-outputs/SKILL.md` line 517) but **is never defined**. Treat it as an error in the source.

Lane creation is governed by the Step 1 Swimlane Rules (Mandatory): only when a new actor has no existing lane, or an explicit business rule requires one. Never for visual grouping.

### Slice status / slice borders

A slice is rendered as a **`SLICE_BORDER` node** added to an already-resolved column. It marks an existing column; it does not create one. Slice `type` is one of `state-change` / `state-view` / `automation`, and `title` must be passed explicitly in the request body — "it is never derived automatically from the command/read model/automation node".

**Slice *status*** (e.g. planned / in-progress / done) is **not defined anywhere in the corpus read**. The slicing skill explicitly excludes planning concerns: "Slicing itself does not require planning team allocation, sprint sizing, or effort estimates."

### Comments — the two-type severity notation

The validating skills post findings as node comments via the `handle-comment` skill:

- **`TASK`** — critical violations that must be fixed
- **`QUESTION`** — warnings and recommendations

This is the corpus's complete severity vocabulary for annotations on the board.

### Specs / scenario nodes

Scenarios are posted per column via `POST /timelines/$TL/columns/$COL/scenarios`; the **SCENARIO spec node is created automatically**. Scenario-level flags that alter rendering: `examples` (list read models, snake_case keys), `expectEmptyList`, `expectError` + `errorDescription`.

### Sketches

Every SCREEN node carries a wireframe sketch rendered via `POST /images/$NODE_ID/sketch`. Grid: 50×40, 1 unit = 20 px. Element types: rectangle, text, headline, button, input, line, circle. 14 named colours.

### Automation marking

Step 4's checklist requires "Automation marked with `[AUTO]` to distinguish from user actions `[USER]`" — the corpus's only textual marker convention.

### Gears symbol

Step 4 sub-step 2c is "Document Processor Automation (Gears Symbol)". The symbol is named but not further specified.

### HOTSPOTS — ABSENT

**Hotspots are absent from the material read.** No hotspot element, node type, notation, or concept appears in the seven step skills, the slicing skill, the validating skills, the checklist skill, the orchestrator, or the workshop reference. If hotspots are part of the canonical notation, that definition lives elsewhere — plausibly on `eventmodeling.org`, which was unreachable from this environment. **Do not infer a definition.**

## The 20 rules

A consolidated working rule set, drawn verbatim or near-verbatim from the corpus. Each cites its source.

1. **Every event is past tense and names a completed state change.** `OrderPlaced`, not `PlaceOrder`. — *brainstorming-events*

2. **Every command is a present-tense verb phrase.** `CreateOrder`, `ConfirmPayment`. — *validating-event-models* (lines 70-77) — the only explicit command-naming rule in the corpus

3. **A Role Catalog must exist before any event is brainstormed**, covering human roles and system actors, each with name, description, key actions, and permissions boundary. — *brainstorming-events* (lines 372-420)

4. **Every command is attributed to a specific named role or system actor.** Generic "User" is a CRITICAL violation. — *identifying-inputs*; *validating-event-models* (lines 109-120)

5. **Every event is placed into a named chapter (timeline) with a `chapterId`.** Chapters are created in Step 1 only. An event without one "will never appear in any timeline column and cannot be sequenced, storyboarded, or used in scenarios." — *brainstorming-events* (lines 133-279)

6. **NEVER use the DDD Aggregate pattern for state design.** Every command handler gets its own minimal `[CommandName]State` projection. "This is non-negotiable." — *brainstorming-events* (line 423); the PRIMARY validation gate in *validating-event-models* §6

7. **No computed or derived values in events.** Totals, balances, counts, averages, indexes, scheduled calculations are read models. "immutable facts as events, calculated results as read models." — *identifying-outputs* (lines 87-170); *checklist* (lines 245-270)

8. **Every element carries `meta.fields`, and every field sets `cardinality`.** Default `"Single"` when unsure. Events may have zero fields; every other type may not be empty. — all step skills

9. **Every COMMAND, SCREEN and READMODEL field carries a `mapping`.** A field without one has unknown origin. — *identifying-inputs* (lines 306-338); *storyboarding-events* (lines 309-384); *identifying-outputs* (lines 385-419)

10. **A mapping may only reference an element connected by a board arrow.** — connected-element rule, all three field-bearing types

11. **When a mapping cannot resolve, flag it as a gap. Never invent a connection.** "Write the mapping as-is but flag it as a gap in the completeness notes. Do not invent connections that don't exist." — *storyboarding-events*; the strongest procedural rule in the kit

12. **Every field must have both an origin and a destination.** Command inputs that disappear, and read model fields without a source, are defects. — *checking-completeness* line 3; *checklist* Phase 5

13. **Human roles get SCREEN nodes; system actors and processors get AUTOMATION nodes.** Place both during storyboarding — do not defer automations. — *storyboarding-events* (lines 464-500)

14. **Never place more than one SCREEN node in the same column**, even across different actor lanes. "Two screens in the same column means two different interactions at the same moment... always signals a design error." — *storyboarding-events*

15. **The timeline always reads left-to-right.** SCREEN and COMMAND belong in the same column as the EVENT they produce; no backward arrows. — *identifying-inputs* (lines 365-461)

16. **Every SCREEN and every AUTOMATION must be connected to at least one read model**, unless it provably needs no prior state. Conversely, no read model may sit in a column with no screen or automation to consume it. — *identifying-outputs* (lines 351-383, 423)

17. **Never call `drop` after using `cellId` in `node:created`.** It adds a second cell reference without removing the first. — repeated verbatim in Steps 1, 3, 4, 5

18. **Do not reduce scenarios to a good-case / bad-case pair.** Work all seven scenario types; "No command has only 2 scenarios unless all other types were reviewed and found inapplicable." — *elaborating-scenarios* (lines 199-213)

19. **A slice is exactly one COMMAND, one READMODEL, or one AUTOMATION — never combined**, named exactly after that element, depending on other slices through events only. — *slicing-event-models* (lines 23-40, 115-120)

20. **Validation is read-only.** The only permitted change is comments: `TASK` for critical violations, `QUESTION` for warnings. Fix nothing during validation. — *validating-event-models* (lines 13-14, 35)

**Runner-up rules worth carrying:** every event belongs to exactly one stream/lane; every command produces events or documents its rejection (no zombie commands, read-only excepted); projections are pure and deterministic (no external calls during replay); state is ephemeral — rebuild via `evolve()` and discard; state can be versioned/restored per stream independently.

## When Event Modeling does not fit

The corpus states scope boundaries in several places. It does **not** contain a single consolidated "when not to use Event Modeling" section — what follows is assembled from explicit exclusion statements, and the gap is noted.

### Explicit "do not use" statements in the corpus

**When the artefact already exists.** Step 1: "Do not use for: arranging events in sequence (use eventmodeling-plotting-events), designing commands or read models (use eventmodeling-designing-event-models), **or when a complete event list already exists**."

**When Conway's Law boundaries are irrelevant.** Step 6 is explicitly skippable: "Skip this step if Conway's Law boundaries are not relevant to the project." For a single-team system, the whole step is dispensable — the only one of the seven so marked.

**Before the model is complete (for slicing).** The slicing skill explicitly forbids use "for planning before the event model is complete". Slices are derived, not designed.

**For estimation and team allocation.** "Slicing itself does not require planning team allocation, sprint sizing, or effort estimates — that's a separate concern." Slices are **not** work-estimation units in this corpus, contrary to common agile practice.

**For organisational team structure.** Delegated out of slicing to `eventmodeling-applying-conways-law`.

### Structural signals that the model is the wrong shape

The validation skills define a threshold at which the answer is not "fix the model" but "start again":

> Model should be **redesigned** when: Multiple phases fail; Architectural assumptions are fundamentally flawed; Anti-patterns are systemic and pervasive; Would require rewriting core event structure.

And the three Final Questions function as fitness tests. A **No** to Question 2 — "Could you change your core algorithm/calculation without changing event history?" — indicates the domain's value is in a computation rather than in a history of facts. A system whose essence is a continuously recomputed number, and which has no meaningful audit history, will resist this method: everything worth modelling ends up in read models and the event stream becomes a thin log of inputs.

A **No** to Question 1 — "Could an architect unfamiliar with this domain understand the model in 15 minutes?" — indicates the model has failed at its primary purpose, which the workshop reference frames as shared understanding among a group of 5-8 people.

### The collaborative premise

The workshop reference frames **all seven steps as human collaborative sessions**: group size 5-8; required roles Product Owner / Domain Expert, 2-3 Developers, 1-2 QA/Tester, 1 Facilitator; multi-day schedule Day 1 = Steps 1-3 (4 hours), Day 2 = Steps 4-7 (4 hours), Day 3 = detailed Step 7 (3 hours).

> This guide helps facilitators run efficient, effective workshops across all 7 steps.

**None of the seven steps is defined as an automated or agent-only activity.** A workshop mistake explicitly named is "**Missing roles**: One person can't represent all perspectives." Where the domain experts, the developers, and the testers cannot be assembled, the method's own reference material says the output will be deficient — regardless of how the board gets filled in.

### What the corpus does not say

The corpus contains **no statement** that Event Modeling is unsuitable for any particular class of system — no exclusion of CRUD applications, reporting systems, batch pipelines, ML systems, or embedded/real-time software. Any such claim would be an extrapolation, not a finding. The exclusions above are the complete set present in the material read.
