## Notes

RECOVERED BY THE RE-SWEEP — the violated arm of the §4.5.5 SHOULD at 3803-3805, which no sweep recorded in either arm. It matters to this chapter because it is the counterfeit of everything else here: a null reverse-path is the mark of a notification, and a message that wears one without being a notification borrows the immunity that goes with it — nothing bounces back to the sender, and a receiver applying NotificationSuppressedForNullReturnPath and the §4.5.5 no-reply rule will treat it as undeliverable-but-unreportable. That is a real consequence of a real state change, which is why it is an event and not a validation rule. Strength: SHOULD, with the exception defined by reference — "not required by a Standards-Track RFC to have a null reverse-path" — so conformance cannot be judged from this document alone; the three kinds §4.5.5 names at 3789-3793 are the known-exempt set and the boundary beyond them is open. Honored arm: an ordinary message sent with a valid non-null reverse-path, which is ReversePathDeclared in the envelope chapter — cross-referenced, not claimed here. Rejected alternative names: BareNullSenderUsed, NullReversePathAbused (rejected — 'abused' asserts intent the RFC does not), NonNotificationSentWithNullPath. Which screens would have killed it: the inbound-only scope and the consumer test (G1).
