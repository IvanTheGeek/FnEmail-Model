## Notes

An unusual strength: not SHOULD-not-cache but SHOULD-use-great-care-in-caching (3746-3747), which permits the act while refusing to bless it — a shape worth preserving rather than flattening to a permission or a prohibition. The justification is that server answers are not stable even within one connection (3747-3749). Reading the cache instead of re-contacting the server is a query and is in set_aside; the RFC's caution is about the WRITE, which is this event. Dropped as derived: cached_until, which is cached_at plus a configured lifetime the RFC never states. Sibling at a stronger strength: MailCommandRejectionCached. Opposite event: CachedNegativeResponseInvalidated. Screens: inbound-only scope, altitude tiers. ⚠️ FIELD HYGIENE PASS: reply_code is KEPT here, and this is one of only two events in the chapter where it survives. The test the method sets is whether the RFC carries the code as data beyond the wire, and 3746-3750 does exactly that: the cached response outlives the exchange that produced it, and the rule at 3749-3750 keys on the code CLASS of the stored value, which makes the stored code the subject of a normative statement rather than the rendering of a decision. RE-SOURCED the example: the inherited 450 had no grounding for an EHLO response, and 550 is one of the three error codes the RFC lists for EHLO at rfc5321.txt:3098. STRUCK cached_at as a bare occurrence stamp — and note that its absence makes the already-dropped cached_until unreconstructible, which is honest, since the RFC states no cache lifetime at all.
