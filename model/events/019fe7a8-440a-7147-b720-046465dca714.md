## Notes

RECOVERED BY THE RE-SWEEP. The inherited set folded this into RecipientListCopiedIntoHeaderSection, and they are not the same act: that one is a sender or server copying RCPT arguments into trace or informational fields at transmission time; this is a RECEIVING system, at delivery time, inventing a relationship the protocol says does not exist and editing the message it is about to hand over. Different actor, different moment, different corruption. Rejected alternative names: EnvelopeHeaderRelationshipDeduced, HeaderSectionRewrittenAtDelivery, ApparentlyToFieldSynthesized. Strength: SHOULD NOT, grounded in the flat statement at 4228-4230 that no inherent relationship exists. This is the one blind-copy event that fires inside the receiving server FnEmail is actually modeling, which makes it the least screenable candidate in the chapter — the inbound-only scope and the responsibility-boundary cutoff both let it through, and the consumer test G1 is the only screen that reaches it. FIELD HYGIENE PASS: nothing struck. All three values are sourced and none is derived: altered_header_field is the field this server wrote, deduced_from is the envelope address it reasoned from, and receiving_host says where — and since the whole point of the event is that a receiving system did what a sending one is separately forbidden to do, naming the host is not the actor restated but the distinction the RFC draws at 4231. Note what is absent and was not invented: no queue id. This server has accepted the message and may well have stamped a §4.4 ID clause, so one would arguably be available here — it is left off because the event is about the header section it is rewriting at delivery, and adding an identifier the earlier passes never claimed would be inventing under cover of hygiene.

COLLISION RESOLVED — merged from 2 independently brainstormed records. Same section, same SHOULD NOT at §7.2 4231-4232, same actor, same stream root, same confidence, and the same two-field payload under two field names. Both records independently made the same distinction against RecipientListCopiedIntoHeaderSection, which confirms they were describing one state change and separating it from the same neighbor.

From the duplicate in 16. Abuse, Security and Registry: RECOVERED BY THE RE-SWEEP — no inherited candidate carried 7.2's second paragraph, only its first. The violated arm of a second, separate SHOULD NOT (4231). Kept apart from RecipientListCopiedIntoHeaderSection on the RFC's own structure: 4220 forbids COPYING what the envelope gave you, 4231 forbids INVENTING a correspondence, and the ground for the second is the flat denial at 4228-4230 that any relationship exists — the sentence docs/smtp-path-vs-mailbox.md rests on. Strength: SHOULD NOT twice, plus a third at 4235 against Apparently-to. Rejected names: EnvelopeHeaderCorrespondenceAssumed, HeaderRewrittenFromEnvelope, DeliveryHeaderSynthesized. Screens that would have killed it: the twelve-slice model, the responsibility-boundary cutoff. FIELD HYGIENE: struck altering_host, an actor restatement. The survivors are the two halves of the forbidden deduction: the envelope address taken as evidence and the header field rewritten on it. No identity key: the message has none in RFC 5321, 4.4's ID clause at line 3336 being an optional trace clause carrying an Atom or an RFC 5322 msg-id, not an identifier the spec puts on events.
