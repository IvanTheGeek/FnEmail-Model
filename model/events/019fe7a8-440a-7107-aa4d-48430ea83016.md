## Notes

MERGED: the inherited SenderAddressRecordUpdated (§3.4-3.5 sweep) and AddressBookEntryUpdated (§7 sweep) are the same state change found from opposite ends of the document. This name is kept because it is the RFC's own words at lines 4287-4288; SenderAddressRecordUpdated, ClientRoutingMemoryUpdated and ReplacementAddressPersisted are the rejected alternatives. Note that §7.4's general form is "update its future behavior", with the address book given only as an e.g. — a second event for the general behavior change was considered and rejected as padding, since the RFC offers no other instance. Strength is the interesting part: §3.4 mentions this event only by forbidding the server to assume it happened, TWICE, in identical words (1194-1196 and 1204-1206). That doubled MUST NOT is strong evidence the event is real and merely unobservable from the server side, which is a different thing from not existing — and it is the entire reason 251 and 551 exist. The authenticity check that §7.4 says should precede it is a read and is set aside; the rewrite is the event; the version done WITHOUT that check is kept separately as AddressCorrectionAcceptedFromUnauthenticatedServer. Stream root INVENTED: Correspondent Address Record — none of the offered roots fits a sender-side stored address for someone else's mailbox; Mailbox is wrong because this record is not the mailbox, it is one party's belief about where another party's mailbox is. Screens: responsibility-boundary cutoff, inbound-only scope, the consumer test (G1), and the twelve-slice model — all four fire, because this is state on the far side of the wire. Citation fixed: inherited candidate quoted a fragment cut mid-line ("to automatically update its future behavior (e.g., updating the"); extended here to the whole clause, which does span 4286-4288.

⚠️ FIELD HYGIENE PASS (fields and notes only): struck two fields. learned_from_reply_code (251) — the rendering of a decision made on the far side of the wire, and §7.4 rfc5321.txt:4286-4288 treats the two codes as one case ("the 251 or 551 reply codes") while nothing in RFC 5321 says the client stores which one it heard. What the record holds is an old address and a new one. announcing_server (foo.com) — struck as padding beyond the essential pair, and the judgment is flagged rather than buried because it is the one strike in this chapter made on the method's "only what the business needs" rule rather than on a missing source: the value foo.com IS sourceable (rfc5321.txt:4886), so rule 5 would have let it stand. The entry is one party's belief about where a correspondent's mailbox is; §7.4's concern with the server's identity is a precondition on the write, not a column in the record, and it is carried where it belongs, on the sibling AddressCorrectionAcceptedFromUnauthenticatedServer. If a later step finds that provenance is what tells the two siblings apart in a read model, this is exactly where it goes back. No identity key was invented; old_address is the key of the record being rewritten. Sourced: old_address at rfc5321.txt:4897; new_address composed from the RFC's Green (4884) and xyz.com (1940).

COLLISION RESOLVED — merged from 2 independently brainstormed records. Same section, same actor, same state change found from opposite ends of the document. The one real disagreement was announcing_server: one copy called it load-bearing because 4288-4289 makes certainty about that server's authenticity the precondition of the whole event; the other struck it as padding beyond the essential pair, flagging that the value is sourceable (4886) so only the method's 'only what the business needs' rule kills it. Struck: the authenticity precondition is a condition on the write and is already the distinguishing fact of the sibling AddressCorrectionAcceptedFromUnauthenticatedServer, so carrying it here claims it twice. Both arguments are preserved so the strike is checkable and restorable if a read model needs provenance to tell the siblings apart.
