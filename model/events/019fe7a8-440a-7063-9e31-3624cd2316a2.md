# `RelayInspectedMessageData`

A server performing a relay function read into the message data — far enough to tell whether Return-path header fields were present — which it is forbidden to do.

## Where RFC 5321 says so

| Section | Lines | Text |
|:--|:--|:--|
| §4.4 | 3234-3237 | *"SMTP servers performing a relay function MUST NOT inspect the message data, and especially not to the extent needed to determine if Return-path header fields are present."* |
| §4.4 | 3229-3231 | *"any further (forwarding, gateway, or relay) systems MAY remove the return path and rebuild the MAIL command as needed to ensure that exactly one such line appears in a delivered message."* |
| §2.3.10 | 810-814 | *"A "relay" SMTP system (usually referred to just as a "relay") receives mail from an SMTP client and transmits it, without modification to the message data other than adding trace information, to another SMTP server for further relaying or for delivery."* |

Line numbers are into [`docs/rfc/rfc5321.txt`](../../docs/rfc/rfc5321.txt), the archived copy. Quotations keep the specification's own words and spellings (AGENTS.md rule 2).

## Notes

RECOVERED BY THE RE-SWEEP. The violated arm of the MUST NOT at 3234-3237, and the reason the contradiction flagged on ReturnPathRemoved is worth a row rather than a note: two adjacent paragraphs of §4.4 permit an act and forbid the only way to perform it correctly, so an implementer who follows 3229-3231 literally produces this event every time. It is the clearest instance in this chapter of the spec being unimplementable as written, and Step 1 is where that gets onto the wall rather than into an appendix. §2.3.10 810-814 supplies the underlying principle — a relay transmits 'without modification to the message data other than adding trace information' — which is what the inspection prohibition protects. Confidence 'likely' because the RFC never records the violation as an occurrence. Screens: inbound-only scope, HELO-only charter, and the condemned status register. ⚠️ FIELD HYGIENE PASS 2026-08-09 — one field struck. message_id: RFC 5321 supplies no message identifier; §4.4's ID clause (line 3336) is optional and belongs to the receiver's own Received: stamp, msg-id is RFC 5322's, and f2C8D14 is this project's minted queue_id value from commit 6acfc68. Identity here is the relaying host and the depth it read to — and inspection_depth survives because the prohibition is graded, not flat: the MUST NOT forbids inspecting at all 'and especially not to the extent needed to determine if Return-path header fields are present', so how far the server read is the fact that distinguishes a marginal breach from the one the RFC names.
