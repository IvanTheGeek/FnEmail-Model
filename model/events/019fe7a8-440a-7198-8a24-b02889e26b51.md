## Notes

The over-time counterpart of the per-session ServiceExtensionsAdvertised: the advertisement is per-session, the configuration is not. The spec assumes it constantly — 1778-1780 speaks of extensions 'offered by the server and accepted by the client' without ever saying how a server came to offer any — so likely rather than certain: the RFC constrains what is advertised, not how it gets configured. §2.2.3 589-591 added by the re-sweep and it is the consequential one: enabling an extension can CHANGE THE MINIMUM LIMITS of §4.5.3, which means this event can silently move the values set by SizeLimitConfigured, within a session. The effective limit is a function of configuration plus negotiated extensions, not of either alone. Distinguish from ServiceExtensionRegistered (IANA, years, global) and from BilateralAgreementEstablished (two operators, X-prefixed, never registered). Screens: the HELO-only charter has no extensions to configure; the altitude tiers place configuration at Infrastructure. FIELD HYGIENE: struck two fields. ehlo_param (10485760) could not be sourced — the SIZE parameter's value is RFC 1870's business, not RFC 5321's — and it duplicated SizeLimitConfigured's limit_octets, so it was unsourceable and derived at once; the structural point that a keyword may carry parameters survives in the §4.1.1.1 citation. enabled_at is the event's own occurrence time, metadata rather than payload. ehlo_keyword survives with its value verified at rfc5321.txt:3524, where the RFC names the 'SIZE' service extension. No session, transaction or connection key was present; identity is the server plus the keyword enabled.
