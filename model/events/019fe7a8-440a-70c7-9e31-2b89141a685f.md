## Notes

TWO facts in one RFC sentence: the reply the client sees, and the storing the server does. The storing half now has its own event (RecipientBuffered) and this one keeps the reply half. FnEmail already has RecipientAccepted with forward_path, so the name is settled in both places. Rejected alternative names: ForwardPathAccepted, RecipientAllowed. The stored list is what MailTransactionConfirmed later releases the server to process. Opposite events, five of them, deliberately not merged: RecipientRejectedAsUndeliverable, RecipientRejectedWithForwardingAddress, RecipientRejectedWithoutAddressInformation, RecipientRejectedForPolicy, RelayingDeclined — a refusal is not an acceptance and the five refusals differ in cause, in code and in what they disclose.

FIELD HYGIENE PASS: struck one field, reply_code (250), as the wire rendering of a decision the event's name already carries. §3.3 1061-1062 supplies the code and is cited above, so the fact survives as a citation rather than as payload. ⚠️ Worth naming: with the code gone this event's payload is identical to RecipientBuffered's, which is exactly the tension the note above records — one RFC sentence, two facts — and the two remain separate on their meanings, not on their fields. FnEmail's own RecipientAccepted carries forward_path and nothing else, which the strike now matches. No identity key was present to strike; the forward-path is the identity of the Recipient stream.
