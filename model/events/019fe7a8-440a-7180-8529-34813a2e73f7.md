## Notes

The unwritten precondition behind the whole of §4.5.1: the postmaster obligation is quantified over 'any of the domains for which the SMTP server provides mail service', so the obligation's extent is a set that some earlier administrative act populated, and the RFC never names that act. service_role is carried because 3394-3396 scopes the obligation to systems 'supporting mail relaying or delivery' — a domain added for relaying and one added for final delivery both trigger it; a submission-only arrangement arguably does not. serving_host added in the merge so the event names both sides. Sibling where the interesting bug lives: MailServiceDomainRemoved — mail for postmaster@bar.com arriving after removal. Screens: the consumer test G1 and the Infrastructure altitude tier. FIELD HYGIENE: nothing struck; all three fields survive and each is now sourced. service_role's value is the RFC's own term, verified at line 3208 ('final delivery'), with the contrasting value 'relaying' from 3394-3395 — a genuine two-valued distinction, not padding. No session, transaction or connection key was present; identity here is the pair of domains, which is what the spec's own quantifier ranges over.
