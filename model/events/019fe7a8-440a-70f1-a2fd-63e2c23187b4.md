## Notes

Recovered by the re-sweep. The inherited NegativeResponseCached noted the MUST NOT at 3749-3750 in prose but modeled only the permitted act, so the prohibited arm had no event. Splitting it out is what makes the violation visible from the payload alone: an instance of NegativeResponseCached with command_verb MAIL and a 5yz reply_code is non-conforming, and a reader should not have to reconstruct that from a note. This is the strongest keyword in §4.5.4.1's caching paragraph and it is scoped narrowly — 5yz only, MAIL only; a cached 4yz to MAIL, or a cached 5yz to RCPT, is not covered by it. Rejected name: PermanentMailRejectionCached. Screens: inbound-only scope, condemned status register. ⚠️ FIELD HYGIENE PASS: NOTHING STRUCK. reply_code survives the computed-and-derived rule on the strongest ground available anywhere in this chapter — 3749-3750 names the code class as the thing that MUST NOT be stored, so the code is the subject of the prohibition and not a rendering of a decision. The example 550 is one of the RFC's own listed MAIL error codes at rfc5321.txt:3104. reverse_path is the MAIL command's argument and therefore what the cached rejection is a rejection OF, which is why the event is not merely about a host. No session, transaction or connection identifier appears here or could: RFC 5321 supplies none, and the cache outlives every session anyway, so the destination host is what carries identity.
