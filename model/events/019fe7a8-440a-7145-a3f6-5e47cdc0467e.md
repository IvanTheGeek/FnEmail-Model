# `BlindCopySentAsSeparateTransaction`

A sending system split one message into one transaction per blind-copy recipient, each carrying a single RCPT command, so no recipient list exists to leak.

## Where RFC 5321 says so

| Section | Lines | Text |
|:--|:--|:--|
| §7.2 | 4223-4226 | *"Since this rule is often violated in practice, and cannot be enforced, sending SMTP systems that are aware of "bcc" use MAY find it helpful to send each blind copy as a separate message transaction containing only a single RCPT command."* |
| §7.2 | 4214-4218 | *"Addresses that do not appear in the message header section may appear in the RCPT commands to an SMTP server for a number of reasons. The two most common involve the use of a mailing address as a "list exploder" (a single address that resolves into multiple addresses) and the appearance of "blind copies"."* |

## Notes

CITATION WIDENED during the merge: the inherited candidate quoted only the tail fragment at 4224-4226; the sentence starts at 4223 with the reason it exists, and the reason is the interesting part. Strength: MAY — and it exists only because the SHOULD NOT at 4220 is unenforceable, which the RFC concedes in the same sentence. A privacy control implemented as transaction multiplication. Rejected alternative names: BlindCopyIsolatedInOwnTransaction, PerRecipientTransactionCreated, MessageSplitForBlindCopies. Reaches a similar multiplied state to MessageCopyCreated and to Appendix B's copy generation, from a completely different motive — privacy rather than queuing — and is kept separate for exactly that reason. Screens: the one-event-per-command design target (one submitted message becomes N sessions, N MAIL commands, N DATA bodies), inbound-only scope. FIELD HYGIENE PASS: peer_host struck — 1 field. It was foo.com, which is Brown@foo.com's domain resolved to a next hop: derived from the recipient this event already carries, by way of the address-resolution machinery that is chapter 6's subject. §7.2 lines 4223-4226 says nothing about the peer either — the sentence is about the sending system's choice to split, not about where the pieces go. What remains is the single RCPT recipient the transaction was built around and the reverse-path that opened it, the latter also serving as the nearest handle the wire carries for a transaction that RFC 5321 gives no identifier to at all.
