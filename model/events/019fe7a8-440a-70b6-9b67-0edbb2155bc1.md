# `MessageDeliveredAfterResponsibilityDeclined`

A server that had answered the end-of-data indicator with a failure code delivered the message anyway, so a message the sender still owns was delivered twice.

## Notes

RECOVERED BY THE RE-SWEEP — the violated arm of the two MUST NOTs in §4.2.5, which no sweep named. This is the reason those MUST NOTs exist: the client has been told it still owns the message and will requeue it, so any delivery by the declining server produces a duplicate that neither party can reconcile. It is the exact mirror of DuplicateMessageReceived — there the client duplicates because it did not hear a success; here the server duplicates after announcing a failure. Doubtful as an event because a conforming system never emits it and because, like every duplicate in this chapter, it is observable only from the recipient's mailbox, never from either MTA. If it is dropped later, drop it for being unobservable from inside one system, not for being forbidden. Screens: all of them — nothing in the current model has a place for a counterparty's misbehavior. Rejected alternative names: DeliveryAttemptedAfterRefusal, RefusedMessageDeliveredAnyway.

FIELD HYGIENE PASS: struck three of four. transaction_id is fabricated, and doubly empty here: the transaction was refused, so no queue id was stamped either, and RFC 5321 supplies nothing that names the message this server is delivering after saying it would not. declining_server is struck as a session-level fact. declined_reply_code is struck as a rendering of a prior event's decision, and that prior event — DeliveryResponsibilityDeclinedTemporarily or …Permanently — is modeled, so the fact is already in the stream. delivered_to survives as the one observable of the violation, and it is the right one for the reason the note gives: the only place this event can be seen from is the recipient's mailbox.
