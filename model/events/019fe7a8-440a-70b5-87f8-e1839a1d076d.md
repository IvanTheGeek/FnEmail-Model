## Where RFC 5321 says so

| Section | Lines | Text |
|:--|:--|:--|
| §4.2.5 | 2943-2957 | *"When an SMTP server returns a positive completion status (2yz code) after the DATA command is completed with \<CRLF>.\<CRLF>, it accepts responsibility for: o delivering the message (if the recipient mailbox exists), or o if attempts to deliver the message fail due to transient conditions, retrying delivery some reasonable number of times at intervals as specified in Section 4.5.4."* |
| §4.1.1.4 | 2045-2049 | *"In sending a positive "250 OK" completion reply to the end of data indication, the receiver takes full responsibility for the message (see Section 6.1). Errors that are diagnosed subsequently MUST be reported in a mail message, as discussed in Section 4.4."* |
| §6.1 | 3962-3965 | *"When the receiver-SMTP accepts a piece of mail (by sending a "250 OK" message in response to DATA), it is accepting responsibility for delivering or relaying the message."* |

## Notes

Merge of four sweep candidates naming one state change: DeliveryResponsibilityAccepted (×3, from the §4.2-4.3, §4.4-4.5.2 and §5-6 spans) and ResponsibilityForMessageAccepted (§1-2.4 span); rfc_refs unioned, computed fields dropped. Rejected alternative names: ResponsibilityForMessageAccepted, ResponsibilityForMessageAssumed, MessageAcceptedForFurtherProcessing, DeliveryResponsibilityAssumed. CHAPTER OVERLAP, stated rather than resolved: §4.2.5 is one of THIS chapter's anchors, but the chapter roster also gives "the 250-after-DATA moment" to Responsibility Handoff and Final Delivery; the assembler must dedupe against that chapter, and the reason both hold a claim is that one 250 carries two facts (see MessageAcceptedForProcessing, the transaction-side fact). Strength: descriptive in §4.2.5, with a MUST attached to what follows (2047-2049). Note the RFC's own hedge, "(if the recipient mailbox exists)" — acceptance obliges delivery, retry OR notification, but promises none of them. reverse_path is payload, not decoration: §4.2.5 lines 2956-2957 name it as the address a later notification must use. Rule 2 detail from the §5-6 sweep, preserved: the "must" at line 3964 is lowercase and therefore not normative. Screens: the responsibility-boundary cutoff keeps this event and discards everything it obliges.

FIELD HYGIENE PASS: struck four of six. transaction_id is fabricated — RFC 5321 supplies no transaction key; where an identity key exists at this moment it is the queue id the receiver stamps in the §4.4 ID clause (rfc5321.txt:3336), and it is carried on MessageAcceptedForProcessing, the sibling reading of the same 250, rather than duplicated here. accepting_server is struck as a session-level fact fixed by the connection. reply_code is struck as a rendering, and note that §4.2.5 is written about the CLASS (2yz), not about 250 — the class is what the event's name states. accepted_at is struck as the event's own occurrence time. Both surviving fields have jobs the RFC assigns them: reverse_path is required by the notification obligation at rfc5321.txt:2956-2957 ("using the address in the SMTP MAIL command"), which the note above already argued and which survives verification; forward_paths is what the delivery obligation is owed on, per recipient.
