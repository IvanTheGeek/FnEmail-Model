## Notes

Merged two candidates of the same name from different spans (§3.1 sweep and §4.2/4.3 sweep). Rejected alternative names: ServiceReadyAnnounced, ConnectionGreetingSent, OpeningMessageSent. Strengths: 'Normally' for sending it — not a 2119 keyword; MAY for the software identification, so its absence is a real fact set by SoftwareVersionAnnouncementDisabled and not padding; SHOULD for the sender waiting on it (§4.3.1 lines 3000-3001). announced_name is payload rather than decoration because the greeting is the one reply with its own ABNF production and §4.2 lines 2610-2612 let a client act on the text of 220. Where the host has no meaningful name an address literal stands in (§4.3.1 lines 3005-3006), which implies an unwritten ServerHostNameConfigured event. A further optional greeting fact not raised as its own event: §3.1 lines 969-971 note some systems also identify their contact point for mail problems, and say this is 'not a substitute for maintaining the required "postmaster" address'. Opposite arm, kept separate: MailSessionRefusedAtConnectionOpening. FIELD HYGIENE PASS: struck 2 fields. session_id struck — the spec names no such key; identity on this event is carried by the channel it is sent on and by announced_name, which §4.3.1 lines 3003-3005 requires to be the server's official name. reply_code 220 struck as the rendering of the decision this event already names; §4.2 lines 2610-2612 licenses a client to act on the TEXT of a 220, which is why greeting_text stays and the code does not. software_identification is kept because §3.1 makes its presence a real MAY whose absence another event causes, but its example has no RFC source and the RFC treats it as part of the same greeting line, so a later step may fold it into greeting_text.
