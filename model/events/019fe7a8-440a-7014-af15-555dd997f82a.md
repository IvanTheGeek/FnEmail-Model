## Notes

MERGED from the inherited MessageReturnedAsUndeliverable (§5.1 variant) and RENAMED to disambiguate. Explicitly NOT merged with the identically named §2.4 candidate, which is a delivery system's content judgment at the last hop — under the merge rule, a content refusal is not a routing exhaustion, and the two keep separate slots in separate chapters. Strength: MUST. Produces the same thing on the wire as the §6.1 non-delivery notification but from a different cause at a different point in the lifecycle; whether they are one event with a reason field or two events is a genuine merge question for a later step, not for Step 1, which is why both are recorded. Note the RFC calls it 'an error condition' and then requires a return rather than a report — the only branch in §5.1 that does not end in 'reported as an error', so RoutingErrorReported deliberately does not cover it. Rejected alternative names: MessageReturnedAsUndeliverable (ambiguous with §2.4 and §6.1), RoutingCandidatesExhaustedAfterSelfMatch (names the condition, not the state change the MUST requires). Which project screen would have killed it: the responsibility-boundary cutoff. ⚠️ FIELD HYGIENE PASS: struck message_id (example \<f2C8D14@foo.com>). RFC 5321 supplies no message identifier: §4.4's ID clause is optional (Opt-info = [Via] [With] [ID] [For], line 3329; ID = CFWS "ID" FWS ( Atom / msg-id ), lines 3336-3337) and is written by a receiving host into its own trace field, §6.4 line 4131 permits an originating server to add a message-id 'when none appears' and so proves one need not exist, and D.3's worked relay carries neither a Message-ID header nor an ID clause on its Received line at 5064. f2C8D14 appears nowhere in the RFC; it is this project's own minted queue-id value. What carries identity here is the envelope — the reverse-path the return must reach, which is the same address the return is addressed to, and the relay that is returning it; both surviving values come from D.3.
