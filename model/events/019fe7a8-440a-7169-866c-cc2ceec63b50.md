## Notes

Inherited (candidate 22); citations verified, and §4.1.1.7 added from the re-sweep because it is the normative definition of what EXPN returns and no inherited record cited it. Strength: MUST give the mailboxes (1273-1274), MAY include the full names (1273). The RFC's own example leaks three real addresses at three different organizations in one reply, which is why the field examples use those values rather than the project's standing ones. Line 2141 notes the reply 'will have multiple lines except in the trivial case of a one-member list' — the singleton case is the separate event UserNameExpandedAsSingletonList. Rejected alternative names: ExpnAnswered, ListMembershipReturned, MailingListExpanded (rejected because MailingListExpandedAtSource, candidate 30, already names a different act — an originating system rewriting an envelope — and conflating a disclosure with a rewrite is exactly the merge error the instructions warn against). Sibling at smaller blast radius: MailboxExistenceDisclosedViaVrfy. Consequence event by a different actor: AddressesHarvestedViaExpn. Which screen would have killed it: the consumer test (G1), the capture/decision lens, the inbound-only scope, and the guest-viewed-calendar test if the read and the disclosure are treated as one. FIELD HYGIENE PASS: nothing struck. No reply code and no invented identity key; the three disclosure values are quoted from the RFC's own EXPN reply at lines 1316-1318 and were re-verified line by line in this pass. requesting_client stays for the reason given on MailboxExistenceDisclosedViaVrfy — a disclosure is only a disclosure if there is a party it went to — and it is not a fabricated key: §4.4 lines 3325-3327 make TCP-derived information a fact the server holds, and §4.1.4 lines 2498-2500 make the client's IP a legitimate basis for deciding about EXPN specifically. Identity is the list plus the channel; the RFC supplies no session key.
