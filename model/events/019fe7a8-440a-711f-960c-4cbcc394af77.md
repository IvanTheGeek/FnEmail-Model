# `ForeignErrorRoutedToHeaderOriginator`

## Where RFC 5321 says so

| Section | Lines | Text |
|:--|:--|:--|
| §3.7.4 | 1612-1617 | *"The translation algorithm used to convert mail from the Internet protocols to another environment's protocol SHOULD ensure that error messages from the foreign mail environment are delivered to the reverse-path from the SMTP envelope, not to an address in the "From:", "Sender:", or similar header fields of the message."* |
| §4.4 | 3258-3260 | *"The reverse-path address (as copied into the Return-path) MUST be used as the target of any mail containing delivery error messages."* |
| §3.9 | 1691-1693 | *"the return address in the envelope ("MAIL FROM:") MUST be changed to be the address of a person or other entity who administers the list."* |

Line numbers are into [`docs/rfc/rfc5321.txt`](../../docs/rfc/rfc5321.txt), the archived copy. Quotations keep the specification's own words and spellings (AGENTS.md rule 2).

## Notes

RECOVERED BY THE RE-SWEEP: the violated arm, and it is the single most consequential violation in the chapter. On a mailing-list message the envelope reverse-path is the list owner and the From: is the human author, so this misrouting sends every foreign bounce to an author who cannot act on it and leaves the list owner blind — the exact failure mode Appendix B lines 4779-4786 describes as the source of repeated mail loops. Both fields are needed: recording only the destination loses the fact that a correct destination existed and was passed over. Values are chosen to make the divergence visible per rule 8 — \<Smith@bar.com> in the header, \<Jones@foo.com> on the envelope. Opposite event: ForeignErrorRoutedToReversePath. Related but distinct: the list chapter's ReturnPathRewritten is what CREATES the divergence this event then gets wrong. Rejected alternative names: ErrorMisroutedToFromAddress, BounceSentToHeaderSender. Which project screen would have killed it: inbound-only scope, responsibility-boundary cutoff.

FIELD HYGIENE PASS: struck message_ref (example f2C8D14) — no message identifier in RFC 5321; the pair of addresses is the identity and the substance together. ⚠️ CORRECTED correct_reverse_path, and the correction exposes that the preserved note and the fields disagreed. The note builds the whole case on the mailing-list divergence, where the envelope return path is the list administrator; the field then gave \<Jones@foo.com>, the walk scene's recipient, which is neither the author nor an administrator and made the divergence unreadable. §3.9 lines 1691-1693 supplies the rule but no mailbox, so the value is now an illustrative list-administrator address, plainly labeled. error_destination keeps \<Smith@bar.com>, which is correct for the From: author. Added §3.9 as a third rfc_ref so the list rule the note leans on is citable. source_header_field verified: "From:" and "Sender:" appear at line 1616.
