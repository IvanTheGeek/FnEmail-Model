|:--|:--|:--|
| §4.1.1.1 | 1787-1800 | *"In situations in which the SMTP client system does not have a meaningful domain name (e.g., when its address is dynamically allocated and no reverse mapping record is available), the client SHOULD send an address literal (see Section 4.1.3)."* |

## Notes

Carried unmerged from the §4.1.1.1 sweep. SHOULD in both places, never MUST, and the MUST that precedes it is qualified — 'MUST, if possible'. Carries a precondition nobody writes down: the client's address WAS dynamically allocated and a reverse mapping record WAS NOT created, which is a DHCP-shaped event outside SMTP entirely. §4.1.3's whole existence rests on that precondition. The IPv6 form is 'IPv6:' plus the address, and a General-address-literal needs a Standardized-tag specified in a Standards-Track RFC and registered with IANA (§4.1.3 lines 2403-2405) — a registration event with the IETF and IANA as actors on a timeline measured in years, belonging to the Extension Registry chapter. Screens: the HELO-only charter kills it outright, because the HELO ABNF at line 1831 admits only Domain — a HELO client in exactly this situation has no conforming argument, a hotspot the current model cannot express. FIELD HYGIENE PASS: struck 2 fields. session_id struck — no such key; the literal itself is what the client offers in place of a name, so it carries the identity this event is about. substitution_reason struck — the RFC gives the dynamic-allocation case only as an 'e.g.' at lines 1787-1800 and again at 2474-2479, and, more decisively, the reason is invisible on the wire: the receiving server can never observe why a literal was substituted, so recording it as payload asserts a fact no party to the protocol holds. The precondition it was trying to carry is kept in the prose above, where the note already names it as a DHCP-shaped event outside SMTP.
