# `BareLineFeedTerminationAccepted`

A receiving server treated a line ending in a bare LF as a terminated line, or a bare \<LF>.\<LF> as the end of mail data, and so ended the content somewhere the sender did not.

## Notes

RECOVERED BY THE RE-SWEEP — the sweeps quoted both MUST NOTs inside MailDataAppended's notes but never named the event. It is the receiver-side opposite of BareLineTerminatorTransmitted and the two are deliberately not merged: one is a client transmitting, one is a server accepting, and either can occur without the other. Strength: MUST NOT twice, the second time specifically about the end-of-data sequence, and the RFC goes out of its way to forbid the tolerant reading — "even in the name of improved robustness". The conforming arm produces no event but a very concrete outcome the spec never states: a client sending Unix line endings gets no termination at all, the transaction dies on the DATA Termination timeout, and the message is retried — so BareLineTerminatorTransmitted, DataTerminationTimeoutExpired and DuplicateMessageReceived are one causal chain that no single section of the RFC draws. Screens: all of them; nothing in the current model has a place for a counterparty's misbehavior. Rejected alternative names: BareLfEndOfDataMisrecognized, NonConformingLineEndingHonored.

FIELD HYGIENE PASS: struck two of three. session_id is fabricated — RFC 5321 supplies no session key; the channel is the identity, and for this event the channel is also the subject, since what the server misread is the octet stream on it. receiving_server is struck as a session-level fact: which server is receiving is established once by the connection and its greeting, and repeating it per event is padding. sequence_accepted survives and its value is the RFC's own, at rfc5321.txt:2032. Rendering caution per rule 5: \<LF>.\<LF> must stay inside a code span in any markdown, or the angle brackets are eaten silently.
