## Notes

RECOVERED BY THE RE-SWEEP — named as an uncarried sibling in the inherited ReversePathRewrittenBeforeRelay notes and kept separate on the RFC's own 'and/or' at line 3911, which says these are two facts and not one. This is the arm that changes ROUTING: rewriting the forward path changes the delivery domain and therefore re-enters DeliveryDomainLexicallyIdentified with a new name, restarting the whole chapter — which is why it belongs here and why it is not merely the mirror image of the reverse-path half (that one changes who a bounce reaches, not where the message goes). Strength: a parenthetical MAY, with no rules given for the rewrite: 🟥. The stream_root is Recipient rather than Transaction because a forward path is per-recipient and a message with three RCPTs can have one rewritten and two not. Rejected alternative names: RcptToRewrittenAtExchanger, EnvelopeRecipientRewritten. Which project screen would have killed it: the responsibility-boundary cutoff and the inbound-only scope. ⚠️ FIELD HYGIENE PASS: struck message_id (example \<f2C8D14@foo.com>), on the same grounds as the reverse-path half: RFC 5321 supplies no message identifier, §4.4's ID clause is optional and is the receiving host's trace entry (3329, 3336-3337), §6.4 line 4131 proves a message may carry none, and f2C8D14 is this project's own minted value absent from the RFC. Identity on a Recipient-rooted event is the forward-path itself — which is exactly what the old and new values carry, so striking the key cost nothing here. old_forward_path is D.3's own value; new_forward_path stays illustrative because the RFC gives no worked rewrite.
