# `RecipientFailureReportedAfterContentAccepted`

A server that deferred recipient verification until the content had arrived reported the failure as a reply to the end-of-data indicator instead of as a later mail message.

## Where RFC 5321 says so

| Section | Lines | Text |
|:--|:--|:--|
| §3.3 | 1144-1150 | *"However, in practice, some servers do not perform recipient verification until after the message text is received. These servers SHOULD treat a failure for one or more recipients as a "subsequent failure" and return a mail message as discussed in Section 6 and, in particular, in Section 6.1. Using a "550 mailbox not found" (or equivalent) reply code after the data are accepted makes it difficult or impossible for the client to determine which recipients failed."* |

## Notes

RECOVERED BY THE RE-SWEEP; no sweep produced an event from §3.3 lines 1144-1150, although one produced RecipientValidationDeferred from the §6.1 restatement of the same problem. Strength: SHOULD, on the arm the RFC prefers (return a mail message later); this event is the arm it discourages, and the discouragement is stated as a consequence rather than a prohibition — the client cannot tell WHICH recipients failed, because the reply is one code for a transaction that may carry a hundred recipients. That information loss is the state change worth recording. Doubtful because it is a described practice rather than a specified behavior, and because it overlaps MessageRejectedAtEndOfData on the wire: the difference is entirely in the cause and in what the client can learn. Preferred sibling, owned by the Non-Delivery Notification chapter and cross-referenced: the subsequent-failure mail message of §6.1. Related: RecipientValidationDeferred (§6.1 lines 4000-4006), which is the precondition and belongs to Mail Transaction. Screens: the consumer test and the one-event-per-command target.
