## Notes

Inherited from candidate 234; citations checked and correct. "Permanent" is a claim about this exchange, not about the world — the RFC says so directly at 2685-2686 and names its two cures, which are the source of two over-time events living in other chapters (RecipientAddressCorrected, raw candidate 253, and AccountStatusAltered, raw candidate 244). Strength: SHOULD NOT for repeating, which is markedly weaker than the MUST NOTs §4.2.5 applies after end-of-data; the difference is load-bearing — a 5yz to RCPT discourages repetition, a 5yz after \<CRLF>.\<CRLF> forbids the server from ever retrying. Kept separate from TransientFailureReturned for the reason stated there. Screens: the condemned status register.

FIELD HYGIENE PASS (chapter 14): three of four fields struck. session_id struck — RFC 5321 names no session, transaction or connection identifier, and f2C8D14 is nowhere in the RFC; identity here is position in the session. reply_code struck as the rendering of the server's decision: lines 2557-2559 assign the number to the automaton, but on the emitting side it is the decision written out, and the 5yz class the client actually forks on is already in the event's name — keeping the code would also have made the permanent arm look like a payload difference when it is a naming difference. failure_text struck: "the text is for the human user" (2558-2559). command_verb KEPT: the command was refused, so no accepted-command event records it and this is the only capture of what drew the refusal.
