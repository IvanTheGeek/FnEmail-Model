## Notes

RECOVERED BY THE RE-SWEEP — the violated arm of a MUST NOT that the sweeps recorded only as a folded sibling ("MessageDataWithheldByClient") inside DataCommandRejectedOutOfSequence's notes, never as an event. Strength: MUST NOT, stated twice in one sentence, the second time generalized to every case. The honored arm is the absence of an event, which is why only the violation is nameable here. Consequence the RFC does not state: the content lines are then parsed as commands and each draws a 500, which is how this failure actually surfaces — worth a hotspot, since nothing in §3.3 says what the server does. Doubtful as an event because it is non-conforming client behavior rather than a sanctioned state change; kept under the kit's "If unsure whether something is state-changing, include it and refine later". Screens: the inbound-only scope keeps the arrival but not the client's act; the responsibility-boundary cutoff and the altitude tiers both file it below Protocol. Rejected alternative names: MessageDataSentWithout354, PrematureContentTransmitted.

FIELD HYGIENE PASS: struck two of three. session_id is fabricated — RFC 5321 supplies no session key; the channel carries identity, and here it carries the whole finding, because the violation is defined entirely by what state the channel was in. last_reply_received (503) is struck as a rendering of a prior event's decision, recoverable from that event. first_content_line survives as the one fact that makes the event observable at all — the octets that arrived when they should not have. Its value is the walk scene's 1998 timestamp in a Date header field, and the field name Date is itself named by the RFC at rfc5321.txt:1153 ("the header fields such as those named Date, Subject, To, Cc,"); Appendix D's own content line at rfc5321.txt:4903 is a placeholder ("Blah blah blah...") and teaches less, per rule 8.
