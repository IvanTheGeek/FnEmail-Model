## Notes

RECOVERED BY THE RE-SWEEP — no inherited candidate carried the reply-code half of disabling, though two carried the disabling act. This is where the violated arm actually lives, and it is a configuration violation, not a runtime one: choosing 500, 502 or a blanket 550 for a disabled VRFY is a setting, made once, that puts the server permanently out of conformance. The RFC names all three wrong answers explicitly — 500/502 at §3.5.3 1380-1381, a blanket 550 at §7.3 4249-4251, a bare 250-after-syntax-check at 4247-4248 — and one right answer, 252, under a MUST. Four citations because each names a different failure; none is redundant. Kept as its own event rather than a field on VrfySupportDisabled because the two fail independently: a site may disable correctly and answer wrongly, or never disable at all and still answer 250 after a syntax check. Screens: the HELO-only charter and the condemned status register. FIELD HYGIENE: nothing struck. This is the one place in the chapter where a reply code survives the derived-value rule, and the line that makes it data is §7.3 4243-4245 (rfc5321.txt:4244), which lays a MUST on which code a disabling site returns; the RFC then enumerates four different configured values a site can actually hold — 252 conforming, and 500, 502, blanket 550 and bare 250 each named as non-conforming — so the field records a stored choice that varies, not the rendering of a runtime decision. disabled_command likewise varies, on §3.5.2's 'either or both', with VRFY sourced at 4239-4240. No session, transaction or connection key was present; identity is the site named by its domain plus the command the setting applies to.
