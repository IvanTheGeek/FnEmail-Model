## Notes

Inherited from raw candidate BounceSuppressedForHostileContent, kept intact. SHOULD NOT with an escape clause ("unless the receiving site is confident that those messages will be usefully delivered"), plus an explicitly stated default at 4061-4063 — the RFC rarely names its own default this plainly, and that sentence is what settles the ambiguity the escape clause opens. LIVE CONTRADICTION, recorded and deliberately not resolved: §6.1 3970-3971 makes notification a MUST on any post-acceptance delivery failure, while this is a SHOULD NOT. The available reconciliation is that §6.2's case is a rejection rather than a post-acceptance failure — but the chapter never says so, and §6.2 4018-4020 explicitly routes messages that "cannot be delivered, and cannot be rejected by the SMTP server during the SMTP transaction" into the bounce path, which puts them straight back under §6.1's MUST. A reader applying both literally is stuck. This is a hotspot at the point where it bites, not an appendix note. The precondition HostileContentDetected is recovered as its own event below; the RFC disowns the decision in the same sentence that depends on it. Opposite event, recovered below: BounceSentDespiteHostileContent. Rejected alternative names: NonDeliveryMessageWithheld, BackscatterAvoided (rejected — 'backscatter' is not the RFC's word). Which screen would have killed it: the four altitude tiers would exile the content detection to a non-protocol tier and then leave nothing to trigger the suppression.

=== FIELD HYGIENE PASS === Struck two of three fields. (1) message_ref (f2C8D14) — fabricated; RFC 5321 supplies no message identifier. (2) rejection_reason — struck: it held the constant "hostile content", which the event's own name already states and which the RFC states at rfc5321.txt:4058 and 4063; a field with one possible value carries no information, and its content is now the separate event HostileContentDetected, so keeping it here also duplicated a fact across two events. WHAT CARRIES IDENTITY HERE INSTEAD: the reverse-path of the rejected message, the surviving field — the only handle available once the minted key is gone, and the address the withheld bounce would have gone to. Example corrected: it read \<Jones@foo.com>, the walk scene's RECIPIENT standing in a reverse-path field; a bounce goes to the originator, \<Smith@bar.com> (rfc5321.txt:4893).
