## Notes

Merged from two DeliveryAttemptFailed records and from ConnectionAttemptFailed (Appendix D.3, 4997-4999, narrated in prose with no reply code because there is no server to answer) — rejected names: ConnectionAttemptFailed, DeliveryAttemptFailedForAddress. DeliveryAttemptFailedForAddress (§5.1 3874-3876, per candidate address in a multihomed list) is deliberately NOT merged: it is the address-level fact inside one host-level attempt and it belongs to the address-resolution chapter; cross-referenced, not claimed. No keyword attaches to the failure itself — the MUST at 3703-3704 presupposes it ("after one attempt has failed"), which is the strongest evidence that the fact must be recorded. failure_reason is kept because the RFC explicitly wants strategy to vary with it (3705-3707). Dropped as derived: attempt_number. Distinct from DeliveryGivenUp — one attempt failing is not concluding the message can never be delivered, and conflating them is how retry logic gets lost. Screens: inbound-only scope, responsibility-boundary cutoff. ⚠️ FIELD HYGIENE PASS: STRUCK destination_address — derived by address resolution, and the per-address arm of this fact is the address-resolution chapter's DeliveryAttemptFailedForAddress, which the notes above already decline to merge; carrying the address here claimed it twice. destination_host is kept and is essential rather than decorative, because the MUST at 3703-3704 is scoped per destination. attempted_at is kept for the same reason: the mandatory delay is measured from this exact moment, so it is payload, not an occurrence stamp. queue_entry_id kept on §4.4's ID-clause ground (rfc5321.txt:3336); f2C8D14 is this project's minted value, not the RFC's.

COLLISION RESOLVED — merged from 2 independently brainstormed records. The closest call of the eighteen, and it merges. Both copies root at Queue Entry and both cite 3.6.3 1494-1496 word for word; the actors differ only as a subtype, since a relay that accepts the task 'then becomes an SMTP client' (3.6.2 1450-1453), so 'relay SMTP server acting as SMTP client' is 'sending SMTP client'. The RFC draws no distinction between an originator's failed attempt and a relay's: 4.5.4.1 3690-3693 speaks generically of a mail queue entry that 'will include not only the message itself but also the envelope information'. The genuinely separate arm here is per-address, at 5.1 3873-3877, and neither copy claimed it — which is the evidence that these two were claiming the same host-level fact.

From the duplicate in 8. Relaying: Carried from #83. Distinct from DeliveryDeterminedImpossible and NOT merged with it: one attempt failing is not the same fact as concluding the message can never be delivered, and conflating them is how retry logic disappears. The evidence that attempts are countable and individually recordable is the RFC's own plural at 1480, 'subsequent delivery attempts'. Strength: none stated. HOTSPOT: this span never specifies retry counts, intervals, or a give-up rule - nothing says when a relay is PERMITTED to stop trying, only what it MUST do once it has decided. Rejected names: OnwardDeliveryAttemptFailed, RelayAttemptFailed.
