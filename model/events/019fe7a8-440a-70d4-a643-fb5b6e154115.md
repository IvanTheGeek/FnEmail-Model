## Where RFC 5321 says so

| Section | Lines | Text |
|:--|:--|:--|
| §4.5.3.1.8 | 3537-3539 | *"The minimum total number of recipients that MUST be buffered is 100 recipients. Rejection of messages (for excessive recipients) with fewer than 100 RCPT commands is a violation of this specification."* |
| §4.5.3.1.8 | 3546-3550 | *"A client that needs to deliver a message containing over 100 RCPT commands SHOULD be prepared to transmit in 100-recipient "chunks" if the server declines to accept more than 100 recipients in a single message."* |

## Notes

RECOVERED BY THE RE-SWEEP: the VIOLATED ARM of the MUST at 3537-3538, stated by the RFC in its own words as 'a violation of this specification' — one of the few places in the whole document where the spec names the non-conforming state outright rather than leaving it to be inferred. No sweep harvested it; the honored arm (RecipientBuffered, RecipientBufferLimitReached) was harvested twice. configured_limit rather than a count of accepted recipients: the limit is a stated fact of the server, a count would be derived from the stream, and it is the limit being below 100 that makes the event what it is. This event is a conformance fact, and it has a real consumer — an operator or a conformance monitor watching a peer, which is exactly the reader the raw set's UnknownCommandRejected candidate identified for the same kind of evidence. Rejected alternative names: NonConformingRecipientLimitApplied, RecipientLimitViolatedSpecification. Screens: the consumer test G1 would kill it inside the current model, and the altitude tiers would place it outside the Protocol tier.

FIELD HYGIENE PASS: struck two fields. session_id (f2C8D14) goes because RFC 5321 supplies no session identifier and the value is this project's own minted queue-id example from commit 6acfc68; identity is the channel while the session lives. reply_code (452) goes on two grounds at once: it is the wire rendering of a decision, and §4.5.3.1.8 3537-3539 states this violation without naming any code at all, so the value was unsourced — the RFC's 452 MUST at 3598-3600 governs a conforming implementation limit, which is the opposite case. configured_limit SURVIVES and is what makes the event a violation rather than a refusal; the note's reasoning for choosing a stated limit over a derived count is exactly right and is preserved. Its example is labeled illustrative because the RFC names only the 100 floor (3537), never a violating value.

From the duplicate in 14. Protocol Fault Handling: RECOVERED BY THE RE-SWEEP from §4.5.3.1.8 lines 3537-3539 — the violated arm of the buffered-recipient MUST, which no inherited candidate carried as an event although candidate 321 mentioned the floor when discussing configuration. Distinct from PreviouslyAcceptedRecipientsDiscarded: that one is a disorderly limit, this one is a limit set too low in the first place, and the two can occur in the same session. It is the runtime consequence of a non-conforming RecipientLimitConfigured, the same configuration-then-violation pairing as ShortCommandLineRejectedAsTooLong. The 100-recipient floor is also what makes the client's chunking strategy terminate — merged sibling, named rather than given a row: RecipientListSplitIntoChunks, the client's SHOULD at 3546-3550 to transmit in 100-recipient chunks when a server declines more; without the floor the chunking could shrink forever, which is exactly the convergence argument the RFC spells out at 3580-3596.

FIELD HYGIENE PASS (chapter 14): session_id struck — RFC 5321 names no session, transaction or connection identifier, and f2C8D14 is nowhere in the RFC; identity here is the transaction plus the forward-path. recipients_accepted struck as a derived fold: the violation is established by folding the transaction's accepted recipients against the 100-recipient floor at lines 3537-3538, which is read-model work by the method's own rule, and a fold does not become payload by being copied onto the event that provokes it. rejected_forward_path KEPT.
