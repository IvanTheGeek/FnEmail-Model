## Notes

Recovered by the re-sweep as the violated arm of the SHOULD at 600-602 — no sweep carried it, and it is the arm that costs a real message. Both timeout values are on the payload deliberately: the violation is visible only as a comparison, so an event carrying one of them proves nothing. The example values here are equal rather than inverted, which is the commonest way an operator gets this wrong. Distinct from DeliveryGivenUp, which is give-up after exhausted retries; here retries were still possible in a form that was never attempted. Rejected name: FallbackTimeoutMisorderedAgainstBounceTimeout. Screens: HELO-only charter, inbound-only scope, condemned status register. ⚠️ FIELD HYGIENE PASS: NOTHING STRUCK, and the decision is a close one worth recording. Both durations are configured values, and the same argument struck give_up_after_days from DeliveryGivenUp as configuration restated. They are kept here because the SHOULD at 600-602 constrains only their RELATIONSHIP, so a payload carrying one of them says nothing at all, whereas DeliveryGivenUp's copy said nothing the configuration event did not already say. The countervailing point is recorded rather than resolved: the comparison itself is a fold and a read model could perform it from RetryParametersConfigured and ExtensionFallbackTimeoutElapsed, in which case these two fields would go and this event would reduce to identity plus required_extension. bounce_timeout_days keeps the RFC's own three-day figure (602-603); requeue_timeout_days is labeled illustrative because three days is NOT the RFC's figure for it — one day is — and the equality is the whole point.
