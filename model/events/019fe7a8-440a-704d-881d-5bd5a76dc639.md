## Notes

RECOVERED BY THE RE-SWEEP as the violated arm of the MUST at 4071-4072 — and it is the arm that explains why §6.3 exists, since a loop only persists because some server did this. Note the strength collision that makes the event ambiguous rather than simply non-conforming: §3.6.3 line 1527 says loop detection is something a relay does 'optionally', while §6.3 4071-4072 makes stopping trivial loops a MUST. A server that passes on a *non-trivial* loop is therefore conformant under both, and one that passes on a trivial one violates §6.3 while looking like it exercised §3.6.3's option. Since 'trivial' is undefined, no observer can tell which happened. 🟥. The event is also self-amplifying in a way worth drawing: its own occurrence increments received_count, which is the evidence the *next* server will use, so a chain of these events is what eventually produces MailLoopDetected somewhere downstream — the failure creates its own detector. Opposites: TrivialLoopStopped, MailLoopDetected, LoopingMessageRejected. FnEmail screens: the responsibility-boundary cutoff, the inbound-only scope, and the consumer test. ⚠️ FIELD HYGIENE PASS, two strikes. `message_ref` struck: RFC 5321 supplies no message identifier and f2C8D14 is this project's minted queue id; identity is the growing Received: chain, which is the only thing that persists across the hops this event describes. `received_count` struck as a derived value — a count folded from the lines the message carries. THE SELF-AMPLIFYING ARGUMENT ABOVE SURVIVES AND IMPROVES: what the event's occurrence actually increments is the number of Received: lines in the message, which is data; the count is what a later reader derives from them. Stating it that way removes the last suggestion that a counter travels with the message. The event is now single-field; its justification stands on the act of forwarding, not on the struck field.
