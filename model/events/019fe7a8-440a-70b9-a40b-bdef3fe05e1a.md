## Notes

MERGE: MailTransactionInitiated (the §1-2.4 sweep) and MailTransactionStarted (the §4.1 sweep) are the same state change under two names; rejected alternatives carried here so the naming work is not lost — MailTransactionInitiated, TransactionOpened. Strength: declarative, no RFC 2119 keyword on the opening itself. Deliberately kept SEPARATE from ReversePathDeclared, TransactionBuffersCleared and ReversePathBuffered even though one MAIL command produces all four: the §3.1-3.3 sweep folded MailTransactionStarted INTO ReversePathDeclared and said so in its notes, and the fold is what the project's 'one event per command' design target forces — that screen is named and not applied here. transaction_id must be separate from session_id because 2506-2507 makes many transactions per session explicit. Opposite events: MailTransactionAborted, MailTransactionConfirmed, PendingTransactionCanceled. Sibling recovered by the re-sweep and held over for cap reasons: ObsoleteTransactionBeginningCommandReceived — 2502-2503 and 2507 name SEND, SOML and SAML as transaction-beginning commands, so receiving one is a distinct event.

FIELD HYGIENE PASS: struck three fields, leaving the event FIELDLESS. session_id (f2C8D14) and transaction_id (f2C8D14-t1) go because RFC 5321 supplies no session, transaction or connection identifier — grep for 'session (id\|identifier)\|transaction (id\|identifier)\|connection (id\|identifier)' over docs/rfc/rfc5321.txt returns nothing, and f2C8D14 returns nothing either; it is this project's own minted queue-id example, traceable to commit 6acfc68. ⚠️ The note above argues 'transaction_id must be separate from session_id because 2506-2507 makes many transactions per session explicit'. 2506-2507 is real and the inference is not: the RFC makes many transactions per session explicit and names NONE of them, which is the finding. What carries identity here is position in the session — while the session lives the channel is its identity, and the open transaction is the one begun by the last MAIL and not yet confirmed or aborted. started_at struck as well: RFC 5321 places a date-time in exactly one construct, the Received stamp at §4.4 3311-3313, which belongs to the trace chapter; MAIL carries no time on the wire, so occurrence time here is ambient log metadata rather than payload — and the example was not even the RFC's, whose own timestamps read 'Thu, 21 May 1998 05:33:29 -0700' (5014). Fieldless is the correct outcome: this event's whole content is that a transaction is now open, and the MAIL command's actual payload is carried by ReversePathDeclared, which this chapter deliberately keeps separate.
