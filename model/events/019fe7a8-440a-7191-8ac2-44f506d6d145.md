## Notes

The RFC distinguishes two limit_kind values with different obligations, and the field exists to carry that: an IMPLEMENTATION limit MUST answer 452 (3598-3600), a SITE-POLICY limit MAY answer 5yz (3601-3603). The distinction is invisible to the client except through the code, and the client's retry behavior forks on it. §4.5.3.1.8 3543-3546 added by the re-sweep — a MUST on ORDERLY behavior that the raw set did not carry, whose violated arm (silently discarding recipients already accepted) is the worst failure in this whole section because the client is told the message was accepted for addresses that were dropped. The event is a precondition the spec presupposes: §4.5.3.1.10 opens with 'If the server has a configured site-policy limitation', so the configuring act already happened and nobody wrote it down. Client-side counterpart, deliberately separate: ClientRecipientsPerTransactionLimitConfigured. Screens: the condemned status/config register, the altitude tiers, inbound-only scope. FIELD HYGIENE: struck overflow_reply_code (550). §4.5.3.1.10 3598-3603 derives the code from limit_kind — an implementation limit MUST use 452, a site-policy limit MAY use a 5yz — so carrying the code duplicated a derivation the spec states outright, and the emission itself happens at runtime when the limit is exhausted; that fork is preserved in the note above and in the citation rather than as a field. limit_kind survives and is the fact that matters, sourced to the phrase 'configured site-policy limitation' at rfc5321.txt:3601. max_recipients is a real configured value, but its example is labeled illustrative because the RFC supplies only the floor of 100, never a ceiling. No session, transaction or connection key was present; identity is the server named by its domain.
