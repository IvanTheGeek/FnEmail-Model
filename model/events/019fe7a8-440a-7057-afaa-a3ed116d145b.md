## Notes

Inherited candidate 274, kept, refs unioned with §4.5.3.2.6 from candidate 337. An unusual MUST: it binds effort — 'MUST seek to minimize' — with no threshold, so it is unverifiable as written and the duplicate is the only observable fact. That is why there is no honored-arm event here and why saying so matters: EndOfDataResponseIssuedPromptly was considered and refused, because nothing in the RFC makes 'prompt' decidable. The sender-side sibling is MessageRetransmittedAfterTimeout, owned by whichever chapter carries §4.5.3.2 timeouts; the recipient-side consequence is DuplicateMessageCopiesDelivered, below, and the two are deliberately kept apart because they can be days apart and belong to different roots. Screens: the 'one event per command' target would refuse a second event arising from the same DATA command. ⚠️ FIELD HYGIENE PASS 2026-08-09 — three fields struck, and the strip turns up the sharpest finding in the chapter. message_id AND duplicate_of both went: RFC 5321 supplies no message identifier (§4.4's ID clause at line 3336 is optional and is the receiver's own trace clause; msg-id is RFC 5322's), and both carried the same example f2C8D14 — this project's minted queue_id value — which made the pair look like a correlation the protocol provides. It does not. 🟥 With no identifier on the wire, the receiver has no protocol means of RECOGNIZING the second copy as a copy; that is precisely why §6.1 4008-4011 can only tell it to answer faster, and why the RFC offers prevention rather than detection. The event remains a real fact about the world — two copies arrived — but its actor cannot observe it as such, and that gap is the finding, not a defect in the event. cause: struck because the RFC names exactly one cause here ('as the result of timeouts', 4008-4009), so the field could take only one value and carried no information. Identity is the channel and the retransmission that arrived on it.

That inability is itself the hotspot: the RFC asserts the duplicate exists without saying how anyone detects it. Sender-side sibling: DataTerminationTimeoutExpired. FIELD HYGIENE PASS: struck all four fields, and the strip completes an argument the merge had only half-made. The merge already rejected a Message-Id form on the correct ground that Message-Id is RFC 5322's, not RFC 5321's — but it then substituted transaction_id and duplicate_of_transaction_id, which RFC 5321 does not supply either. Both are struck, and with them goes the last pretense that the receiver can name what this message duplicates: that is precisely the hotspot the note states, and a fabricated correlation key was hiding it. receiving_server is struck as a session-level fact. cause is struck as a derived diagnosis — it is an inference about the far end's timer that the receiver cannot make, and §6.1 4008-4009 states the mechanism generically rather than as per-instance data. Fieldless, and the emptiness is the finding: RFC 5321 asserts duplicates exist and supplies nothing with which to identify one. Confidence stays likely — the event is real; only its detectability is in doubt, and that was already recorded.
