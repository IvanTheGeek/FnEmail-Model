## Notes

RECOVERED BY THE RE-SWEEP. The capped sweep named it in HeaderAddressTransformedForInternet's notes as "dropped for space" — a candidate the cap killed, restored here. It is the LIBERAL-ACCEPTANCE half of the chapter's Postel pair; HeaderAddressTransformedForInternet is the CONSERVATIVE-GENERATION half, and the two must stay separate because their strengths differ (SHOULD accept, MUST generate conformant) and because one governs input and the other output. Strength: SHOULD. The example is the RFC's own source-routed forward-path from §4.1.1.3 line 1944, so it is real by construction rather than invented. Rejected alternative names: LiberalAddressAcceptanceApplied, AllValidAddressFormatsAccepted, InternetSideAddressAccepted. Opposite event: ValidAddressFormatRefusedByGateway. Which project screen would have killed it: inbound-only scope; the capture/decision lens would want this classified before allowing it.

FIELD HYGIENE PASS: nothing struck — this record carried no fabricated identity key and no f2C8D14, which makes it one of only three clean records in the chapter (with SourceRouteIgnoredByGateway and GatewayDesignatedForTransportBoundary). Both address-bearing values verified in the source: line 1944 reads RCPT TO:\<@hosta.int,@jkl.org:userc@d.bar.org>, which sources accepted_address and accepted_in together. accepted_in survives the essentiality test because §3.7.3 line 1596-1597 distinguishes two loci — "in SMTP commands and in the RFC 822 header section" — and which one the address arrived in is a fact, not a derivation.
