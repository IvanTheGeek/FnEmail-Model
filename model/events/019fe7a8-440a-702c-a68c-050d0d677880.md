## Notes

Carried over from idx 194 with its citations verified and tightened (the inherited '3173-3176' split into 3173-3174 and 3175-3176, which are two different sentences with two different jobs). MUST, but conditional — it fires only 'If the FOR clause appears', so omitting FOR entirely is fully conforming and is the usual escape for a multi-recipient message; that escape is now its own event, TraceForClauseOmitted, recovered by the re-sweep. Opposite arm: MultiplePathsStampedInForClause. Consequence when the narrowing is done badly or not at all: BlindCopyRecipientDisclosedInTraceField (§7.6). A third sibling the inherited notes named and I did not promote — MessageSplitPerRecipient, one copy per recipient so each copy's FOR is honestly single — belongs to the delivery chapter, not here. Rule 8 note kept from the inherited record: instantiate other_accepted_paths with a real second recipient and the disclosure problem is visible immediately. FnEmail screens: the 'one event per command' target — this event has no command of its own, it is a consequence of the RCPT count exceeding one, discovered at stamping time. ⚠️ FIELD HYGIENE PASS: struck the fabricated `message_ref` identity key — the RFC supplies no message identifier, and f2C8D14 is not in it. Identity is carried by the forward-paths themselves, which is fortunate for this event: the narrowing is a relation between one chosen path and the accepted rest, so the two surviving fields are the event. Sourcing check on the rule-8 value: \<Brown@foo.com> is the RFC's own second recipient in Appendix D.4 at line 4899, so the multi-recipient case is instantiated from the spec rather than invented.
