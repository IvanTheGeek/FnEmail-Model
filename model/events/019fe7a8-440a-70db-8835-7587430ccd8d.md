## Notes

THREE commands abort (2505-2506), hence aborting_command as a field rather than three sibling events — real values: RSET, EHLO, QUIT. 🟥 HOTSPOT under rule 12: 2085-2089 lists FOUR positions where RSET 'is effectively equivalent to a NOOP (i.e., it has no effect)' — immediately after EHLO, before EHLO, after an acknowledged end of data, and immediately before QUIT. In those positions THIS EVENT DOES NOT OCCUR, so the same command is sometimes an event and sometimes not; the no-op case is set aside as a non-event, not merged in. Two boundaries a later step must keep: RSET MUST NOT close the connection (2089-2091), that being reserved for QUIT — so a timeout is not a QUIT and a RSET is not a close. Cross-reference, DO NOT MERGE: SessionReinitialized (raw set) is the EHLO-arm of this same abort seen from the session's side, and PendingTransactionCanceled is an abort with no command behind it at all. Rejected alternative names: TransactionReset, TransactionDiscarded. Nothing in FnEmail kills the base event.

FIELD HYGIENE PASS: struck two fields, session_id (f2C8D14) and transaction_id (f2C8D14-t1). Both key and value are fabricated: grep over docs/rfc/rfc5321.txt for session, transaction or connection identifiers returns nothing, and f2C8D14 returns nothing either — it is this project's own minted queue-id example from commit 6acfc68. What identifies the aborted transaction is its position in the session: it is the one opened by the last MAIL and not yet confirmed, which 2507-2512 states from the other direction when it lists the only three legal positions for a new MAIL. While the session lives the channel is its identity, and after QUIT there is no session to name. aborting_command SURVIVES with the real three-value range the RFC gives at 2505-2506 — RSET, EHLO, QUIT — which is what keeps three sibling events from being needed, and the 🟥 hotspot about RSET's four no-op positions is untouched by this pass.
