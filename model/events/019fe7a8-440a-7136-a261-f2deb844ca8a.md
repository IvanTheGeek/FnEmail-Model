## Where RFC 5321 says so

| Section | Lines | Text |
|:--|:--|:--|
| §3.9.2 | 1723-1727 | *"The return (backward-pointing) address in the envelope is changed so that all error messages generated by the final deliveries will be returned to a list administrator, not to the message originator, who generally has no control over the contents of the list and will typically find error messages annoying."* |
| §6.1 | 3970-3973 | *"If there is a delivery failure after acceptance of a message, the receiver-SMTP MUST formulate and mail a notification message. This notification MUST be sent using a null ("\<>") reverse-path in the envelope."* |

## Notes

CITATION CORRECTED during the merge: the inherited candidate cited §6.1 lines 3971-3974 for the notification MUST; the sentence begins at line 3970 ("If there is a delivery failure after acceptance of a message, the") and the null-reverse-path MUST ends on 3973, so the range is 3970-3973. §6.1 heading confirmed at line 3960. The payoff event, and it happens long after the session that carried the message has closed — possibly days later, after the §4.5.4.1 retry schedule runs out. Green@foo.com is used because Appendix D.1 line 4898 makes it the failing recipient with "550 No such user here" in the RFC's own worked multi-recipient scenario. The notification itself carries a null reverse-path per §6.1 3972-3973, which is why it cannot bounce again; §4.5.5 lines 3796-3801 says such failures are often routed to the postmaster alias instead, tying this back to AliasExpanded. Opposite event, kept separate and cross-referenced: ErrorMessageReturnedToOriginator, which is what happens when the rewrite did not occur. Screens: responsibility-boundary cutoff kills it outright; chapter 12 (Non-Delivery Notification) owns the bounce's composition, this chapter owns only where it landed. FIELD HYGIENE PASS: reply_code struck — 1 field. A reply code is the rendering of a decision on the wire, and the test the method sets is whether the RFC carries the code itself as data beyond that. It does not here: §6.1 (3970-3973) requires that a notification message be formulated and mailed with a null reverse-path and says nothing about the code travelling on it, and the 550 in the example is a wire reply spoken by foo.com inside a live session at rfc5321.txt:4898, days earlier and to a different party than the bounce this event describes. Instantiating it made that plain — the 550 in the field is a reply this delivery agent never sent and this administrator never sees. No identifier was struck or added: the bounce is a different message from the one that was expanded, so no queue id of the original applies to it, and RFC 5321 supplies no identifier that would link them; what identifies this event is the administrator it reached and the recipient whose delivery failed.
