## Notes

RECOVERED BY THE RE-SWEEP. The raw candidate FailedNotificationRedirectedToPostmaster said in as many words that it had folded this companion event in "for slot budget" — the 32-event cap, admitted on the record — so recovering it is the cap's cost being paid back. It is a standing rule with a lifetime measured in years, and every FailedNotificationRedirectedToPostmaster presupposes that it fired at some earlier time; without it, the redirect has no cause. Strength: none — the RFC describes the arrangement at some hosts and requires it nowhere. "e.g., via the postmaster alias" makes the mechanism illustrative, so redirect_target is not necessarily a postmaster address, and the model must not assume it is. Related but NOT merged: PostmasterMailboxProvisioned (§4.5.1, the mandatory postmaster mailbox) is a different configuration event in the provisioning chapter — having a postmaster address and routing dead notifications to it are separate acts. Rejected alternative names: DeadLetterRedirectConfigured, PostmasterAliasProvisioned, FailedNotificationRoutingConfigured. Which screens would have killed it: every one — no command, no session, no consumer; the altitude tiers put it below Protocol tier.

=== FIELD HYGIENE PASS === NOTHING STRUCK. The second of only two events in the chapter that carried no fabricated field — no message_ref, no f2C8D14, no session or transaction key. host survives as the Server Configuration stream's own identity rather than as a restatement of the actor (a host administrator), the same line drawn for site on InvalidReturnAddressDropPolicyAdopted and against the nine actor-restating host fields struck elsewhere here. redirect_target survives with the RFC's "e.g." at rfc5321.txt:3801 recorded in its example_source, so the illustrative status the note above insists on now travels with the field rather than only with the prose.
