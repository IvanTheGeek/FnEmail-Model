## Notes

Harvested by meaning from the §3.4-3.5 sweep, which filed it under "List Expansion at Source" — the state change is list expansion and belongs to this chapter even though its anchor (§3.5.4, heading confirmed at line 1407) is chapter 13's. Kept separate from PseudoMailboxExpanded and NOT merged: a relay's expansion is not an originator's, the actor differs, the moment differs (before any RCPT is sent rather than after acceptance), and the return path is untouched because there is no list in the envelope to rewrite for. The RFC describes it as attempted practice rather than prescribing it, and §3.5.4 goes on to deprecate the deduplication that motivated it — but the expansion itself is not what is deprecated, only its use for eliminating duplicates, which is the separate event below. Rejected alternative names: SourceExpansionPerformed, ListExpandedByOriginator, RecipientListFlattenedBeforeSend. Screens: inbound-only scope, responsibility-boundary cutoff, altitude tiers. FIELD HYGIENE PASS: nothing struck, and worth recording why no identifier was added to fill the gap. This event fires at the originating end before any RCPT is sent, so nothing has been accepted anywhere, no receiving host has stamped a §4.4 ID clause, and there is no queue id, message id or transaction id to carry — RFC 5321 supplies none of them, and the grep confirms it. What identifies the event is the list it expanded and the host that did it. All three surviving values are the RFC's own: Example-People and its three members from the EXPN example at 1315-1318, and bar.com from Appendix D.1 line 4881 as the sending host.
