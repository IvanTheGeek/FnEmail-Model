## Notes

Carried from the inherited candidate; the §6.1 ref is dropped from the refs and kept as the consequence note instead, since §6.1 belongs to the Non-Delivery Notification chapter. Strength: a MAY, and only a PARENTHETICAL one — the span gives no rules for the rewrite itself anywhere: 🟥. Consequence that reaches beyond routing: rewriting the reverse path changes who a later bounce reaches, tying straight to §6.1's MUST that the notification go to the address from the envelope return path. Counter-case worth keeping: at §4.1.1.3 the RFC's own worked relay forwards the reverse-path UNCHANGED (compare lines 1943 and 1949) — a relay does not become the sender, so this rewrite is the exception rather than the rule. The RCPT TO half is a separate event on the RFC's own 'and/or' and must not be fused. Rejected alternative names: MailFromRewrittenAtExchanger, EnvelopeSenderRewritten. Which project screen would have killed it: the responsibility-boundary cutoff and the inbound-only scope. ⚠️ FIELD HYGIENE PASS: struck message_id (example \<f2C8D14@foo.com>). RFC 5321 supplies no message identifier — §4.4's ID clause is optional and belongs to the receiving host's trace field (3329, 3336-3337), §6.4 line 4131 permits an originating server to add a message-id 'when none appears' and so proves one need not exist, and f2C8D14 appears nowhere in the RFC. On a Transaction-rooted event, identity is the transaction's position in the session, and the reverse-path is what the MAIL command set; the before and after are the whole state change and neither is recoverable from the other. old_reverse_path is D.3's own value; new_reverse_path stays illustrative because the RFC gives no worked rewrite, which is the same 🟥 recorded above.
