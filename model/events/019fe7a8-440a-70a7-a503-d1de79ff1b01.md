# `EndOfMailIndicatorRecognized`

A line consisting of a single period was recognized by the server as the end of the mail data, closing the content and releasing the stored transaction for processing.

## Notes

Harvested; §4.1.1.4 line 2036-2037 added by re-sweep, and it is what turns this from a parsing detail into an obligation — receipt REQUIRES the server to process the stored transaction. Kept separate from EndOfMailDataIndicated because the two ends can disagree about whether this happened: that disagreement is exactly what DataTerminationTimeoutExpired and DuplicateMessageReceived are made of. §4.4 line 3275-3277 hangs the entire partial-success apparatus on "the processing following the end of mail data indication", so naming the indicator as its own event is what makes that dependency visible; folding it into MessageAccepted hides that acceptance, trace insertion, delivery and notification all occur strictly after it, in that order. Fieldless would be defensible (the kit permits it) but recognized_at is the timestamp the trace line's stamp derives from, so it is not padding. Screens: the 'one event per command' target (DATA already has its event) and the consumer test. Rendering note per rule 5: "\<CRLF>.\<CRLF>" must stay inside a code span in any markdown or the angle brackets vanish silently.

FIELD HYGIENE PASS: struck both fields, and this overturns one sentence of the note above. transaction_id is fabricated — RFC 5321 supplies no transaction key; identity is the channel, and the event is fixed by position. recognized_at is struck too: the note defended it as "the timestamp the trace line's stamp derives from", but that is the argument for its being derivable, not for its being payload. The trace stamp of §4.4 (Stamp ... FWS date-time, rfc5321.txt:3311-3313) is a consumer's copy of this event's own occurrence time, and an event's occurrence time is inherent to it, not a field on it. So the honest reading is the one the note called defensible: fieldless. What the event carries is the obligation §4.1.1.4 2036-2037 attaches to it, and that is not a payload.
