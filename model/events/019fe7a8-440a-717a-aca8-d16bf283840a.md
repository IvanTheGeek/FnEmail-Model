## Where RFC 5321 says so

| Section | Lines | Text |
|:--|:--|:--|
| §4.1.4 | 2490-2494 | *"The NOOP, HELP, EXPN, VRFY, and RSET commands can be used at any time during a session, or without previously initializing a session. SMTP servers SHOULD process these normally (that is, not return a 503 code) even if no EHLO command has yet been received; clients SHOULD open a session with EHLO before sending these commands."* |
| §4.1.4 | 2448-2451 | *"A session that will contain mail transactions MUST first be initialized by the use of the EHLO command. An SMTP server SHOULD accept commands for non-mail transactions (e.g., VRFY or EXPN) without this initialization."* |
| §4.1.1.7 | 2143-2145 | *"This command has no effect on the reverse-path buffer, the forward-path buffer, or the mail data buffer, and it may be issued at any time."* |

## Notes

RECOVERED BY THE RE-SWEEP. §4.1.4 is not among this chapter's listed anchors, but it is where the spec says what the diagnostic commands' relationship to a session actually is, and no inherited candidate carried it. This is the fact that makes Address Diagnostics a chapter rather than a corner of the transaction: VRFY, EXPN, HELP and NOOP are the commands that exist outside the mail transaction entirely, and the RFC groups them explicitly at 2490-2491 with RSET. Strength: SHOULD process normally on the server, SHOULD open with EHLO on the client (2493-2494), and a MUST for initialization only for sessions that will contain mail transactions (2448-2449) — three different obligations in one paragraph, pulling in different directions. Rejected alternative names: NonMailCommandAccepted, UninitializedSessionCommandProcessed, DiagnosticsUsedBeforeGreeting. Opposite: DiagnosticCommandRejectedAsOutOfSequence. Which screen would have killed it: the HELO-only charter (a session with no HELO at all is outside it by construction), the responsibility-boundary cutoff, the twelve-slice model which starts at the greeting, and the consumer test. Worth a hotspot for a later step: if a model's session root only comes into existence at EHLO, these events have no session to belong to, and the stream_root chosen here — Session — presumes a session that begins at connection rather than at greeting. FIELD HYGIENE PASS: struck session_id (f2C8D14), and the strike is unusually pointed on this record: THIS EVENT HAPPENS WHEN NO EHLO HAS BEEN RECEIVED, so there is not even a claimed domain to key on, let alone a session identifier the RFC never defines anywhere (verified by grep — session, transaction and connection identifiers are all absent from rfc5321.txt). What carries identity is the channel itself and the client's IP address, and §4.1.4 lines 2498-2500 names that address as one of the legitimate bases for deciding about exactly these commands — so client_address is not a substitute invented to plug the hole, it is the thing the RFC actually points at. The hotspot the note above raises is sharpened rather than answered: with the fabricated key gone, the question of what a session root even is before EHLO has nothing standing in front of it. command is kept because it genuinely ranges over the five commands the RFC groups at line 2490.
