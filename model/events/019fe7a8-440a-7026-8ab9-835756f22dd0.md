## Notes

RECOVERED BY THE RE-SWEEP — three MUSTs in §5.1 all end 'MUST be reported as an error' and NOT ONE inherited candidate carried the reporting act itself; every one of them carried only the finding that triggers it. Strength: MUST, three times. 🟥, and the largest gap in the chapter: how, to whom, and with what reply code are unspecified everywhere — a 5yz reply to the peer if the session is still open, or a bounce if the message was already accepted, are different events with entirely different visibility to the sender, and the inherited TargetDomainFoundNonExistent notes flagged the same hole without giving it a slot. Deliberately ONE event with a cause field rather than three, because the RFC states one obligation with three triggers; if a later step finds the audience or mechanism differs by cause, it splits — that split is a Step 2 question, not a Step 1 one. Deliberately does NOT cover the fourth failure branch at 3932-3934, which requires a return rather than a report and is MessageReturnedUndeliverableAfterSelfMatch. Rejected alternative names: DeliveryErrorReported, ResolutionFailureReported. Which project screen would have killed it: the one-event-per-command design target. ⚠️ FIELD HYGIENE PASS: struck forward_path — all three MUSTs are stated about the domain lookup, not about any one recipient, so the recipient is a read-model join; the same strike was applied to TargetDomainFoundNonExistent and NoUsableMailExchangerFound. cause survives and is NOT a rendered decision: it names which of the three triggering branches fired, which is the discriminator the inherited merge deliberately chose, and its example is the RFC's own wording at 3845. No reply_code was present and none is added: the RFC licenses no code on any of the three branches, which is the 🟥 recorded above. No fabricated identity key was present.
