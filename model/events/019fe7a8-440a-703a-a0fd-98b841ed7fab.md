## Notes

RECOVERED BY THE RE-SWEEP — named as a sibling in idx 197's notes and never given a row. Worth keeping because the same SHOULD NOT is stated three separate times in one section, once per registry (clauses at 3346-3348, links at 3356-3357, protocols at 3373-3374), and a spec that repeats itself three times is telling you the violation is common. Strength: SHOULD NOT throughout, never MUST NOT, so an unregistered name is discouraged and legal — which is precisely why private WITH values are ubiquitous in real trace lines. Note the interaction with §3.7.2 lines 1586-1588: a receiver MUST NOT reject on trace format, so there is no enforcement path for this SHOULD NOT anywhere in the protocol. That combination — repeated prohibition, no enforcement — is a 🟥. Stream root is Message rather than Extension Registry because the state change is in the stamped message; the registry is unchanged and that is the whole complaint. Siblings: TraceClauseRegistered, ProtocolNameRegistered. FnEmail screens: the consumer test / G1 and the altitude tiers. ⚠️ FIELD HYGIENE PASS: struck the fabricated `message_ref` identity key — RFC 5321 supplies no message identifier, and f2C8D14 is this project's own minted queue id rather than anything in the RFC. Identity is the stamped line: the unregistered name sits in one clause of one hop's Received: field and nowhere else. Sourcing now stated — 'WITH' is the RFC's keyword at 3334 and foo.com is the walk scene's server, while LOCAL is invented, which is unavoidable for the same reason as in ProtocolNameRegistered: an unregistered name is by definition one the RFC does not carry.
