## Notes

Recovered by the re-sweep: the inherited RecipientsGroupedIntoSingleTransaction carried the limit only as a field, so the moment the limit actually bites had no event. MAY strength (3764-3766), and it is the sending client's own self-imposed ceiling — not the receiving server's, which is §4.5.3.1.10 and a different chapter. This is where the outbound batching rule meets the inbound recipient-buffer limit from the other side of the wire; the two must not be merged, since one is a client choosing to split and the other is a server refusing to accept. Dropped as derived: the number of transactions produced. Rejected name: RecipientBatchLimitReached. Screens: inbound-only scope, altitude tiers. ⚠️ FIELD HYGIENE PASS: NOTHING STRUCK, but the example value is now labeled honestly. The RFC gives no number for the client's own ceiling at 3764-3766; the 100 that the sweep reached for belongs to the RECEIVING server at rfc5321.txt:3549, which is precisely the confusion this record's own notes warn against, so the source line records that rather than lending the figure false authority. The earlier decision to drop the transaction count was already correct under the derived-value rule. No transaction identifier appears and none could — RFC 5321 supplies none. queue_entry_id kept on §4.4's ID-clause ground (rfc5321.txt:3336); f2C8D14 is this project's minted value, not the RFC's.
