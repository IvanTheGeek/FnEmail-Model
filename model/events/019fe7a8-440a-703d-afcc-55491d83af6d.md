## Notes

Carried over from idx 93 unchanged in substance; its citations verified. The inherited record notes it is the one event in the §3.6-3.7 span that lands squarely inside this project's inbound-only scope, and that it is a prohibition on a rejection the model might otherwise think it was entitled to make — both worth preserving. Two strengths again: MUST NOT reject on trace format, SHOULD be 'extremely robust', so tolerance is mandatory and grace is merely recommended. The premise at 1581-1582 is itself an unwritten precondition — the message came from a non-SMTP environment, a fact about provenance the receiver usually cannot observe. Whether accepting is an event at all is arguable, since the state change is that the message simply proceeds; the refusal being forbidden is what makes the non-rejection load-bearing, and that tension is recorded rather than resolved. Opposite arm, recovered by the re-sweep: MailRejectedOnTraceHeaderFormat. Related upstream cause: FromClauseOmittedFromTrace, ObsoleteDateFormUsedInTraceLine, UnregisteredTraceNameUsed — all produce the malformed input this event must swallow. FnEmail screens: the consumer test / G1, and the HELO-only charter, since trace headers arrive inside DATA. ⚠️ FIELD HYGIENE PASS: struck the fabricated `message_ref` identity key — RFC 5321 names none, and f2C8D14 is not in the RFC. This is the one event in the chapter where the loss is most visible and most correct: the message being accepted is identified by the live channel, since acceptance happens inside the session and before anything has been queued or stamped by this host. Two differ only in example values (both wrong in different directions) and citation precision; the third additionally strikes a field the other two keep, with an argument that survives inspection.

From the duplicate in 9. Gatewaying: Two strengths in one sentence: MUST NOT reject on trace format, SHOULD be extremely robust. The second is the wider obligation and is folded here rather than given its own card, because tolerance without a rejection is unobservable — but the fold is recorded so a facilitator can split it. This is the ONE event in this chapter whose actor is an ordinary receiving server rather than a gateway, which is why the inbound-only project charter keeps it and deletes almost everything else here; that asymmetry is itself the useful finding, noted in extras.md by the §3.6-3.7 sweep. Opposite event: MailRejectedOnTraceHeaderFormat, split out by the re-sweep. Rejected alternative names: NonconformingTraceHeaderTolerated, ForeignTraceFormatAccepted. Note the stream_root choice: Transaction, not Message — the acceptance is a decision inside one receiving transaction, whereas the malformed line is a property the message carries onward.

FIELD HYGIENE PASS: struck two fields. (1) message_ref (example f2C8D14) — RFC 5321 supplies no message identifier; on a Transaction-rooted event the identity is the transaction itself, which the RFC gives no key for either: while a session lives, the channel is its identity, and this acceptance is located by its position in that session, after DATA. (2) originating_environment (example X.400) — the receiving server cannot know it. That is not a quibble: a malformed trace line arriving from a foreign environment is malformed precisely because the via clause that would have named the environment is missing or unparseable, so this field asks the actor for the fact whose absence defines the event. Unsourceable and unknowable, therefore invented. Also corrected receiving_host, which read bar.com: in the walk scene bar.com is the sending client and foo.com the receiving server.
