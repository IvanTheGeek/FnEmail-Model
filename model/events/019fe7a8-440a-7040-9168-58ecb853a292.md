## Notes

Carried over from idx 201, renamed from ReturnPathRemoved to ReturnPathRemovedInTransit so it cannot be confused with ReturnPathHeaderStrippedBeforeDelivery — different actor, different moment, different downstream evidence. Rejected alternative names: ReturnPathRemoved, ReturnPathStrippedByRelay. MAY, not MUST or SHOULD — permission granted precisely because the final-delivery determination at 3226-3228 is unreliable. THE CONTRADICTION IN THE SPAN, preserved from the inherited record and re-verified: a relay is forbidden to look for the header it is permitted to remove (3234-3237 versus 3229-3231). That is a real contradiction, not a reading error, and it is worth a 🟥 under rule 12; the presumable reconciliation is that a forwarder or gateway is not acting in a pure relay function, but the RFC never says so. The forbidden inspection itself is set aside as a read. Companion event on the envelope side: ReversePathRebuiltForOnwardHop, split out because removing a header and rewriting an envelope act on two different objects. FnEmail screens: the inbound-only scope and the HELO-only charter both exclude relaying outright. ⚠️ FIELD HYGIENE PASS: struck the fabricated `message_ref` identity key — RFC 5321 names no message identifier, and f2C8D14 is not in the RFC. The removed path is the identity, and the loss is instructive here: with no key on the message, nothing downstream can tie this removal to the delivery it was meant to tidy, which is a sharper statement of the same gap the contradiction above describes. Both surviving values come from the walk scene.
