## Notes

Kept as harvested; §4.3.2 line 3119 added by re-sweep, and it independently confirms 503 and 554 as the pre-354 error set for DATA, so the two codes are not an artifact of §3.3's prose. Strength: MAY, and two codes for one condition — 503 and 554 mean different things to a diagnosing operator, so a facilitator may reasonably split this into DataCommandRejectedAsOutOfSequence and DataCommandRejectedForNoValidRecipients. This is the first of the RFC's 'only two points' at which DATA can fail; the second is MessageRejectedForIncompleteTransaction, which is the post-354 twin of the same condition and is carried separately below. Opposite event: MailDataTransferAuthorized. Rejected alternative name: DataCommandRefused. Screens: none kills it outright, but the twelve-slice model has one refusal per transaction and this is a second.

FIELD HYGIENE PASS: struck all three fields. session_id is fabricated — no session identifier exists in RFC 5321; identity is the channel, and the refusal is fixed by its position (the DATA that had no usable envelope). reply_code and reply_text are struck as renderings of the decision: 503 and 554 are what the server writes on the wire, not facts it holds afterward, and the RFC carries neither beyond the exchange. Striking reply_code makes the split flagged above sharper rather than softer — with the code gone, the only way to distinguish "command out of sequence" from "no valid recipients" is to name two events, which is exactly the ruling a later step now has to make on purpose instead of by field value.
