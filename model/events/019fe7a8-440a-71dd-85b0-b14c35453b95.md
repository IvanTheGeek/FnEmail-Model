## Notes

MERGE of the inherited AddressVerificationRefused with the 7.3 half; names rejected: AddressVerificationRefused, VerificationRefused, DisclosureRefusedWith252. NOT merged with two other 252 candidates identical on the wire and not the same state change — AddressVerificationDeclinedAsUnverifiable (3.5.3 lines 1383-1390) and VerificationDeclinedWithDeliveryPromised (4.2.2 lines 2820-2821). Same code, three unrelated causes. Strength: MUST (4244), the strongest 2119 keyword in section 7 apart from 8's trace-field MUST. Doubtfulness inherited and answered: a 252 is not a lookup result, it is a refusal to disclose, and 7.3 spends four sentences ruling out every cheaper answer. The RFC's own scenario contradicts it: D.4 line 5114 answers S: 250 Mark Crispin \<Admin.MRC@foo.com>. Screens that would have killed it: the HELO-only charter, the query filter. FIELD HYGIENE: struck reply_code (252) as the rendering of the decision the event already names — 4243-4245 specifies which code goes on the wire, which makes it wire syntax rather than data held afterwards, and the method's bar on computed and derived values covers it. Struck requesting_client: the requestor is the far end of the channel, the channel is the identity, and 7.3 makes the requestor no part of the refusal. Both survivors come from the RFC's own D.4 line 5113, C: VRFY Crispin — real data rather than a placeholder (rule 8).
