## Notes

RECOVERED BY THE RE-SWEEP — named as an uncarried sibling in the inherited notes. Strength: the MUST at 3874-3876 is on a *capability* ('MUST be able to try'), not on trying, so this event is the terminal state of a loop the RFC never quite mandates. 🟥: §5.1 states no terminal state for the no-success case — the message falls into §4.5.4.1's retry regime rather than into an error here, and nothing in this section says when exhaustion becomes permanent failure. Distinct from AlternateAddressLimitReached (candidates remain there) and from DeliveryAttemptFailedForAddress (one address, not the list). Opposite event: NextHopChannelEstablished, the success that stops the loop. Rejected alternative names: AllDeliveryAddressesFailed, NextHopCandidatesExhausted. Which project screen would have killed it: the inbound-only scope and the responsibility-boundary cutoff. ⚠️ FIELD HYGIENE PASS: struck message_id (example \<f2C8D14@foo.com>). RFC 5321 supplies no message identifier — §4.4's ID clause is optional and belongs to the receiving host's trace field (3329, 3336-3337), §6.4 line 4131 permits adding a message-id 'when none appears' and so proves one need not exist, and f2C8D14 is this project's own minted value, found nowhere in the RFC including Appendix D. No queue_id was substituted: the RFC defines no queue entry, and identity here is the queue entry itself plus the destination it was for. Both surviving fields take walk-scene values.
