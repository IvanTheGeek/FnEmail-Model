## Notes

Inherited from candidate 284; citations re-checked and correct. MAY, and only for an originating server or one used as a submission target — the role is part of the event's identity, not metadata, because the identical edit is forbidden to a relay (see MessageRepairRefusedByRelay). Two preconditions the section states without naming as events, and both are worth someone's attention: the server "can identify or authenticate the client", and "there are prior agreements between them" — the second is an over-time administrative fact between two organizations that never appears on a protocol model and yet governs whether the repair is legitimate at all. Raw candidate 66, SubmissionArrangementEstablished, is the nearest existing event to that agreement and belongs to the submission chapter; cross-referenced rather than duplicated here. client_identity is carried because the whole legitimacy of the repair turns on how much the server knows about the client (4137-4139). Screens: the inbound-only scope, and mutating a message in flight has no slot in the capture/decision two-kinds lens.

FIELD HYGIENE PASS (chapter 14): client_identity struck — it is the session's EHLO or HELO claim copied forward and is recoverable from the greeting, which is the same call an earlier pass made when it dropped previous_text from ReplyTextCustomized; lines 4123-4125 make the server's knowledge of the client a PRECONDITION for the repair being appropriate, and a precondition is not payload, so the inherited note's justification for the field does not survive. message_id KEPT, because here it is the added VALUE and not a key: line 4131 is "Addition of a message-id field when none appears". Its example is corrected — the old \<f2C8D14@foo.com> used this project's own minted queue id, which appears nowhere in RFC 5321 and is the wrong kind of thing for an RFC 5322 msg-id in any case. Section 4.4 line 3336 does license a msg-id, in the optional ID clause of a trace header, but the RFC gives no example of one, so the replacement is built from sourced parts and labeled illustrative. added_by KEPT and sourced to section 4.4's By-domain clause at line 3319, where the RFC records the acting host per hop; its value is corrected from mail.foo.com, absent from RFC 5321, to foo.com, which Appendix D names as a host at 4882 and its own trace line uses at 5064.
