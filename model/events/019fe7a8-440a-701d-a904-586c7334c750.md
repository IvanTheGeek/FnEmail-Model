## Where RFC 5321 says so

| Section | Lines | Text |
|:--|:--|:--|
| §5.1 | 3909-3912 | *"If an SMTP server receives a message with a destination for which it is a designated Mail eXchanger, it MAY relay the message (potentially after having rewritten the MAIL FROM and/or RCPT TO addresses), make final delivery of the message, or hand it off using some mechanism outside the SMTP-provided transport environment."* |
| §5.1 | 3917-3918,3927 | *"If it determines that it should relay the message without rewriting the address, it MUST sort the MX records to determine candidates for delivery."* |

## Notes

MERGED from the inherited MessageRelayedToNextHop (§5.1 variant) and RENAMED. Explicitly NOT merged with the identically named §4.1.1.3 candidate, which is a relay forwarding a SOURCE-ROUTED message and belongs to the Relaying chapter — under the merge rule, a relay's send under source routing is not this disposition, and fusing them would lose the fact that this arm is chosen from a three-way MAY. Strength: MAY for the disposition, MUST for the sort that follows it. This is the only one of the three arms that requires the MX list to be examined at all (3913-3915), which is what makes the disposition a routing event rather than a delivery one. Siblings, both now carried: MessageDeliveredFinallyByDesignatedExchanger and MessageHandedOffOutsideSmtpEnvironment. The determination that precedes it is a decision-read and is set aside. Which project screen would have killed it: the responsibility-boundary cutoff and the inbound-only scope. ⚠️ FIELD HYGIENE PASS: struck message_id (example \<f2C8D14@foo.com>). RFC 5321 supplies no message identifier — §4.4's ID clause is optional (Opt-info = [Via] [With] [ID] [For], 3329) and is written by the receiving host into its trace field (ID = CFWS "ID" FWS ( Atom / msg-id ), 3336-3337), §6.4 line 4131 permits an originating server to add a message-id 'when none appears' and so proves one need not exist, and D.3's relay writes a Received line at 5064 with no ID clause and no Message-ID header anywhere. f2C8D14 appears nowhere in the RFC. On a Message-rooted event what carries identity is the envelope — the forward-path being relayed — together with the hop it moved between; all three surviving values come from D.3.
