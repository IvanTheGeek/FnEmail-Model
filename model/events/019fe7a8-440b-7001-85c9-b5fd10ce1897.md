## Notes

RECOVERED BY THE RE-SWEEP. The 7.x set-aside pile filed 'HELP command output and reading server type or version from the greeting' as a display and kept only the operator's configuration choice. Doubtful and kept anyway, for the reason MailboxExistenceDisclosedViaVrfy was kept elsewhere: the state change is not in the server, it is in the world — information that might be useful in a hostile attack (4297-4298) is now over there and cannot be recalled. If disclosure via VRFY is an event, disclosure via banner is one too, and the two must be ruled on together. Strength: none for the act; 7.5's only 2119 keyword is the SHOULD at 4304 arguing FOR disclosure. Two carriers named at 4296-4297, greeting and HELP — one event with a carrier field, splittable. Rejected names: BannerDisclosedServerVersion, ServerFingerprintExposed, HelpResponseDisclosedIdentity. Screens that would have killed it: the consumer test, the query filter, the HELO-only charter. FIELD HYGIENE: struck server_host as an actor restatement. What remains exposes a real gap instead of hiding it: THERE IS NO FIELD FOR THE SOFTWARE AND VERSION THEMSELVES, because RFC 5321 never instantiates one — 3.1 lines 964-966 permit the announcement, 7.5 debates it, and every Appendix D scenario shows a greeting with no version in it (D.1 line 4886, D.3 line 5057). A payload field here would have to be invented outright, so none is added and the absence is the finding. disclosed_in is near-quoted from 965-966 and carries the two-carrier distinction. receiving_client is the peer address derived from the TCP connection (4.4 lines 3325-3327) and is the point of the event. Confidence unchanged.
