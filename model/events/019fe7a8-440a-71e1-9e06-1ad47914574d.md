## Notes

MERGE of the inherited MailingListAccessRestricted (3.5.1, inferred from the RFC's example) with 7.3's explicit statement that administrators have installed such protections. Names rejected: MailingListAccessRestricted, ListAccessControlApplied, ListHarvestingProtectionEnabled. 4263-4265 supplies what 3.5.1 only implied — the RFC shows the refusal (S: 550 Access Denied to You.) and never the configuration producing it. Reply text quoted with the RFC's own capitalization and period per rule 2. Real contrast inside the RFC: Executive-Washroom-List (1322) is protected where Example-People (1315) is not, evidence that protection is per-list, not per-command. Strength: none; 4263-4265 describes what administrators did. Runtime arm in another chapter: ExpnAccessDenied. Direction of causation worth keeping: protections on lists came FIRST and pushed harvesters toward EXPN. Screens that would have killed it: altitude tiers, inbound-only scope, twelve-slice model. FIELD HYGIENE: struck installed_by (\<Jones@foo.com>) — RFC 5321 names no list administrator and gives none any identity; 4263-4265 says only that administrators have installed protections, and putting a mailbox on that is invention. protection has no RFC source and says so plainly: the spec shows the 550 at line 1323 and never the configuration behind it, which is the whole reason this event exists.
