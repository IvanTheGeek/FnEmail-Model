## Notes

MERGED from candidates 9 (VrfySupportDisabled) and 293 (AddressVerificationDisabled, which covered both commands with a command field). The merged form was rejected and the per-command split kept, because §3.5.2 line 1360-1361 says 'either or both' — they are independently switchable — and the consequences differ: disabling EXPN removes an EHLO extension line (MUST, 1365-1366) while disabling VRFY does not. AddressVerificationDisabled is carried here as the rejected alternative name, along with VerificationCommandTurnedOff and VrfyDisabledForSecurity. The re-sweep added §4.5.1 lines 3380-3392, which no inherited candidate cited in this connection and which sharpens the contradiction into a four-way one: SHOULD support (1219, 1359), MAY provide a way to disable (1360), MUST support to conform (3381-3382, with VRFY listed at 3392), and disabling produces the 500/502 replies that 1380-1381 calls not in full compliance. The spec sanctions a configuration it elsewhere forbids. That is a genuine hotspot and rule 12 says it gets a marker where it bites. §4.5.1's MUST-list also contains both EHLO and HELO, so a HELO-only charter is a scope decision against an explicit MUST, not a reading of one. Which screen would have killed it: the condemned status/phase register (capability state read as status), the four altitude tiers (Infrastructure, not Protocol), the HELO-only charter, the twelve-slice model which has no configuration slice. Sibling: ExpnSupportDisabled. Runtime consequence: VerificationDeclinedAsDisabled. FIELD HYGIENE PASS: struck disabled_by (\<postmaster@foo.com>). RFC 5321 nowhere records who changed a server's configuration — it has no administrator identity, no change record and no audit concept — and the actor field already says Site administrator, so the field was a payload invented to give a configuration event something to carry. The value is what made it easy to miss, and the near-miss is worth recording: 'postmaster' is a reserved mailbox the RFC genuinely does require at lines 3394-3396, so \<postmaster@foo.com> looked sourceable, but requiring a mailbox is not recording who operated a switch. Sourcing a value does not save a field. reason is kept because the RFC attaches a motive to the permission itself at 1359-1360 ('For security reasons') and names the harvesting trend at 4253-4254, so the field has a source even though the phrasing is ours. server_host is the stream's own identity here, this event's root being Server Configuration, so it is not padding on this record as it is on the runtime ones. No reply code and no invented identity key were present.
