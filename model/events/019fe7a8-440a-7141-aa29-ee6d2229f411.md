# `BlindCopyRecipientAddressedInEnvelopeOnly`

A recipient was named in a RCPT command while appearing nowhere in the message header section, so the delivered message carries no trace of that recipient.

## Where RFC 5321 says so

| Section | Lines | Text |
|:--|:--|:--|
| §7.2 | 4214-4218 | *"Addresses that do not appear in the message header section may appear in the RCPT commands to an SMTP server for a number of reasons. The two most common involve the use of a mailing address as a "list exploder" (a single address that resolves into multiple addresses) and the appearance of "blind copies"."* |
| §7.2 | 4228-4230 | *"There is no inherent relationship between either "reverse" (from MAIL, SAML, etc., commands) or "forward" (RCPT) addresses in the SMTP transaction ("envelope") and the addresses in the header section."* |

## Notes

RECOVERED BY THE RE-SWEEP. §7.2 opens by naming two reasons an envelope recipient appears in no header field; the inherited set carried an event for the first (the list exploder, merged into PseudoMailboxExpanded) and nothing at all for the second, which is the one the section is titled after. This is the fact every other blind-copy event in the chapter protects or leaks. It is also the cleanest statement in RFC 5321 of the envelope/header separation that docs/smtp-path-vs-mailbox.md is about — line 4228's "There is no inherent relationship" is stronger than anything in §3.3. Rejected alternative names: BlindCopyRecipientAdded, EnvelopeRecipientAbsentFromHeaderSection, RecipientHiddenFromHeaderSection. No RFC 2119 keyword: it is a statement of fact about what happens, and the keywords in the section all attach to what must not be done about it. A parent framing — EnvelopeRecipientSetDivergedFromHeaderSection, covering both reasons at once — was considered and rejected as an observation over the two concrete events rather than an event. Screens: inbound-only scope (this fires at the client), and the one-event-per-command target would fold it into RCPT. FIELD HYGIENE PASS: transaction_id struck — 1 field, and it was the chapter's only invented identity key. RFC 5321 supplies no transaction identifier: grep -niE "session (id\|identifier)\|transaction (id\|identifier)\|connection (id\|identifier)" over docs/rfc/rfc5321.txt returns nothing, and its value, f2C8D14, appears nowhere in the RFC either — it is this project's minted queue id, which does not even name a transaction, and it could not apply here in any case since this event fires at the client before anything has been accepted. What identifies the transaction is its position in the session: opened by MAIL, recipients accumulated under RCPT, ended at DATA or RSET, and while the session lives the channel is its identity. The reverse_path kept here is the nearest handle the wire actually carries — the MAIL FROM argument that opened this transaction — and that absence is a genuine finding about the spec, exactly what Step 1's stream-root sub-step exists to surface, so it is left standing rather than papered over.
