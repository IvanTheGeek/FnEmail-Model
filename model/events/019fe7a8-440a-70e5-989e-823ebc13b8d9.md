## Notes

Merged from MessageRequeued, MessageRequeuedByClient and MessageRequeuedForRetry — rejected names all recorded. Strength: the requeue is a MAY with two named arms (2962-2963), so this and QueuedMessageReturnedToUser are alternatives at one decision point, not a sequence. CITATION CORRECTION, rule 3: the inherited MessageRequeuedForRetry cited §4.1.1.10 2215-2219 for a client requeue after a premature close, but the text there says "the server MUST cancel any pending transaction ... and generally MUST act as if the command or transaction in progress had received a temporary error" — the obligation named is the SERVER's, and the client's requeue follows from §4.2.5's retained-responsibility sentence instead. The §4.1.1.10 reference is dropped rather than carried forward. Also note the RFC hedges its own MUST with "generally" at 2218, which is unusual. Deliberately NOT merged with MessageQueuedForDelivery: first entry into the queue and return to it after a failed attempt are different state changes on the same entry. Dropped as derived: attempt_number. Screens: inbound-only scope, responsibility-boundary cutoff. ⚠️ FIELD HYGIENE PASS: STRUCK declining_reply_code — a reply code is the rendering of a decision, and here it is the trigger rather than payload: §4.2.5 2959-2960 keys on the 4yz class, and nothing in RFC 5321 requires the code to be retained past the reply that carried it. The two events in this chapter that keep a reply code, NegativeResponseCached and MailCommandRejectionCached, keep it because the RFC makes the stored response itself the subject of a rule at 3746-3750; this event has no such ground. STRUCK requeued_at as a bare occurrence stamp. queue_entry_id kept on §4.4's ID-clause ground (rfc5321.txt:3336); f2C8D14 is this project's minted value, not the RFC's.
