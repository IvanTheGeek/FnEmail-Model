## Notes

RECOVERED BY THE RE-SWEEP. The merged list carried the in-session replies (250 and 251) but nothing for the forwarding itself. Both arms of lines 1191-1194 are about forwarding messages, and 251's own text is a promise in the future tense — "will forward to" — so the keeping of that promise is a separate fact at a separate time, by a server that is now acting as a client toward xyz.com. Strength: MAY. Marked likely rather than certain because the RFC states the permission and the promise but never names the completed act. The unnamed violated arm — the server replied 251 or 250 and never forwarded — is real and is the reason to keep this event visible; it is not proposed as its own event because §3.4 does not state it, and the obligation that would ground it (§2.1's requirement that a server accept responsibility for either delivering the message or properly reporting the failure) sits outside this chapter's anchors and was not opened, so nothing is claimed about its wording. Screens: the responsibility-boundary cutoff kills it outright — this is precisely the work that begins where the FnEmail model ends; the twelve-slice model has no relay slice.

⚠️ FIELD HYGIENE PASS (fields and notes only): one field struck, one converted. message (MessageId, f2C8D14) became queue_id (QueueId) rather than being struck outright, and the test was run before the field was kept. RFC 5321 supplies no message identifier: the only "message-id" in the whole text is at rfc5321.txt:4131, a gateway adding an RFC 5322 header field where none appears, which is not an SMTP-level key. But §4.4 Trace Information (heading at rfc5321.txt:3156) does make room for one — Opt-info = [Via] [With] [ID] [For] at rfc5321.txt:3329, and ID = CFWS "ID" FWS ( Atom / msg-id ) at rfc5321.txt:3336 — and this server has already accepted the message and written its Received line, so a queue id is the field the RFC's own syntax provides for. Two limits recorded rather than glossed: the ID clause is OPTIONAL, so a server that omits it holds no message identifier the spec knows about at all; and f2C8D14 is not in the RFC, it is this project's own minted value from the walk, so the example is labeled as such. relayed_at struck — it duplicates the event's own occurrence time, which is not payload; §4.4's Stamp does carry a date-time (rfc5321.txt:3312) but that is the receiving server's, written at accept time, not this server's relay time.
