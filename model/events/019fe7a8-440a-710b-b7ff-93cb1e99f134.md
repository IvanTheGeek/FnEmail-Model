## Notes

Strength: SHOULD on providing the mechanism (1208-1211) — note the SHOULD binds the IMPLEMENTATION, while the event recorded here is the OPERATOR pulling the lever, which carries no keyword at all. The RFC never says what the default must be, a genuine ambiguity a later step will have to settle. The verb is two-valued — disable OR restrict — and restriction is per-site policy, which is why the restriction field is free text rather than a flag; that is a known weakness, not a considered design. Honored arm of the SHOULD, considered and NOT promoted to its own event: DisclosureConfigurationMechanismProvided, the implementation shipping the lever — a design-time change by the Implementer role, which the §7 sweep already flagged as doubtful because it initiates no state change in a running system. Violated arm of the SHOULD: a server supports 251/551 with no way to switch them off, and a concerned site cannot comply — its consequence is kept as SensitiveAddressInadvertentlyDisclosed. Opposite arm of the operator act: re-enabling or widening disclosure, noted as the sibling AddressUpdateDisclosurePermitted and not proposed separately because the RFC names only the disabling direction. Same shape elsewhere in the RFC: VrfySupportDisabled, ExpnSupportDisabled (§3.5.2), GreetingDisclosureConfigured (§7.5). Screens: the four altitude tiers put configuration below the Protocol tier; the condemned status register would read the resulting capability as a status field; the twelve-slice model has no configuration slice. Citation note: the inherited candidate quoted from line 1209 under the label 1208-1211; extended here to the full sentence, which does begin at 1208.
