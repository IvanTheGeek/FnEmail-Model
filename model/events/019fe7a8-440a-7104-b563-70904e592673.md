## Notes

MERGED: absorbs the 251 half of the inherited ForwardPathAdvertised (§4.2-4.3 sweep), which had folded 251 and 551 into one event "to fit the count" and flagged the split as needed because the two differ in custody — 251 accepts the message and undertakes to forward it, 551 refuses and merely redirects. The split is made here. ForwardPathAdvertised's session_id was dropped in favor of transaction (the state change belongs to a RCPT inside a transaction), and its queried_address/forward_path names are recorded as rejected alternatives along with AddressCorrectionAnnounced and ForwardPathReturned. Strength: MAY for using 251; MUST NOT for the assumption that follows (1194-1196). This is one of only two replies whose TEXT a client may act on (§4.2 2563-2565, and 2610-2612 names them "change of address"), and the RFC immediately forbids relying on the client having acted — an "emitted, consumption not guaranteed" shape that Step 1 must keep visible. Screens: the consumer test (G1) would kill it, because nothing drawn consumes a corrected address — and note the spec and that screen disagree in writing here, since the RFC forbids the emitter from assuming a consumer exists; "one event per command" would fold it into the RCPT event; inbound-only leaves the client-side half unmodeled. Downstream siblings: AddressBookEntryUpdated, MessageRelayedToCorrectedAddress. Citation fixed: inherited candidate cited 1184-1187 for "must be evaluated carefully by implementers" — that sentence begins at 1185; line 1184 is the RFC 821 pointer.

⚠️ FIELD HYGIENE PASS (fields and notes only): struck two fields, and the merge note above now reads as a record of the defect travelling rather than being fixed — ForwardPathAdvertised's session_id was replaced by transaction, one invented key swapped for another. transaction (f2C8D14) struck: RFC 5321 supplies no transaction identifier, and f2C8D14 is this project's own minted queue id, absent from the RFC. Identity here is position in the session — the RCPT under the open MAIL FROM. reply_code (251) struck, and this event had the chapter's strongest case for keeping one, so the case was tested rather than assumed: §4.2 lines 2563-2565 do make 251 one of five codes whose message text "must be parsed and interpreted by machines", which is the RFC treating a reply as data. But what is parsed is the forward-path, and this event already carries it as corrected_mailbox. The code selects which of §3.4's four arms this is; it is not payload on it. Sourced: addressed_mailbox at rfc5321.txt:4897; corrected_mailbox composed from the RFC's Green (4884) and xyz.com (1940), the address itself absent from RFC 5321.

COLLISION RESOLVED — merged from 2 independently brainstormed records. Same section, same actor, same reply; the two copies are the same event found from 3.4 and from 7.7. The example pair had to be chosen and the RFC decided it: there is no worked 251 exchange anywhere in RFC 5321 — 251 occurs only in prose and reply-code lists (1185, 1193-1194, 1208, 1392, 2563, 2611, 2818, 2877, 3108, 3127, 4286, 4334) — so both candidate pairs are compositions. Green@foo.com wins because it is the RFC's own instance of a recipient with no mailbox at the addressed host, which Appendix D.1 answers with 550 No such user here at 4897-4898 and which is exactly the condition 251 is the alternative disposition for; the walk-scene pair \<Smith@bar.com> to \<Smith@foo.com> additionally reads oddly, since Smith@bar.com in a RCPT at foo.com is the relay request of RelayingDeclined. The walk-scene pair and both caveats — that the RFC shows 550 for Green, and that xyz.com is introduced at 1940 as a relay host — go into the survivor's notes.
