## Notes

MERGE of two inherited candidates naming one state change: ReplacementAddressAssociatedWithMailbox (7.7) and MailboxRelocationRecorded (3.4, which additionally carried an effective_from field). Names rejected: MailboxRelocationRecorded, ForwardingAliasProvisioned, PriorAddressLinkedToCurrent. The effective_from field was dropped in the merge because 7.7 does not have it and 3.4 does not require it; the argument for restoring it is that a relocation has a date and a consolidation does not. Section 7.7 worries only about DISCLOSING the association, which presupposes an event that created it; the spec never specifies that event, which is why this is likely rather than certain. Strength: no 2119 keyword anywhere in 7.7 — 'should ensure that they select and configure servers appropriately' (4336-4338) is lowercase. Real contrast inside the RFC: D.1 line 4898 answers S: 550 No such user here for a nonexistent user, where a site holding a replacement record would have answered 551 and named it — exactly the disclosure 7.7 flags. Screens that would have killed it: inbound-only scope, twelve-slice model, altitude tiers. FIELD HYGIENE: struck server_host (bar.com) — the mailbox carries its own domain, so the field restated half of another field and the actor besides. The dropped effective_from stays dropped and now has a stated reason rather than an inherited one: RFC 5321 dates no such record anywhere, and the only 1998 timestamp available is the walk scene's message-receipt time, which is a different fact. Identity: the mailbox, which is the stream root and the first field.
