## Notes

RECOVERED BY THE RE-SWEEP, and the clearest thing the cap cut. Eleven sweeps produced RecipientBuffered for the forward-path side and NOTHING for the reverse-path side, although §4.1.1.2 states the insertion in the very same sentence as the clearing — the clearing half was harvested (TransactionBuffersCleared) and the inserting half was dropped. The mirror pairing with RecipientBuffered is what makes the §4.1.1.3 sentence at 1936-1938 meaningful: RCPT appends to one buffer and is required NOT to touch this one, which is a fact about persistence that only exists if this event exists. Rejected alternative names: ReversePathStored, SenderBuffered, ReversePathInserted. Killed by: the 'one event per command' target (a second event on the same MAIL), the consumer test G1, and the capture/decision lens — all named, none applied. Distinguish from ReversePathAccepted: the storing is what the server does, the 250 is what the client sees, and they are separable the way §3.3's RCPT sentence separates them at 1061-1062.

FIELD HYGIENE PASS: struck two fields, session_id and transaction_id, both fabricated in key and in value — RFC 5321 names no such identifier and f2C8D14 appears nowhere in the document (it is this project's own minted queue-id example from commit 6acfc68). Identity here is the buffer's own content: this event says which reverse-path is now in the reverse-path buffer, and the buffer belongs to the open transaction on the channel, which is what distinguishes it while the session lives. This is one of the two events whose survival lets the discarded-value fields on TransactionBuffersCleared and the envelope fields on MailTransactionConfirmed be struck as derived — the buffer is in the stream, so it never needs copying onto later events.
