## Notes

Inherited from raw candidate NullReversePathReplacedOnForward, kept intact; its §3.6.1 cross-reference is corrected to §3.6.3 (heading verified at line 1475). The violated arm of a SHOULD NOT, recorded on the brief's two-arms instruction. It earns its own event rather than a flag because it names actors the rest of the chapter leaves implicit — alias resolvers and mailing list expanders are exactly the systems that rewrite envelope senders. Consequence if it happens: the loop prevention established by NullReversePathSet is defeated and bounces can circulate; a bounce that acquires a real return address can bounce again. The conforming arm is the same event with substituted_reverse_path absent, i.e. NullReversePathPreservedOnForward, and whether those are one event with an optional field or two events is a real modeling question a facilitator should be asked — recorded, not resolved. Note the sentence carries two SHOULD NOTs of different shape: adding a non-null reverse-path where there was none, and changing a null one to a non-null one; they are folded here because for a null-reverse-path message they are the same act. Rejected alternative names: ReversePathAddedToNotification, LoopProtectionRemovedOnForward, NullSenderRewritten. Which screens would have killed it: the inbound-only scope and the responsibility-boundary cutoff — forwarding is past the model's edge in both directions.

WHAT CARRIES IDENTITY HERE INSTEAD: the substituted reverse-path and the forward-path the message went on to, since the message's ORIGINAL handle — its reverse-path — was null and is exactly what the forwarding system destroyed. (2) original_reverse_path — struck: it held the constant \<>, which the event's own name states, and the record's own note above explains why the value can only ever be that one (for a null-reverse-path message the two SHOULD NOTs at rfc5321.txt:3818-3820 collapse into a single act). A field with one possible value carries no information. substituted_reverse_path survives as the fact that makes the event meaningful, with its example now anchored to the mechanism §3.9.2 actually describes at rfc5321.txt:1723-1726, where a list changes the backward-pointing address so errors reach a list administrator — the RFC does not print an address, so the value stays illustrative and is labeled so.
