## Notes

RECOVERED BY THE RE-SWEEP. The §4.1 sweep's MailTransactionStarted notes say outright that a candidate NullReversePathAccepted 'was folded in here for the field cap and should be recovered by a later step' — this is that recovery, taken from the declaring side. Cross-reference, DO NOT MERGE: NullReversePathSet (raw set, §3.6.3) is the notifying server composing its own message; this is the wire declaration inside a transaction, and a receiving server sees only this one. Strength is easy to misread and was checked twice: 1506 offers the technique permissively ('One way to prevent loops'), then 1508-1509 makes it a flat MUST once such a message is being transmitted. Syntax point that only real data shows: `MAIL FROM:` is not `MAIL FROM:\<>`, and §4.1.1.2's grammar at line 1913 has no space after the colon. Which screen would have killed it: the inbound-only scope, and the twelve-slice model has no notification slice.

FIELD HYGIENE PASS: struck one field, declaring_host (bar.com). The MAIL command carries no host: the client's identity on the wire comes from the connection and from whatever it claimed in EHLO, so on this event the channel carries it. Nothing in RFC 5321 attaches a declaring host to MAIL FROM. reverse_path is KEPT rather than struck as a constant restating the event's name, because \<> is literally the RFC's own text at 1522 and it is the one place in this chapter where the value and the syntax point are the same thing — 'MAIL FROM:' is not 'MAIL FROM:\<>'. A later step may reasonably drop it and leave the event fieldless; that would be a judgment about restatement, not about fabrication, and it is flagged here rather than taken.
