## Notes

MERGE of idx 283 (MailLoopDetected, the threshold crossing) and idx 80 (MessageLoopDetected, the verdict from trace information) — the same state change reached by the same evidence; rejected alternative names: MessageLoopDetected, LoopThresholdCrossed, ReceivedLineCountExceeded. The chapter roster's phrase is 'loop threshold crossed', but the merged name avoids binding the event to the counting technique, which §6.3 explicitly calls one method among others ('Whatever mechanisms are used'). Two strengths, unflattened: counting is a SHOULD-with-a-number and only for servers that choose that technique, while detecting *trivial* loops is an unconditional MUST with no mechanism specified — carried separately as TrivialLoopStopped. Optionality is stated a third time at §3.6.3 1527 ('optionally'), so a relay that never detects loops is conformant there and non-conformant under 4071-4072 depending on which loops it misses: 🟥. received_count is a count of real headers present in the message, not a derived score, but it is re-derivable and the tension is recorded rather than resolved. THE PRECONDITION NOBODY WROTE DOWN: every hop having prepended a Received: line (§4.4 3159-3160) is the only reason counting works at all, and §6.3 never says so — §5.1's incomplete server-identity list is what generates the loops in the first place. FnEmail screens: the consumer test / G1, and the twelve-slice model has no loop control. ⚠️ FIELD HYGIENE PASS, three strikes on this event. (1) `message_ref` struck: RFC 5321 supplies no message identifier and f2C8D14 is this project's minted queue id; what carries identity is the accumulated Received: chain the message brings with it, which is also the evidence for the detection. (2) `received_count` struck under the no-derived-values rule — THE TENSION THE INHERITED NOTE RECORDED IS NOW RESOLVED AGAINST THE FIELD. §6.3 4067-4069 describes 'Simple counting of the number of Received: header fields', which is a fold over data the message already carries; the count exists only once someone counts, which is the definition of a read-model value. The lines themselves stay in the message and anyone may recount. (3) `rejection_threshold` struck: it is not a fact of this occurrence at all but a copy of configuration state, and it has a proper home in LoopRejectionThresholdConfigured, whose whole reason for existing was to give that number an origin. Both surviving values are invented host names, which is worth noticing — after the strikes this event is thin, and the honest reading is that most of what it appeared to know was the counting, not the loop.
