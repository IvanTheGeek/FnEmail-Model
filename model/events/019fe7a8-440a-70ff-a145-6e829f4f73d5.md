## Notes

Harvested into this chapter because the chapter owns retry, but its span is §4.2.1 and the reply-code chapter has a competing claim; cross-referenced rather than exclusively claimed, and a facilitator should assign it once rather than twice. SHOULD strength (2674-2675). Deliberately NOT merged with MessageRequeued or RetryScheduled: this is a command-level repeat inside a live dialogue, possibly seconds later, where those are queue-level attempts days apart — and the RFC's own definition of 4yz depends on the command being "repeated identically" (2679), which has no analogue at queue level. Dropped as derived: attempt_number. Screens: inbound-only scope, responsibility-boundary cutoff. ⚠️ FIELD HYGIENE PASS: three fields struck, the most in the chapter. STRUCK queue_entry_id — this event's stream root is Session and its own notes insist the fact is command-level and not queue-level, so importing the queue entry's identity contradicted the event's own reading; §4.2.1 2673-2680 mentions no queue. RFC 5321 supplies no session, transaction or connection identifier either, so nothing replaces it: while the session lives, the channel is its identity and the command's position in the dialogue is the event's. STRUCK previous_reply_code — the rendering of the server's decision, and here purely a trigger: §4.2.1 keys on the 4yz CLASS, not on a particular code, and nothing requires the code to be retained past the reply, which is the test that let the code stay on NegativeResponseCached and MailCommandRejectionCached and fails here. STRUCK attempted_at as a bare occurrence stamp. What survives is the command verb, which is the one fact §4.2.1 2677-2680 makes essential, since the whole 4yz definition rests on the command being repeated identically; RCPT is the RFC's own token from the minimum-implementation list at rfc5321.txt:3387.
