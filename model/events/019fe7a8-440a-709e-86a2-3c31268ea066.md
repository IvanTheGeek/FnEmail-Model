## Where RFC 5321 says so

| Section | Lines | Text |
|:--|:--|:--|
| §4.5.3.1.6 | 3512-3514 | *"The maximum total length of a text line including the \<CRLF> is 1000 octets (not counting the leading dot duplicated for transparency). This number may be increased by the use of SMTP Service Extensions."* |
| §4.5.3.1.9 | 3554-3557 | *"Errors due to exceeding these limits may be reported by using the reply codes. Some examples of reply codes are: 500 Line too long."* |

## Notes

RECOVERED BY THE RE-SWEEP. The sweeps folded the 1000-octet text-line limit into OversizedMessageDataRejected's notes and flagged that it "deserves its own event"; it is separated here because the object, the limit and the reply code all differ from the message-content limit. Two payload subtleties that are easy to lose: the 1000 octets INCLUDE the \<CRLF>, and they explicitly do NOT count the leading dot added for transparency (3513) — so the limit is measured against the line as composed, not as sent, which puts this event on the far side of DotStuffingApplied. Strength: the limit is stated as fact; §4.5.3.1.9 offers the codes as examples only ("Some examples of reply codes are:", 3554-3555), so 500 is illustrative and the reply text is operator-configurable — copy the RFC's own sample punctuation exactly, "500 Line too long." with the period, where its 501 sample has none. Extensions may raise the limit (3514), so limit_octets is a per-server, per-session fact and not a constant. Siblings: OversizedMessageDataRejected (whole content), OversizedCommandLineRejected (§4.5.3.1.4, the command channel — belongs to Protocol Fault Handling, cross-referenced not claimed). Screens: the altitude tiers.

FIELD HYGIENE PASS: struck four of five. session_id is fabricated — no session key exists in RFC 5321; identity is the channel. line_octets is a computed measurement of the line the event is already about, which the method assigns to a read model. reply_code and reply_text are struck as renderings, and the note above had already established the ground: §4.5.3.1.9 offers 500 as an example only, so the RFC never carries it as data. limit_octets survives and is the one field that is neither derived nor invented — it is the server's own ceiling, sourced at rfc5321.txt:3512, and line 3514 makes it variable per server, so it is a genuine fact about the instance rather than a constant.
