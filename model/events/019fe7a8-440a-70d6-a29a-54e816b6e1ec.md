## Notes

RECOVERED BY THE RE-SWEEP; named inside RecipientBufferLimitReached's notes as a sibling 'folded into this note' and never given an event of its own. SHOULD, stated twice. This is the rare event whose content is a DISAGREEMENT between what the wire said and what the receiver of that reply decided it meant — treated_as_reply_code is a code that was never transmitted by anyone, the client's own reclassification, and the whole retry behavior of a 100-recipient message forks on it. It is the same shape as the raw set's TransactionTreatedAsTemporaryFailure (§3.8, a synthesized 451 for a reply that never came) and the two together are worth carrying as a probe of whether reply codes belong to the wire or to the model — they argue that a code can be a domain fact with no wire event behind it. stream_root is Queue Entry, not Transaction: the transaction is over, and what survives is a queue decision about addresses. Screens: inbound-only scope (client actor), and the protocol altitude tier would call a reply code an artifact of wire encoding, which this event inverts.

FIELD HYGIENE PASS: struck one field, treated_as_reply_code (452), and KEPT one reply code — the only one to survive the chapter. received_reply_code stays because RFC 5321 carries the code itself as data beyond the wire here and says so: 'Clients SHOULD treat a 552 code in this case as a temporary, rather than permanent, failure so the logic below works' (rfc5321.txt:3577-3578), and 3600-3601 repeats it. The code has crossed out of the reply and into the client's queue logic, where it is the thing being reasoned over; that is the exception the method's no-computed-values rule leaves open, and the line that makes it data is 3577. treated_as_reply_code goes because the value is fabricated in a subtler way than f2C8D14: the RFC says clients treat the reply as TEMPORARY, a classification, and never says they relabel it 452 — 452 is the SERVER's correct code at 3574, borrowed here for a client act the spec does not describe. A later step wanting to keep the reclassification should carry the classification the RFC actually states, temporary versus permanent, not a code no one transmitted. remote_host and affected_forward_paths survive: the peer that replied and the addresses that stay queued are both real facts of a queue entry, which §4.5.4.1 3692-3693 confirms 'will include not only the message itself but also the envelope information'.

COLLISION RESOLVED — merged from 2 independently brainstormed records. Same subsection, same actor, same SHOULD, both recovered from the same fold — a textbook duplicate discovery. Two things had to be chosen. Cardinality: List wins, because 3581 puts at least 100 successful RCPT commands in the server's recipients buffer and 3591-3594 has the client retransmitting 'those addresses that received 452 responses', so the affected set is plural by construction. Root: Queue Entry wins over Recipient, because 3591 names 'the SMTP client's queue' explicitly as the thing the convergence argument is about; Recipient is recorded as the alternative, since the reclassification is per-address in its effect.

From the duplicate in 14. Protocol Fault Handling: RECOVERED BY THE RE-SWEEP. Candidate 326's notes named it as a folded sibling and it never got a row. It is one of the few places in the RFC where a client is instructed to DISBELIEVE a reply code — to read a 5yz as a 4yz because the spec knows the servers that send it are following the obsolete RFC 821 — so the client's severity classification stops being a function of the code and becomes a function of the code plus the context. That is a real fact worth its own event and it is invisible in any model where severity is derived from the first digit. Strength: SHOULD, with the reason stated plainly, "so the logic below works" — the reclassification exists to keep the 100-recipient convergence argument valid. It applies only in this case, not to 552 generally; §4.2.2 line 2839 gives 552 a different meaning entirely (exceeded storage allocation), so a client that generalizes the reclassification breaks something else. Merged sibling, named rather than given a row: RecipientListSplitIntoChunks (see RecipientRejectedBelowMandatoryMinimum). Screens: the inbound-only scope.

FIELD HYGIENE PASS (chapter 14): session_id struck — RFC 5321 names no session, transaction or connection identifier, and f2C8D14 is nowhere in the RFC; identity here is the recipient in the client's queue, which is already the stream root. treated_as_code struck as derived: lines 3575-3576 fix the target at 452 for this condition, so given the received code the treatment follows from the rule, and the event's name states it anyway. received_reply_code KEPT, and line 3576-3578 is what makes it data — "Clients SHOULD treat a 552 code in this case as a temporary, rather than permanent, failure" — the RFC names the code as the input a client reads and then disbelieves. forward_path KEPT.
