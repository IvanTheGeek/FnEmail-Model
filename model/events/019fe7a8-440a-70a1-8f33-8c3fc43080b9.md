# `HighOrderBitCleared`

A receiving server silently altered message octets by clearing the high-order bit on content it had not agreed to receive as 8-bit.

## Where RFC 5321 says so

| Section | Lines | Text |
|:--|:--|:--|
| §2.4 | 903-908 | *"An originating SMTP client that has not successfully negotiated an appropriate extension with a particular server ... ## Notes

Harvested; the §2.3.1 citation is added here by re-sweep because it carries the fact the §2.4 quote does not — the extension can relax the restriction for the BODY only, never for the header fields, so a message whose header fields carry the high bit is out of bounds even with 8BITMIME negotiated. Strength: MAY, so both arms are permitted and neither required; the sibling arm from the same sentence, MessageRejectedAsInvalidForHighOrderBit, is equally real and is not modeled separately only because it collapses into MessageRejectedAtEndOfData's failure reply. The precondition is a NEGATIVE one: extension negotiation did not succeed — the absence of an event is what licenses this one, which is a shape worth flagging. The RFC knowingly permits silent corruption; §2.4 lines 911-913 say so. Screens: the altitude tiers file octet handling at Infrastructure, and the twelve-slice model has no content mutation at all. Related session-level event, cross-referenced to the Session Lifecycle chapter rather than claimed here: EightBitTransmissionEnabledForSession.

FIELD HYGIENE PASS: struck all three fields. transaction_id is fabricated — RFC 5321 names no transaction identifier; identity is the channel, and this event's precondition is itself a fact about the channel (that no 8-bit extension was negotiated on it). receiving_server and sending_client are struck as session-level facts: both parties are fixed by the connection and its greeting, so carrying them on a per-octet mutation is padding. The event is now fieldless and the shape is right — what changed is the content, silently, and the RFC provides no field that records which octets were altered. That absence is the finding: §2.4 lines 911-913 permit the corruption and supply nothing that would let anyone detect it afterward, which is the same undetectability IrreversibleStorageTransformApplied and DuplicateMessageReceived carry.
