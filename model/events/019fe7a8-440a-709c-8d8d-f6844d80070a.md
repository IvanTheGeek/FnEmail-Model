## Where RFC 5321 says so

| Section | Lines | Text |
|:--|:--|:--|
| §4.1.1.4 | 1997-1998 | *"This command causes the mail data to be appended to the mail data buffer."* |

## Notes

Harvested, with the §2.3.9 anchor added by re-sweep — that section is what makes 'message content' and 'mail data' one thing and fixes its boundaries as exactly the interval between the 354 and the end-of-data indication. The sweep's field appended_octets was DROPPED on merge: it is a computed value, which the kit forbids, and the alternative it forced (a fieldless event) is available without it. Genuine open question a later step must decide, not this one: whether streaming content is one event, one event per line, or no event at all until termination — the field 'line' above assumes per-line and is the honest version of that assumption. Rejected alternative names: MailDataBuffered, ContentLineReceived, MessageTextAccumulated. Screens: the capture/decision lens and the altitude tiers would both place buffer appends at Infrastructure; the consumer test kills it because nothing in the model reads a partial buffer. Siblings on the same octets: DotStuffingApplied, DotUnstuffingApplied, TextLineLengthExceeded.

FIELD HYGIENE PASS: struck one of two. transaction_id is fabricated — RFC 5321 names no transaction identifier; while the session lives the channel is the identity, and this event's place in the content stream is fixed by its position between the 354 and the end-of-data indication, which is exactly the interval §2.3.9 defines. line survives: it is the mail data itself, which §4.1.1.4 1994-1996 makes the substance of the event, and the earlier merge already removed the computed appended_octets alongside it. The value is illustrative and labeled as such; only the header field name Subject is RFC-sourced.
