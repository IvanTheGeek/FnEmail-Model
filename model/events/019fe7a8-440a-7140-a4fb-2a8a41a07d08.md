## Notes

Harvested by meaning; SHOULD NOT strength, stated at lines 1416-1417. Step 1 records what the spec makes possible, not only what it blesses, and a deprecated behavior that systems demonstrably perform is exactly the candidate a later gate should reject on the record rather than one nobody wrote down. The reason it fails is stated in the RFC itself: aliasing via MX and CNAME records, local host aliases, and proxying arrangements mean the same person reachable at two addresses cannot be recognized as one — which makes the alias and DNS provisioning events the direct cause of this event's unreliability. Sibling with the same shape, different actor and different strength: RecipientSuppressedByHeuristic (§3.9 1703-1706), where the suppression happens at the expanding server and is "strongly discouraged" rather than SHOULD NOT. Marked doubtful because the losing arm of a SHOULD NOT is a weak event. Rejected alternative names: DuplicateSuppressedAtSource, RecipientDeduplicated, DuplicateEliminationAttempted. Screens: inbound-only scope, responsibility-boundary cutoff, consumer test G1. FIELD HYGIENE PASS: retained_via struck — 1 field. Instantiated with real data it does not cohere, which is rule 8 finding the defect the way rule 8 is supposed to: the value was Example-People, the very list whose source expansion dropped the address, so the field read that SQSmith was retained through the mechanism that removed him. Whatever it was reaching for — the other address judged to be the same person — the RFC never supplies it, and the judgment itself is a derived comparison over the expanded set, which the method sends to a read model. Left with dropped_recipient alone, sourced to the EXPN example at line 1318. The strike does not collapse the candidate, which rests on the sentence at 1410-1412, but it does leave it thinner, and it was already doubtful for the reason recorded above; left doubtful.
