## Where RFC 5321 says so

| Section | Lines | Text |
|:--|:--|:--|
| §4.5.4.1 | 3759-3764 | *"When a mail message is to be delivered to multiple recipients, and the SMTP server to which a copy of the message is to be sent is the same for multiple recipients, then only one copy of the message SHOULD be transmitted. That is, the SMTP client SHOULD use the command sequence: MAIL, RCPT, RCPT, ..., RCPT, DATA instead of the sequence: MAIL, RCPT, DATA, ..., MAIL, RCPT, DATA."* |
| §4.5.4.1 | 3764-3767 | *"However, if there are very many addresses, a limit on the number of RCPT commands per MAIL command MAY be imposed. This efficiency feature SHOULD be implemented."* |

## Notes

RECOVERED BY THE RE-SWEEP. Not carried by any inherited candidate, and easy to lose because it LOOKS like RecipientLimitConfigured — but the brief's rule applies exactly here: a relay's send is not an originator's, and a client's self-imposed batching ceiling is not a server's acceptance ceiling. Different actor, different section, opposite side of the wire, and they interact: a client limit of 100 against a server limit of 500 wastes nothing, a client limit of 500 against a server limit of 100 produces the 452 chunking dance of §4.5.3.1.8 3546-3550. MAY for the limit, SHOULD for the one-copy efficiency feature it qualifies, SHOULD again for implementing that feature — three keywords in four lines. Runtime arm in another chapter: RecipientsGroupedIntoSingleTransaction. stream_root is Server Configuration in the sense of a sending system's configuration; if the roster ever splits sender configuration from receiver configuration, this moves. FIELD HYGIENE: nothing struck; both fields are essential. The value 100 is sourced honestly: §4.5.4.1 3764-3767 permits the limit and names no number at all, so the 100 is borrowed from the 100-recipient chunks at rfc5321.txt:3548, which is exactly the interaction described above — recorded here so nobody later mistakes it for a §4.5.4.1 figure.
