## Notes

RECOVERED BY THE RE-SWEEP as the violated arm of the MUST at 3173-3174. Distinct from BlindCopyRecipientDisclosedInTraceField, which is the harm; this is the act. Kept separate on the merge rule that a violation is not its consequence — a multi-path FOR on a message with no blind copies discloses nothing, and a single-path FOR can still disclose if the one path named is a bcc recipient. 'Deprecated' at 3175-3176 is doing real work: the form existed and was legal in earlier practice, so this event is how a message stamped by an old implementation looks today. The security issues it points at live in §7.2 (heading confirmed at line 4212), which belongs to the alias-and-list chapter. FnEmail screens: the inbound-only scope, since the stamping host is by definition upstream, and the responsibility-boundary cutoff. ⚠️ FIELD HYGIENE PASS: struck the fabricated `message_ref` identity key — no such key exists in RFC 5321 and f2C8D14 is not in the RFC. The stamped paths are the identity and the violation at once. Corrected the stamped_paths example under rule 8 for the same reason as TraceForClauseOmitted: a list of one cannot show a violation whose definition is 'more than one', and the single-element example silently made the event unfalsifiable. Both values are sourced.
