## Notes

A refusal is not an acceptance, so this is kept separate from ResponsibilityForMessageAccepted rather than folded into it as a reply_code variant, per the merge rule. Split out from the inherited DeliveryResponsibilityDeclined (candidate 246), which merged 4yz and 5yz to fit the sweep's count and said so in its own notes — the merge is undone here because the two have different downstream events: after 4yz the client may requeue freely, after 5yz it SHOULD not retry the same server without user review. Rejected alternative names: MessageRejectedAtEndOfData (inherited candidate 180, which covered both arms generically), DeliveryResponsibilityDeclined, TransactionFailedAtEndOfData. MUST NOT strength on the server's own subsequent delivery attempt. Two facts a later step will otherwise re-derive: the buffers are cleared on completion of the DATA command either way (§4.1.1.4 2038-2040), so a refused message leaves the session as clean as an accepted one; and responsibility does not move, which is the entire difference between this event and DeliveryFailedAfterAcceptance for the very same failure. Screens: none kill it, but a model with an accept event and no decline event at this point has an asymmetry worth a 🟥. ⚠️ FIELD HYGIENE PASS 2026-08-09 — three fields struck. transaction_id: RFC 5321 supplies no such key, and f2C8D14-1 is this project's minted value, not the RFC's; identity here is position in the session (the one reply to the end-of-mail-data terminator) together with the forward-paths the refusal covers, which is why forward_paths stays. reply_code 451: the rendering of the decision the event name already carries — the 4yz class is IN the name, and that is exactly why the inherited merge with the 5yz arm was undone, so re-carrying the code would restore by field what the split removed. reason_text 'Requested action aborted: local error in processing': struck as human-facing rendering, not data — §4.2 line 758 says the text 'is usually intended for human users' and line 2727 says 'Each reply text is recommended rather than mandatory', so the RFC itself declines to make it a fact of the event.

COLLISION RESOLVED — merged from 2 independently brainstormed records. Same section, same actor, same stream root, same meaning, same MUST NOT. Both records are the 4yz half of the same deliberate split from the inherited merged event; one had already reached the fieldless shape and the other had not finished the same reasoning.

From the duplicate in 3. Message Content Transfer: RECOVERED BY THE RE-SWEEP as a split. The sweeps produced one DeliveryResponsibilityDeclined merging 4yz and 5yz "to fit the count", and its own notes asked for exactly this split: "a facilitator may reasonably want DeliveryResponsibilityDeclinedTemporarily and DeliveryResponsibilityDeclinedPermanently as separate events, since their downstream events differ". They do: after a 4yz the client may requeue freely; after a 5yz it SHOULD not retry the same server without user review. Strength: MUST NOT. The sweep also flagged a wording trap worth keeping — the two MUST NOTs differ only in "a subsequent attempt" versus "any subsequent attempt", which is the same obligation stated twice, so a future reader should not hunt for a distinction that is not there. Codes cited from §4.3.2 line 3115: 451 and 452 are the 4yz members of the DATA error set. Opposite event: DeliveryResponsibilityAccepted. Violated arm: MessageDeliveredAfterResponsibilityDeclined. Screens: the twelve-slice model has no post-acceptance refusal at all.

FIELD HYGIENE PASS: struck all four fields. transaction_id is fabricated — and for a declined message there is no queue id either, since nothing was accepted and no trace line is stamped, so RFC 5321 supplies no identity at all for the message the client still owns. declining_server is struck as a session-level fact. reply_code is struck as a rendering, and note that the split this event embodies is a split by CLASS (4yz) rather than by code, so the class is carried by the name and the specific code adds nothing the event does not already say. reason_text is struck as operator-configurable wire text with no RFC source. Fieldless, and correctly so: the state change is a refusal of custody, and the RFC records nothing about it beyond who now owes what.
