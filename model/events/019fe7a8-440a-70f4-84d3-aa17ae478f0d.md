## Where RFC 5321 says so

| Section | Lines | Text |
|:--|:--|:--|
| §4.5.4.1 | 3759-3762 | *"When a mail message is to be delivered to multiple recipients, and the SMTP server to which a copy of the message is to be sent is the same for multiple recipients, then only one copy of the message SHOULD be transmitted."* |
| §4.5.4.1 | 3762-3764 | *"That is, the SMTP client SHOULD use the command sequence: MAIL, RCPT, RCPT, ..., RCPT, DATA instead of the sequence: MAIL, RCPT, DATA, ..., MAIL, RCPT, DATA."* |
| §4.5.4.1 | 3766-3767 | *"This efficiency feature SHOULD be implemented."* |

## Notes

SHOULD three times over — on transmitting one copy (3761-3762), on the command sequence (3762-3764), and on implementing the feature at all (3766-3767). The RFC spells the two sequences out literally rather than describing them. Dropped from the inherited candidate as belonging elsewhere: rcpt_limit_per_mail, which is a configured ceiling and now carries RecipientListSplitAcrossTransactions. Tension worth recording, not resolving: §3.9 1701-1703 speaks of "copies" forwarded to each expanded mailbox, while this rule says one copy on the wire — two different notions of copy in one document, and MessageCopyCreated in the list-expansion chapter is the other one. Opposite event: SeparateCopyTransmittedPerRecipient. Screens: inbound-only scope. ⚠️ FIELD HYGIENE PASS: NOTHING STRUCK. All three fields are load-bearing and none is fabricated: destination_server is the grouping key the RFC's own condition names ("the SMTP server to which a copy of the message is to be sent is the same for multiple recipients", 3759-3762), and forward_paths is the set that got grouped, genuinely a List. No transaction identifier appears and none could — RFC 5321 supplies none, and the mail transaction's identity while it runs is its position in the channel. queue_entry_id kept on §4.4's ID-clause ground (rfc5321.txt:3336); f2C8D14 is this project's minted value, not the RFC's.
