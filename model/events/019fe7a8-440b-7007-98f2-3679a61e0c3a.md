## Notes

RECOVERED BY THE RE-SWEEP; named as an 'upstream sibling' in the inherited ServiceExtensionRegistered notes and never promoted. A separate actor and a separate moment: IANA cannot register without it, so it is a precondition the registry event assumes. The same approval gate governs all three registries — 4395-4398 for extensions, 4411-4414 for link and protocol identifiers, 4435-4437 for additional clauses — so it is one event serving three, which is the argument for keeping it separate rather than duplicating a defining_document field three times. Strength: 'may be made only ... specifically approved' (4395-4398), a lowercase-only constraint expressed as a precondition rather than a 2119 keyword; 2.2.2 lines 536-538 uses lowercase 'must'. Rejected names: ExtensionSpecificationApproved, IesgApprovalGranted, StandardsTrackApprovalIssued. The IESG's stated criterion for the third registry is unusually explicit and worth carrying: 'the IESG is encouraged to approve on the basis of clear documentation and a distinct method rather than preferences about the properties of the method itself' (8, lines 4415-4417). Screens that would have killed it: every one; the altitude tiers have no governance tier, and no seat in the twelve-slice model belongs to a standards body. FIELD HYGIENE: struck approved_for — its value paraphrased 'specifically approved by the IESG for this purpose' (4397-4398), which is fixed by the event's own name, and the better point survives in prose above: one gate serving three registries is an argument for one event, not for a field. approval_track is genuinely two-valued in the source, Standards-Track or Experimental at 4396-4397, and approved_document's example comes from the reference at line 4584. Identity: the approved document; no key was fabricated.
