## Notes

Kept separate from ListExpanded even though both replace the forward-path identically, because the RFC itself insists the difference is real and names it at 1727-1730: the key difference is the change to the backward-pointing address. An alias leaves the reverse-path alone, so bounces reach the original sender; a list does not. Merging all three into PseudoMailboxExpanded{expansion_kind} is the obvious later-step move and would be defensible — all three are on the table deliberately, which is why expansion_kind sits on the parent event. Rejected alternative names: AliasResolved, AliasSubstituted, ForwardPathReplacedFromAliasTable. The chapter title's phrase "alias expanded with return path intact" describes an absence of change, so no separate ReturnPathLeftIntact event is offered — that is 🟤 nothing and is recorded in set_aside. §3.9.1 heading confirmed at line 1710. No RFC 2119 keyword in the whole subsection; it is descriptive prose. Screens: responsibility-boundary cutoff, HELO-only charter, inbound-only scope. Admin.MRC@foo.com is the RFC's own value from Appendix D.5 line 5114; postmaster is named as an alias target at §4.5.5 line 3801. FIELD HYGIENE PASS: nothing struck. Both address values re-verified by opening the file — line 3801 reads "the postmaster alias" and line 5114 reads "S: 250 Mark Crispin \<Admin.MRC@foo.com>" — so this event is the one in the chapter whose payload is entirely the RFC's own data. queue_id kept on the §4.4 ID-clause warrant recorded on PseudoMailboxExpanded; its value is this project's minted one and is now labeled as such.
