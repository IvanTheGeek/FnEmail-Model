## Notes

RECOVERED BY THE RE-SWEEP. §4.4 3180-3182 carries two independent MUST NOTs and the inherited set collapsed both into ReceivedLineChainAltered — but inserting one's own line in the wrong place touches nothing that was already there, so the two are different acts with different evidence. A server can commit this one while scrupulously honoring the other. §3.6.3 sharpens it: the relay's carve-out permits *adding* a Received: field, and adding it in the middle of someone else's header section arguably exceeds even that permission, since finding the middle requires the inspection the same sentence forbids. Consequence: the chain no longer reads newest-first, so the counting technique in §6.3 still works but the ordering that makes trace useful for debugging (3184-3186) does not. Sibling: ReceivedLineChainAltered. Compliant arm: TraceLinePrepended, which is the same act done right. FnEmail screens: the responsibility-boundary cutoff and the inbound-only scope. ⚠️ FIELD HYGIENE PASS: struck the fabricated `message_ref` identity key — RFC 5321 names no such key and f2C8D14 is not in the RFC. Identity is positional in the most literal sense available anywhere in this chapter: this event is *about* a position in the header section, and the insertion point is what distinguishes it from TraceLinePrepended. Sourcing is now stated: the position value is invented, though the RFC's own example message does carry a Subject header field at line 5068, so the illustration lands somewhere the spec actually shows.
