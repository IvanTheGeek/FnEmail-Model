## Notes

RECOVERED BY THE RE-SWEEP as the violated arm of the MUST NOT at 1586-1588; the inherited set carried only the compliant arm (idx 93). It matters more than most violation events because this is a rejection the receiving system takes deliberately, inside a session it controls, with a reply it chooses — it is the kind of thing an implementer does on purpose, believing it to be hygiene. DELIBERATE OMISSION, flagged rather than invented: no reply code is offered as a field, because §3.7.2 specifies none and any code here would be fabricated. That silence is itself notable — the RFC forbids the act without saying what the act would look like on the wire. Distinct from a refusal on any other ground: a 550 for policy or an unknown recipient is not this, and the merge rule that a refusal is not an acceptance cuts both ways here. Opposite: MailAcceptedDespiteMalformedTraceHeader. FnEmail screens: none would kill it outright — it sits inside the inbound-only scope — but the condemned status/phase register and the consumer test would both argue, since nothing downstream consumes the rejection. ⚠️ FIELD HYGIENE PASS: struck the fabricated `message_ref` identity key — RFC 5321 supplies no message identifier and f2C8D14 is this project's own minted value. Identity is the channel: the refusal is issued inside the session, on a message this host will never hold. THE INHERITED RECORD'S DELIBERATE OMISSION IS CONFIRMED CORRECT BY THIS PASS and is worth naming as the standard the rest of the sweep failed to meet — refusing to invent a reply_code is exactly rule 4 of this pass, applied a step earlier and voluntarily. Sourcing: 'Received:' is the RFC's own field name at line 1581; mx.foo.com is invented.

COLLISION RESOLVED — merged from 2 independently brainstormed records. Same section and same MUST NOT (§3.7.2 1585-1589), same actor — chapter 4's '(non-conforming)' is a gloss on the role, not a different actor — and the same two-field payload under two names. The chapters differ only in which anchor sentence drew them: chapter 9 came via the gateway origin of foreign trace headers, chapter 4 via the trace rule itself. One state change.

From the duplicate in 9. Gatewaying: RECOVERED BY THE RE-SWEEP — the violated arm of a MUST NOT, and no sweep carried it. It is not the same state change as its opposite and must not be merged with it: an acceptance and a refusal are different facts with different downstream consequences, and the brief is explicit that "a refusal is not an acceptance". Consequence: mail that crossed a gateway boundary legitimately is lost or bounced for a cosmetic reason, which is exactly the outcome §3.7.2 legislates against. reply_code 550 is illustrative of a permanent refusal; a server could equally use 451, and the field records which rather than deriving it. Rejected alternative names: TraceFormatRejectionIssued, MessageRefusedForNonconformingTrace. Which project screen would have killed it: none cleanly — this one sits inside the inbound-only scope, which makes it the chapter's second survivor alongside MailAcceptedDespiteMalformedTraceHeader.

FIELD HYGIENE PASS: struck two fields. (1) message_ref (example f2C8D14) — no message identifier exists in RFC 5321; a Transaction-rooted refusal is identified by its position in the live session, the channel being the session's identity. (2) reply_code (example 550) — a reply code is the rendering of a decision, and the method forbids computed or derived values in an event. The test the brief sets is whether the RFC carries the code as data beyond the wire, and here it does not even carry it on the wire: §3.7.2 lines 1585-1588 FORBIDS this rejection outright and therefore assigns it no code, so 550 was chosen by the sweep, not read from the source. The preserved note above defends the field on the grounds that "the field records which rather than deriving it" — that defense fails the source test, and it is recorded rather than deleted so the reasoning stays visible. Also corrected rejecting_host, which read bar.com: foo.com is the walk scene's receiving server.
