## Notes

Carried over from idx 195 with citations re-verified line by line. Three SHOULDs, no MUST, and the rationale is explicitly informational — 'Use of UT loses information about the time zone-location of the server' (3200-3201) — so the whole cluster is about how much a trace line reveals about where a server stands, which is the same axis §7.6 worries about from the privacy side. Note the two sections pull in opposite directions and neither cites the other: §4.4 wants local time because it discloses location, §7.6 warns about disclosure. Worth a 🟥. This is configuration-time state, not per-message, which is why it is an event rather than a field on TraceLinePrepended — the -0700 in that event's stamped_at example is *produced* here and otherwise has no origin. Violated arms recovered separately: TraceDateStampedWithZoneNameInsteadOfOffset and ObsoleteDateFormUsedInTraceLine. Set aside as a non-event: TimeZoneNameSuppliedInComment, which is a field of the line, not an occurrence. FnEmail screens: the four altitude tiers put this squarely in Infrastructure, and the consumer test finds nothing reading it. ⚠️ FIELD HYGIENE PASS: nothing struck — this event never carried `message_ref`, correctly, since it is configuration-time and no message exists yet. Sourcing is now stated for all four fields and one is honestly weak: 'local' is the RFC's own word at line 3188 and the offset is the walk scene's, but zone_name_in_comment is a Boolean this project invented to hold the SHOULD at 3201-3202 — the RFC states the behavior and supplies no value. Flagged rather than removed, because the three SHOULDs are three genuinely independent settings and dropping the third would misreport the cluster as two.
