## Notes

RECOVERED BY THE RE-SWEEP. The §3.9 sweep named this candidate and dropped it explicitly for the thirty-two-event ceiling — its span notes say "Two more dropped on merit and named in the events they belong to: ServiceProcessExited and AddressExpansionSupportEnabled" and MailingListDefined's notes say it was "dropped for room". This is exactly the material the cap stole. It is the only place in §3.9 that states an obligation on the host itself rather than on a message in flight, and it is the SHOULD that every other event in the chapter presupposes. Strength: SHOULD, and note what it obliges — support for BOTH models, not either. Rejected alternative names: ExpansionModelsSupported, AliasAndListSupportEnabled, MultipleDeliverySupportEnabled. Its opposite arm is AddressExpansionModelLeftUnsupported. Screens: the four altitude tiers (configuration, not protocol) and chapter 15 (Server Configuration and Provisioning) has an equal claim on it — flagged rather than surrendered, because the SHOULD is stated in §3.9 and nowhere else. FIELD HYGIENE PASS: nothing struck. Two fields, both sourced: foo.com is the RFC's own receiving host from Appendix D.1 and supported_models carries the two model names the SHOULD itself supplies at 1689-1690. No identifier was needed or invented — a Server Configuration stream is keyed by the host, which is the one case in this chapter where the identity key is a real value the RFC prints rather than a minted one. Compare ExpansionDeferredUntilAfterAcceptance, which after its hygiene pass has only this same host field left and was marked doubtful in consequence: the difference is that supported_models is a genuine value set the spec names, where `deferred` was a Boolean restating its own event name.
