## Notes

CITATION CORRECTED to 1744-1746, same reason as DeliveryAcceptedByList. The other half of the pair. source_queue_id is the only thing linking the new message to the old one, and nothing in the SMTP envelope carries that link — the correlation exists in the list's own store and nowhere on the wire, which makes it a fact that survives no reimplementation except as a local record. That is a genuine test case for the four altitude tiers rather than an application of them. Contrast with the constrained list at 1730-1733, where no new message exists at all: two events or zero depending on what the list did to the body, so the classification decides the event count, which is unusual and worth flagging. Rejected alternative names: NewMessageOriginatedByList, ListPostedMessage, ListRepublishedContent. Screens: inbound-only scope (this is an originating act), responsibility-boundary cutoff. FIELD HYGIENE PASS: nothing struck. All four fields are facts this act creates rather than values it carries: the new message's identity, its envelope sender, its envelope recipients, and the link back to the message that caused it. reverse_path survives where DeliveryAcceptedByList's did not, because here the list is writing a new value, not passing an old one along. recipients was tested against the derived-value rule — it is the list's membership, which ListMemberAdded and ListMemberRemoved already record — and kept, because what the posting act produced is the envelope the list actually built, which is a fact about this message and not a query over the membership stream; the same reasoning keeps expanded_addresses on PseudoMailboxExpanded. Both queue ids are now labeled minted, and the note above about the link existing nowhere on the wire is the reason this event is the sharpest illustration in the chapter of what RFC 5321's missing message identifier costs.
