## Notes

Inherited (candidate 25); citations verified. The ambiguity it records is real and worth not re-deriving: lines 1376-1377 say 502 or 500 SHOULD be returned in the syntax-only case, and lines 1380-1381 say returning 500 or 502 for VRFY is not full compliance. The RFC prescribes a reply and then calls sending it non-compliant. The presumed resolution — a compliant server never reaches the syntax-only case because it actually verifies — is nowhere stated, so it stays a hotspot rather than a reading. Strength: MUST NOT on the 250 it replaces, SHOULD on the substitute. §4.5.1 line 3392 puts VRFY on the list of commands that MUST be supported to conform, which sharpens the same contradiction from a third direction: a server may not implement a command it MUST support, and the RFC tells it which code to use when it does not. §4.3.2 lists 500/502/504 as error replies for both VRFY (3128) and EXPN (3133), so the event covers both commands. Rejected alternative names: VrfyNotImplemented, CommandUnimplementedReported, VerificationUnavailable. Which screen would have killed it: the condemned status/phase register (it reads the compliance state as status), 'one event per command'. Cross-reference: CommandRejectedAsUnimplemented in a Command Dialogue chapter names the generic 502 case; this is the VRFY/EXPN-specific one, which carries the non-compliance finding the generic one does not.
