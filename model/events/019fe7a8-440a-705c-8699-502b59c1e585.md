## Notes

RECOVERED BY THE RE-SWEEP. Named as a missing sibling in the inherited FinalDeliveryMade notes ('MessageForwardedToAnotherMailSystem, from 3211-3212 ... which is the same moment classified the other way') and never given a row by any sweep. It matters because it is the reason the final-delivery determination at 3226-3228 is undecidable and the reason relays are given a MAY to strip and rebuild the return path: this event is what happens after a server has already decided it was making final delivery. Cross-reference, do not merge: MessageRelayedToNextHop (inherited candidates 182 and 271) is SMTP-to-SMTP with the message data unmodified except for trace, and belongs to the relay chapter; this event crosses out of the SMTP environment entirely and may transform the message, which §2.3.10 819-822 says a relay is forbidden to do. The two look alike and are not. target_transport_environment carries a real alternative rather than decoration — §1.1 names the public Internet, a firewalled intranet, and non-TCP environments. Screens: inbound-only scope, HELO-only charter, and the responsibility-boundary cutoff. ⚠️ FIELD HYGIENE PASS 2026-08-09 — one field struck. message_id: RFC 5321 supplies no message identifier; §4.4's ID clause (line 3336) is optional and lives in the receiver's own Received: stamp, msg-id is RFC 5322's, and f2C8D14 is this project's minted queue_id value. Identity here is the forward-path being carried onward, which is the only handle that crosses the transport boundary with the message. The example for target_transport_environment is now marked honestly: the RFC names X.400 (line 3466) but as an address form under MIXER, not as an environment; the RFC's own environment list is §1.1 lines 246-248 — the public Internet, a firewall-isolated TCP/IP Intranet, or some other LAN or WAN using a non-TCP transport.
