## Notes

The opposite arm of ListMemberAdded, split from the inherited ListMembershipChanged for the reason recorded there. Rejected alternative names: MailingListMemberRemoved, SubscriberRemoved, AddressRemovedFromMailingList, MembershipRevoked. One member per event rather than a whole-membership snapshot, because that is what actually happens over time and because a snapshot would make every expansion depend on a version rather than on facts. A related sibling is deliberately NOT recorded: MemberDeliveryDisabled after repeated bounces is real-world list behavior with no RFC 5321 support anywhere, and inventing it here would put an unsourced event in a chapter whose whole value is that every row traces to a line. Screens: same four as ListMemberAdded. FIELD HYGIENE PASS: removed_at struck — 1 field, on the same two reasons as ListMemberAdded.added_at. It carried the same transplanted walk-scene timestamp, Tue, 19 May 1998 09:14:07 -0700, which is the tell: one instant cannot be the moment a message was accepted at foo.com, the moment Fonebone joined Example-People, and the moment SQSmith left it. Instantiating with real data is what exposes it, which is rule 8 doing exactly the work it is there for. Both surviving fields are the RFC's own data from the EXPN example at 1315-1318. The event is now two fields, both identity: which list, which member — and no payload beyond that, which the method sanctions outright.
