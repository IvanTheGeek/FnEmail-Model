## Notes

Inherited from raw candidate NotificationDeliveryFailed, kept intact. Distinct from DeliveryFailedAfterAcceptance because the message being abandoned is ITSELF a notification, which forecloses the normal response: §4.5.4 3682-3683 forbids an error message in response to an error message "under any circumstances", and §3.6.3 1505-1506 forbids it again. So this event is a dead end by construction, and that is exactly why the postmaster redirect below exists. Strength: the RFC's diagnosis is stated as usual-case, not certainty — "that usually indicates a problem" (3796-3797) — and the whole clause sits inside parentheses in the source, which is a fair signal of its weight. notification_kind should take one of the three values §4.5.5 names at 3789-3793: non-delivery notifications, DSNs (RFC 3461), MDNs (RFC 3798); this chapter owns only the first, and the other two are named so a reader does not assume the rule is bounce-specific. ⚠️ INHERITED CITATION ERROR CORRECTED: three raw candidates (NotificationSentWithNullReversePath, DeliveryGivenUp, NullReversePathReplacedOnForward) attribute the substantive null-reverse-path text at lines 1494-1519 to §3.6.1. It is §3.6.3 — heading verified at line 1475; §3.6.1 is at line 1421 and ends at 1446, where §3.6.2 begins. Every rfc_ref in this chapter uses §3.6.3. Rejected alternative names: BounceUndeliverable, DoubleFailureOccurred, NotificationBounced (rejected — it cannot bounce, which is the point). Which screens would have killed it: the inbound-only scope and the consumer test (G1).
