## Notes

RECOVERED BY THE RE-SWEEP. The §7 sweep's own span notes named this as a sibling it did not have room for, and the 32-event cap cut it; §4.1.4 lines 2498-2500 independently confirms that access denial based on authentication or authorization is the legitimate basis for refusing EXPN, which makes this the missing precondition of ExpnAccessDenied rather than an optional nicety. Strength: 'may choose' at 4270 is lowercase, not a 2119 MAY — the §7 sweep flagged that §7 is full of lowercase modals that read like keywords and are not, and this is one. Anyone tiering it on strength must read the sentence, not the word. This is a third position between full support and full disablement, and it is the RFC's preferred one: 4265-4269 says the commands remain useful, and 4272-4273 says implementations SHOULD still support EXPN. Rejected alternative names: VerificationRestrictedToAuthenticatedRequestors (the §7 sweep's own working name — rejected only because it omits EXPN, which the sentence names first), DiagnosticAccessScoped, VrfyAuthenticationRequired. Which screen would have killed it: the altitude tiers, the twelve-slice model, the HELO-only charter, and any screen that treats authentication as out of scope — SMTP AUTH is not defined in RFC 5321 and is named here only in passing. Sibling: MailingListAccessRestricted, which is per-list where this is per-server. FIELD HYGIENE PASS: nothing struck. No reply code, no invented identity key, and restricted_commands is quoted from the sentence that licenses the whole event at 4270-4271. permitted_requestors is now labeled illustrative for a reason that matters to the event's confidence: RFC 5321 defines no authentication mechanism of its own, so any concrete requestor class is ours and not the spec's — the same fact the note above records about SMTP AUTH, now visible in the field set instead of only in prose. server_host is the stream's identity on a Server Configuration root.
