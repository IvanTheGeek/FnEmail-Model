## Notes

The other half of the inherited DeliveryResponsibilityDeclined split. ⚠️ Rule 2 detail that must survive: line 2985 reads 'SHOULD not', with a lowercase 'not' — not the RFC 2119 'SHOULD NOT'. Quoted exactly as printed; a reader who normalizes it has changed the citation. Whether the lowercase is editorial slip or deliberate is not decidable from the text, and it is the kind of thing rule 3 exists to catch. The two MUST NOTs at 2960-2961 and 2982-2983 differ only in 'a subsequent attempt' versus 'any subsequent attempt' — the same obligation stated twice, flagged so nobody hunts for a distinction that is not there. The real difference is downstream, in the client, and it is a SHOULD not a MUST. Sibling that follows from this one: MessageHeldForUserReview, inherited candidate 251, owned by whichever chapter carries the client queue. Screens: inbound-only scope keeps the reply but discards the client-side consequence that gives it meaning. ⚠️ FIELD HYGIENE PASS 2026-08-09 — three fields struck. transaction_id: no session or transaction key exists in RFC 5321, and f2C8D14-1 is this project's own minted queue_id value; identity is position in the session plus the forward-paths refused. reply_code 554 and reason_text 'Transaction failed': struck as the rendering of the decision (the 5yz class is already in the event name) and as human-facing text the RFC declines to mandate (§4.2 line 758, line 2727). ONE CAVEAT, recorded because it is the only place in the chapter where the drop-the-reply-code rule is arguable: §4.2.5 line 2986 requires 'user review of the message and response' before the client retries the same server, which does carry a response past the wire — but it carries it in the CLIENT's queue, for a human, and this event's actor is the server. If a later step wants the code back as data, that is the line to cite and MessageHeldForUserReview is the event that should hold it.

From the duplicate in 3. Message Content Transfer: RECOVERED BY THE RE-SWEEP as the other half of the split described under DeliveryResponsibilityDeclinedTemporarily. Strength: MUST NOT for the server, then a lowercase-ish "SHOULD not" for the client — the RFC writes "SHOULD not" rather than "SHOULD NOT" at line 2985, and rule 2 requires the quote to keep it; whether that is a typographic slip or a deliberate softening is a genuine ambiguity, and it is the sentence that governs whether a client may ever retry, so it matters. The client consequence is what makes this a different event from its 4yz sibling: the message stops moving until a human looks at it, which is a state change in the SENDING system with no name in this chapter (cross-referenced to Sending, Queueing and Retry as the sweeps' MessageHeldForUserReview). The 554 text is verified at §4.2.2 line 2846 and is truncated there exactly as the RFC breaks the line. Opposite: DeliveryResponsibilityAccepted. Violated arm: MessageDeliveredAfterResponsibilityDeclined. Screens: same as its sibling.

FIELD HYGIENE PASS: struck all four fields, and this is the one event where the reply-code test was genuinely close. §4.2.5 line 2985-2987 says the client SHOULD not retry "without user review of the message and response" — that is the one line in RFC 5321 where a reply is retained as data past the exchange rather than merely written on the wire. It does not license a reply_code here, for two reasons: the retention is the CLIENT's, on the message it still holds, so it belongs to the sending system's hold event (cross-referenced above as MessageHeldForUserReview in Sending, Queueing and Retry), not to this server-side event; and what is retained is "the response", the whole reply, not a code extracted from it. So reply_code and reason_text are struck as renderings, transaction_id as fabricated (no queue id exists either — nothing was accepted), and declining_server as a session-level fact. Fieldless.
