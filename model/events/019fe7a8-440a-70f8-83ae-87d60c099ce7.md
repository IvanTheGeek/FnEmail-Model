# `QueueFlushTriggeredByPeerContact`

Receiving mail from a host caused queued mail destined for that same host to be released for immediate retry, short-circuiting the retry schedule.

## Notes

Stated twice from opposite sides — §4.5.4.1 3725-3727 as a client optimization and §4.5.4.2 3783-3785 as a server one — with "can" and "could" and no normative keyword either time. Structurally the most interesting event in the chapter: an INBOUND fact causing an OUTBOUND state change, the one place in this material where an inbound session has a consequence outside itself. Dropped as derived: messages_released, a count over the queue. The ETRN request itself is a command, not an event, and is in set_aside; the RFC's point is that this behavior often makes that command unnecessary. Unresolved: whether this and HostReachabilityRestored are one event or two. Screens: inbound-only scope and the responsibility-boundary cutoff, both of which sever exactly the link this event is. ⚠️ FIELD HYGIENE PASS: STRUCK triggered_at as a bare occurrence stamp — the whole point of the event is that it short-circuits the schedule, so no interval is measured from it. peer_address is KEPT, and deliberately in contrast with the host_address struck from HostMarkedUnreachable: here the RFC says "address" in its own words twice, "received from a particular address" (3725-3726) and "from a particular host address" (3783-3785), so the address is the spec's own trigger rather than an address-resolution result imported from another chapter. The inbound session that triggered this carries no identifier the event could reference: RFC 5321 supplies no session, transaction or connection identifier, so the peer's host and address are the whole of what links the two sides.
