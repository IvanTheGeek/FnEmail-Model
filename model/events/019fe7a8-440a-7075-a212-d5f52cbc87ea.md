## Notes

Carried unmerged from the timeout sweep. Held apart from CommandTimeoutExpired because the RFC gives it a distinct purpose and an innocent explanation: the client must distinguish a failed connection from a delayed greeting, and the delay is legitimate load-shedding. So this timeout is NOT evidence the peer is broken, which is what makes it unlike every other timeout in §4.5.3.2 — a delivery attempt that ends here should be retried, not condemned. The 5-minute value is SHOULD strength and a floor, not a fixed figure. The paired non-event, the connection failing at transport level before any greeting is due, belongs to the Queue / Next-Hop chapter. Screens: the inbound-only scope kills it — this is a client event end to end. FIELD HYGIENE PASS: struck 3 fields. session_id struck — no such key in the spec; the channel the client is waiting on is the identity, and server_host names the far end of it. server_address struck as a second name for the same endpoint. waited_seconds struck as a derived and duplicated value: 300 is simply the §4.5.3.2.1 five-minute SHOULD floor restated, so it is site configuration recorded at TimeoutPolicyConfigured, and the actual elapsed time is computable from this event's own occurrence time against the moment the connection opened — the method's ban on computed values covers both readings.
