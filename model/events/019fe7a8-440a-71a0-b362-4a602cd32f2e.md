## Notes

RECOVERED BY THE RE-SWEEP. The inherited candidates carried only the honored arm of the 550 SHOULD; both 3.6.2 and 7.9 state it as SHOULD, so the other arm is conformant-but-discouraged behavior, not a violation, and it is where interoperability breaks: a client keying retry logic on 550 treats 553 or 450 differently. Strength: SHOULD in both places; 7.9 line 4381 attaches it to three landing points while 3.6.2 attaches it only to declining a particular address. Rejected names: RelayRefusedWithWrongCode, PolicyRejectionCodeDeviated. Sibling: RelayTaskDeclined (honored arm). --- FIELD HYGIENE - JUSTIFICATION COLLAPSED; confidence lowered from likely to doubtful. Struck reply_code (553, the rendering of a decision) and relay_host. Once the code is gone this record is RelayTaskDeclined with a different value on the wire: everything that distinguished it lived in that one field, which makes it a field wearing an event's name. Its own inherited note anticipated the verdict - the capture/decision lens 'would call it the same capture with a different value'. Kept, not dropped; deciding is a later step's job. The SHOULD it records is real, and a reader who wants the deviation should attach it to the reply view, not to an event.
