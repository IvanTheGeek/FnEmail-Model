## Notes

MERGE: absorbs TimeoutPolicyConfigured (rejected name; same state change reached from §3.8's cross-reference rather than from §4.5.3.2 directly). Its sweep recorded a distinction worth keeping verbatim: the 'easily reconfigurable' sentence is addressed to CLIENTS ('An SMTP client MUST provide a timeout mechanism', 3612), while the server-side five-minute figure at §4.5.3.2.7 3668-3669 is a bare SHOULD with no reconfigurability language at all — so extending 'easily reconfigurable' to the server side is an inference, not a quotation. Recorded so nobody re-derives it. Seven named per-command minimums, all SHOULD (3620-3621): initial 220 five minutes, MAIL five, RCPT five, DATA initiation two, data block three, DATA termination ten, server timeout five. They are floors an administrator may raise but not lower, so a configured value below one of them is the violated arm. Without this event, CommandWaitTimedOut's limit has no origin. Screens: inbound-only scope and the altitude tiers. FIELD HYGIENE: struck recompile_required (false) — a constant that restates the preference at 3614-3615 ('preferably without recompiling'), which is a property of the mechanism the implementer built, not a fact recorded by an individual reconfiguration. Renamed timeout_seconds to timeout_minutes and changed the example from 600 to 10: RFC 5321 states every per-command minimum in minutes, including the §4.5.3.2.6 heading 'DATA Termination: 10 Minutes.' at rfc5321.txt:3656, so 600 was a unit conversion — a derived rendering of the spec's own number, and unsourceable as written. Both surviving values now come from that one heading line. No session, transaction or connection key was present; identity is the host plus the named timeout.
