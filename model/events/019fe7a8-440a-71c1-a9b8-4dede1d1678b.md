## Notes

RECOVERED BY THE RE-SWEEP. Candidate 226 (ClientStateAdvanced) named it as a merged sibling and it was never given a row. Kept separate from the generic state advance because the state change is different in kind: the client is acting on a code it has no table entry for, which is the forward-compatibility mechanism the whole reply-code scheme rests on. Two MUSTs in one sentence at 2624-2626, restated at 3041-3043 with a SHOULD in front of it — an unusually strong pairing, and worth noting that the SHOULD ("interpret only the first digit") is the weaker general habit while the MUST binds only for unrecognized codes. Note the oddity at 2615-2617: the RFC says "a receiver-SMTP SHOULD test the first digit" where the actor examining a reply is the sender-SMTP; the text is quoted as written per rule 2, and the mismatch is the source's, not ours. Rejected alternative name: ForwardCompatibleReplyHandled. The parent event ClientStateAdvanced (candidate 226) is deliberately NOT carried into this chapter — it is a free-floating status transition whose whole content is "the automaton moved", and it belongs to whichever chapter owns the client state machine; it is named here so the decision is retrievable. Screens: the condemned status/phase register, G1, and the inbound-only scope.

FIELD HYGIENE PASS (chapter 14): session_id struck — RFC 5321 names no session, transaction or connection identifier, and f2C8D14 is nowhere in the RFC; identity here is position in the session. severity_digit struck as a derived value in its purest form — it is literally the first character of received_code, and lines 2624-2626 describe taking it as an operation on the code, not as a separate datum. received_code KEPT; the line that makes it data is 2624-2626, "a sender-SMTP MUST be prepared to handle codes not specified in this document and MUST do so by interpreting the first digit only" — the client did not compute this code, it read it off the wire and had no table entry for it.
