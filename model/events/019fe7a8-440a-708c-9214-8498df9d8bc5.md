## Notes

Merged CommandWaitTimedOut (§3.8 sweep) and ServerInactivityTimeoutExpired (timeout sweep). Rejected alternative names: CommandWaitTimedOut, SessionClosedAfterInactivity, InactivityTimeoutFired. awaited_input matters and SessionClosed{cause:timeout} loses it: §3.8 names two distinct waits, for a command and for data, and §4.5.3.2 gives them different minima. This is the ONLY server-side timeout in §4.5.3.2 and therefore the only one inside the project's current inbound scope — every other member of that section is a client obligation. SHOULD strength and a floor, so it is site-configurable, which is what TimeoutPolicyConfigured records. waited_seconds is the configured limit reached, a fact; an elapsed_seconds field would be a computed value and is deliberately omitted, per the kit's ban on derived data. Its consequence is not an implementation detail: this is one of only three circumstances §3.8 lets a server intentionally close under normal operation, so TransmissionChannelClosed with close_arm timeout is required downstream. It is also the event that resolves the unbounded wait in ClientAbandonedSessionWithoutQuit. FIELD HYGIENE PASS: struck 2 fields. session_id struck: no such key in the spec; the channel about to be closed is the identity. ⚠️ waited_seconds struck, reversing the note above, which argued the configured limit reached is a fact and only an elapsed_seconds field would be derived. The reversal: 300 is the §4.5.3.2.7 five-minute SHOULD floor restated, so the value is standing site configuration already recorded by TimeoutPolicyConfigured, and copying it onto every expiry is duplication whichever way the derived/recorded line is drawn. awaited_input survives and is the better carrier of the point the old note was making, since §3.8 lines 1657-1658 names exactly two waits with different minima.
