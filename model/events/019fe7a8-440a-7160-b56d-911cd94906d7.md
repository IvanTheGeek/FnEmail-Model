## Notes

RECOVERED BY THE RE-SWEEP. The inherited set carried only the refusing arm (CrossTypeVerificationRefused); line 1280-1281 states the accepting arm in the same sentence and it was cut. Strength: MAY for the positive response, SHOULD for the error (1281-1282) — the asymmetry means a server that answers positively is on firmer ground than one that refuses, which reverses the intuition. The precondition is a fact about delivery, not about the directory: 'a message so addressed would be delivered to everyone on the list' — a claim a server can only make from its own expansion rules, so this event depends on MailingListMemberAdded and MailingListCreated (other chapters). Rejected alternative names: ListAcceptedAsUserName, VrfyOnListSucceeded, ListVerified. Which screen would have killed it: 'one event per command', which would fold every VRFY outcome into one; the guest-viewed-calendar test, if a positive verification is read as a pure lookup result. Sibling: UserNameExpandedAsSingletonList, the mirror case on EXPN. FIELD HYGIENE PASS: struck reply_code (250). It is the wire rendering of the positive response the MAY at 1280-1281 licenses, it is not data the RFC carries anywhere beyond the reply line, and the fact it encoded — that the answer was positive — is already the event's name and its meaning. One field survives, the name asked about, quoted from the RFC's own EXPN example at line 1315. No invented identity key was present.
