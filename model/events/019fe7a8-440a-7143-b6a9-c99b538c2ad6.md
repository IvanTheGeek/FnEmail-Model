## Notes

Harvested by meaning as blind-copy handling, which this chapter's charter names. Strength: SHOULD, with the ordering fixed by "then". The removal is only half the privacy guarantee — §7.2 lines 4218-4235 is the other half, and if the same addresses reappear in a trace field or an Apparently-to field the removal bought nothing, which is why RecipientListCopiedIntoHeaderSection and BlindCopyRecipientDisclosed sit in the same chapter. Rejected alternative names: BccFieldsStripped, BlindCopyAddressesRemovedFromHeaderSection, HeaderSectionScrubbedOfBcc. Home-chapter caveat, flagged rather than silently resolved: its anchor is Appendix B and none of the sixteen chapters claims Appendix B, so this event and EmptyBccHeaderFieldInserted are taken here on the strength of the charter phrase "blind-copy handling"; if a submission chapter is ever added they move. Screens: responsibility-boundary cutoff, inbound-only scope. FIELD HYGIENE PASS: nothing struck. removed_addresses is what the event destroys and therefore stays under the line applied across this chapter — after the strip, those addresses survive nowhere in the header section, which is the entire point of the SHOULD at 4740-4741 — and submission_host says which host acted. The citation was re-verified by opening the file: lines 4740-4741 read "Any BCC header fields" / "SHOULD then be removed from the header section.", so the range holds. Compare its immediate successor EmptyBccHeaderFieldInserted, which lost both its fields in this pass: the difference is that this event has a payload that varies and that one does not.
