## Notes

RECOVERED BY THE RE-SWEEP; 7.6 contributed nothing to the inherited set beyond a cross-reference in TraceRecipientNarrowed's notes. The most interesting thing about it, and why it must not be folded into TraceLinePrepended: the disclosure happens through CONFORMANT behavior. There is no violated arm — following the specification exactly is what leaks. Strength: none; 'should be aware of it' (4326-4327) is lowercase and asks for awareness, not action. Rejected names: TraceFieldDisclosedInternalTopology, ReceivedHeaderLeakedHostNames, InternalNameEscapedToPublicInternet. Sibling: BlindCopyRecipientDisclosedInForClause, same subsection. Cross-reference: TraceLinePrepended and TraceRecipientNarrowed are the acts; this is what the acts cost. Screens that would have killed it: the consumer test, the altitude tiers, the 'one event per command' target. FIELD HYGIENE: struck carrying_message — type MessageId, value \<f2C8D14@foo.com>, and both halves are fabrications. RFC 5321 supplies no message identifier; 4.4's ID clause at line 3336 is ID = CFWS "ID" FWS ( Atom / msg-id ), an OPTIONAL trace clause whose msg-id is defined in RFC 5322, so it neither requires nor supplies an identifier for events. f2C8D14 appears nowhere in rfc5321.txt — this project's own minted queue_id from the walk scene, commit 6acfc68 — and nothing here is a queue id, so it does not survive. Struck originating_network as context rather than fact: 4321-4325 describes the LAN case to explain why the leak happens; the leak itself is one host name. That survivor has no RFC source, the spec never showing an internal name, which is exactly why the disclosure is invisible in its own examples. Identity: the message, which this spec cannot identify.
