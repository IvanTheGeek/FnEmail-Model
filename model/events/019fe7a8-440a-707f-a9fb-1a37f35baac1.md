## Notes

RECOVERED BY THE RE-SWEEP, as a split out of the inherited ClientIdentityAnnounced, which fused the client's name claim and the mutual initial state into one event — its own notes said 'Two facts are fused here deliberately, and a facilitator may want them split'. The fusion is precisely what a capped sweep produces. The split matters because the RFC makes this a TWO-PARTY MUTUAL fact confirmed by the reply, not by the command: the client's claim is unilateral, this is not. It is also the only place the spec says a greeting clears buffers on the honored path, which is what makes SessionReinitialized and GreetingRejected legible as its two mid-session variants. Kit tension recorded and deliberately not resolved: with only a reply code and a session key this is close to a fieldless event, which the kit licenses — 'If an event has no meaningful payload beyond its identity (e.g., a simple state transition), it is fine to have no fields or just the identity key' — while warning in the same breath that 'An event without fields is an opaque label'. Both are true here. Screens: the one-event-per-command design target, which wants a single postcondition per greeting. FIELD HYGIENE PASS: struck 2 fields, and this event is now FIELDLESS — the tension the note above recorded is resolved by the source rather than by preference. session_id struck: no session key exists in RFC 5321. reply_code 250 struck: it is the rendering of the confirmation the event name states, and it cannot vary — §4.1.1.1 lines 1822-1825 ties the initial state specifically to a '250 OK'. What identifies this event is its position in the session, immediately after the greeting it answers, and what it asserts is a mutual state with no payload at all. This is the method's sanctioned fieldless outcome, not a stripped event.
