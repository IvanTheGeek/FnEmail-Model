## Notes

CITATION CORRECTED during the merge: the inherited candidate cited lines 1745-1746 for this sentence; it begins with "Such mailing" at the end of line 1744, so the range is 1744-1746. Half of a two-event pair the RFC states in a single clause — "accept a delivery and post a new message" — and splitting it is the point: between the two, the message that arrived has been delivered and the message that leaves has not yet been sent, and they are different messages with different identities. That is a bounded-context boundary the RFC draws itself, and the cleanest example in this chapter of the difference between a relay (one message, many hops) and an origination (a new message). The current model's responsibility boundary lands at MessageAccepted, which is this event under another name for a different actor — the same boundary showing up twice in the protocol with the same shape is worth a facilitator's attention. Rejected alternative names: MessageDeliveredToList, ListAcceptedDelivery, TransitChainEndedAtList. Paired with MessagePostedByList; neither happens when the list is constrained (ListTreatedAsTransitContinuation). FIELD HYGIENE PASS: reverse_path struck — 1 field. It was Smith@bar.com, carried unchanged from the transaction that delivered the message and already recorded on the accepting event, so it is derived under the method's rule. The counter-argument is recorded rather than dismissed, because it is not weak: this is the last moment the original reverse-path applies to this message, and after it the chain is over, which is an argument that the event should capture it. It lost on the line applied across this chapter — a value the event changes or destroys stays, a value merely carried along goes — and on the observation that the arriving message's reverse-path is reachable from the delivery that brought it. What remains is which message and which list took it, which is what the sentence at 1744-1746 actually reports. queue_id kept on the §4.4 ID-clause warrant.
