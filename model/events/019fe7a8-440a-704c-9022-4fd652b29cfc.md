## Notes

RECOVERED BY THE RE-SWEEP — named as a sibling in idx 283's notes and never given a row, which is the single clearest loss the cap caused in this chapter: it carries the *strongest* obligation in §6.3 while the event that was kept carries only a SHOULD. MUST, unconditional, applying whatever mechanism is in use — so unlike MailLoopDetected there is no conforming way to opt out. And the definition is the weakest in the section: 'trivial' is never defined, no mechanism is specified, and 'provisions for detecting and stopping' does not say what stopping means. A mandatory requirement with an undefined trigger and an undefined action is a 🟥 in its own right, and the inherited note flagged it as one. loop_shape carries the observed cycle as a fact rather than a verdict; the example is the trivial case the term must at minimum cover, a host relaying to itself. Opposite arm: LoopedMessagePassedOnUndetected. Related: MailLoopDetected (the counting route to the same conclusion), LoopingMessageRejected (a disposition). FnEmail screens: the consumer test / G1, the inbound-only scope, and the twelve-slice model, which has no loop control at all. ⚠️ FIELD HYGIENE PASS: struck the fabricated `message_ref` identity key — RFC 5321 supplies no message identifier and f2C8D14 is this project's own minted queue id. Identity is the observed cycle plus the host that broke it. `loop_shape` survives the derived-values test as the inherited note argued — it records what was seen, not a score computed from it — but its example is honestly unsourceable and now says so, which is the finding rather than a defect: the RFC never defines 'trivial', so no example of a trivial loop can be taken from the text, and any value here is the modeler's guess at a term the spec left empty while making it mandatory.
