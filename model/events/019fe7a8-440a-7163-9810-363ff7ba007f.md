## Notes

Inherited (candidate 294, renamed from AddressVerificationRefused, which was too broad — it collided with three other refusal events in this chapter). Its citation of lines 4241-4242 quoted only the tail of the sentence; the quote is completed here from the file. Strength: MUST, twice (4241, 4244) — which is the sharpest normative statement in the whole chapter and the reason this is a separate event from AddressVerificationDeclinedAsUnverifiable, whose 252 is a SHOULD arising from inability rather than from policy. The state change is the requester's: it now knows it will get no answer from this host, ever, rather than not this time. Rejected alternative names: AddressVerificationRefused, VerificationSuppressedByPolicy, DisabledCommandAnswered. Upstream configuration events: VrfySupportDisabled and ExpnSupportDisabled. Which screen would have killed it: the HELO-only charter (VRFY and EXPN out of scope entirely), the guest-viewed-calendar test — but a 252 is a refusal to answer, not an answer, which is the argument for keeping it. Standing tension to record and not resolve: §3.5.3 lines 1376-1377 prescribe 502 or 500 in the syntax-only case while §7.3 requires 252 for the disabled case, so a disabled server that also happens to be asked about a syntactically valid address has two MUST-adjacent codes pointing at it. FIELD HYGIENE PASS: struck reply_code (252). This was the hardest strike in the chapter, because here the code is the substance of a MUST — §7.3 line 4244 requires 252 specifically, 'rather than a code that could be confused with successful or unsuccessful verification'. It still goes: the test is whether the RFC carries the code as data beyond the wire, and it does not; the requirement governs what the server emits, and the sentence stating it sits in the rfc_refs. command is kept because §3.5.2 lines 1360-1361 make VRFY and EXPN independently switchable ('either or both'), so it varies and carries information. server_host is kept — sourceable, not derived, not an invented identity key — but flagged: on a runtime reply event it repeats what the actor field already says, and a later step may well find it padding. Striking it would be a modeling judgment, not field hygiene. No invented identity key was present; identity is the query plus the channel.
