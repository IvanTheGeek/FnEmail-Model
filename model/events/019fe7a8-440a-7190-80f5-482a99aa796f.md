## Notes

RECOVERED BY THE RE-SWEEP; the raw set had it only as a boolean field, size_extension_advertised, on SizeLimitConfigured — which is the merge error the brief warns about in reverse: a distinct implementation act flattened into an attribute of a different act. Two SHOULDs in one sentence with different subjects, server and client, plus a lowercase 'should be avoided' governing size restrictions generally. Violated arm, and it is the operationally interesting one: a server that imposes a size limit WITHOUT SIZE gives the client no way to learn it, so the rejection can only arrive after the whole message has been transmitted — the failure is invisible until the most expensive possible moment. Related: an extension registration can change wire limits at every server, per §2.2.2 567-569, which ties this to ServiceExtensionRegistered. Screens: HELO-only charter (no extensions at all), altitude tiers. FIELD HYGIENE: struck two fields. ehlo_keyword ('SIZE') is a constant the event name already carries — this event exists only for that one extension. declared_maximum_octets (10485760) had no source anywhere in RFC 5321, which defers the value to RFC 1870, and it duplicated SizeLimitConfigured's limit_octets, so it was both unsourceable and derived. server_host is kept, unlike on RelayFilteringCapabilityImplemented, because the subject of the SHOULD at line 3522 is 'SMTP server systems' rather than 'implementations' — a deployed system, which the greeting identifies by domain. No session, transaction or connection key was present; RFC 5321 supplies none.
