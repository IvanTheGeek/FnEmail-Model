# `NestedMailCommandRejected`

A MAIL command arrived while a transaction was already open on the session, which the client is forbidden to do.

## Data

**No data.** The method sanctions this: *"If an event has no meaningful payload beyond its identity (e.g., a simple state transition), it is fine to have no fields or just the identity key."* It also warns, of a different case, that *"An event without fields is an opaque label"* — both are recorded here rather than reconciled, because reconciling them is a later step's work, not Brain Storming's.

## Where RFC 5321 says so

| Section | Lines | Text |
|:--|:--|:--|
| §4.1.4 | 2507-2512 | *"MAIL (or SEND, SOML, or SAML) MUST NOT be sent if a mail transaction is already open, i.e., it should be sent only if no mail transaction had been started in the session, or if the previous one successfully concluded with a successful DATA command, or if the previous one was aborted, e.g., with a RSET or new EHLO."* |
| §3.3 | 1018-1020 | *"(In general, the MAIL command may be sent only when no mail transaction is in progress; see Section 4.1.4.)"* |
| §4.1.1.2 | 1885-1886 | *"In general, the MAIL command may be sent only when no mail transaction is in progress, see Section 4.1.4."* |

Line numbers are into [`docs/rfc/rfc5321.txt`](../../docs/rfc/rfc5321.txt), the archived copy. Quotations keep the specification's own words and spellings (AGENTS.md rule 2).

## Notes

RECOVERED BY THE RE-SWEEP. The rule is stated THREE times in the document (1018-1020, 1885-1886, 2507-2512) and the raw set carried it only as a citation inside MailTransactionStarted's supporting quotes — the honored arm was harvested, the violated arm was not. The MUST NOT is on the CLIENT; 2508-2512 then spells out the only three legal positions for a MAIL, which is the clearest statement in the document of the transaction lifecycle: never started, successfully concluded by DATA, or aborted. ⚠️ INFERENCE, FLAGGED: the RFC does not say what the server answers to a nested MAIL. 503 is taken from the out-of-order MUST at 2516-2528 and is this chapter's reading, not the RFC's instruction; §4.1.1.2 gives no code either. Rejected alternative names: MailCommandRejectedAsTransactionOpen, SecondMailCommandRefused. Related events: MailTransactionAborted (which makes a new MAIL legal again), MailTransactionConfirmed (likewise).

FIELD HYGIENE PASS: struck three fields, leaving the event FIELDLESS. session_id (f2C8D14) and open_transaction_id (f2C8D14-t1) both fail on key and on value: RFC 5321 names no session or transaction identifier — grep over docs/rfc/rfc5321.txt returns nothing — and f2C8D14 appears nowhere in the document, being this project's own minted queue-id example from commit 6acfc68. The absence bites hardest here of anywhere in the chapter, because this event's whole content is that a transaction was ALREADY OPEN, and the spec gives nothing to name it with: what identifies the open transaction is its position in the session, the one begun by the last MAIL and not yet confirmed or aborted, on a channel that is its own identity while it lives. 2507-2512 spells out the three legal positions for a MAIL and never once names a transaction. reply_code (503) struck as unsourced and as rendering both — the note above already flags it as this chapter's inference, since the RFC states no code for a nested MAIL anywhere. Fieldless is the correct and informative outcome: the event says a MAIL arrived out of position, and position is what the stream carries.
