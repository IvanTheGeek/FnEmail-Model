## Notes

RECOVERED BY THE RE-SWEEP, and explicitly requested by the raw set: RecipientBufferLimitReached's own notes say 'PreviouslyAcceptedRecipientsSilentlyDiscarded is a real, non-conforming state change that a hostile or buggy MTA produces. It was cut only for slot budget and should be restored; it is the clearest both-arms pair in the span.' Restored. VIOLATED ARM of a MUST. What makes it worth modeling is that it is SILENT — no reply carries it, the client believes those recipients are still accepted, and the only trace is a message that never arrives for people the client watched be accepted with a 250. That is a discrepancy no wire-derived model can see, which is precisely why the accepting event (RecipientBuffered) has to exist for this one to contradict. Deliberately near-fieldless beyond the discarded paths: there is no code, no text and no time the client can observe. Rejected alternative names: AcceptedRecipientsDroppedSilently, DisorderlyRecipientLimitApplied. Screens: the consumer test G1 kills it hardest — nothing in the drawn model consumes an event whose whole content is an absence.

FIELD HYGIENE PASS: struck one field, session_id (f2C8D14) — RFC 5321 supplies no session identifier and the value is this project's own minted queue-id example from commit 6acfc68, absent from the RFC; identity is the channel while the session lives, and the discarded paths themselves say which transaction lost them. discarded_forward_paths SURVIVES, and the distinction against TransactionBuffersCleared is the reason: there, everything in the buffer is discarded, so the contents are recoverable by folding this transaction's RecipientBuffered events and the field was struck as derived; here a SUBSET is silently dropped, and which subset is not derivable from anything — no reply carries it and the client is never told. That is the event's entire content.
