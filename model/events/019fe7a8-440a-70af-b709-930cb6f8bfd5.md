## Notes

Harvested, WITH A CITATION FIX. The sweep wrote that 554 was "an instantiation for walking, not a citation — §4.2 and §4.5, outside my span, are where the codes live". The re-sweep found them: §4.3.2 line 3115 lists 552, 554, 451, 452 as the DATA error set, so 554 is now cited, not guessed. Strength: MUST. Two facts a later step would otherwise re-derive: responsibility does NOT transfer, so the sending system still holds the message and must decide whether the code is permanent or transient; and the buffers are cleared either way (see MailDataBuffersCleared). The all-or-nothing rule is what makes forward_paths a List on the refusal exactly as on the acceptance. Opposite event: MessageAcceptedForProcessing. Narrower siblings kept separately because the RFC names their causes separately: MessageRejectedForIncompleteTransaction, MessageRejectedByPolicy, MessageRejectedForHeaderDefects, OversizedMessageDataRejected. Screens: none kills it, but if the model has one accept event and no reject event at this point, that asymmetry is itself a hotspot.

FIELD HYGIENE PASS: struck three of four. transaction_id is fabricated — and note what follows for a refusal specifically: no queue id is stamped either, because nothing was accepted and no trace line is written, so the refused message has no identity anywhere in RFC 5321. The forward paths are what identifies it, which is why forward_paths stays. reply_code is struck as a rendering — the re-sweep's citation fix stands and is preserved in the note above, but citing 554 as a real DATA-time code establishes what the server writes on the wire, not a fact it holds afterward, and RFC 5321 nowhere carries the code as data. rejecting_host is struck as a session-level fact fixed by the connection.
