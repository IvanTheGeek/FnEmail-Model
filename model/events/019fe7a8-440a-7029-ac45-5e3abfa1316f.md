# `FromClauseComposed`

The FROM clause of a trace line was built from two facts of different provenance at once — the name the client claimed in its EHLO/HELO greeting, and an address literal for the source IP that the server itself read off the TCP connection.

## Notes

RECOVERED BY THE RE-SWEEP — the chapter roster names 'FROM clause built from the claimed name *and* the connection's address' as a topic and no inherited candidate carried it as its own event; idx 193 buried it as two fields. It deserves separation because the two halves are epistemically different: one is a client assertion the server cannot check, the other is an observation the client never made, and the ABNF comment at 3325-3327 says so in the RFC's own words. A model that fuses them loses the only place in the protocol where a claim and a measurement are written side by side. Strength split inside one sentence: supplying the clause is MUST, its two-part content is only SHOULD — so a conforming server may stamp the claimed name alone (see TraceSourceNameStampedWithoutConnectionAddress). Siblings: FromClauseOmittedFromTrace (the MUST violated), TraceLinePrepended (the whole line). FnEmail screens: the 'one event per command' target, since this fires at stamping time with no command of its own, and the two-kinds capture/decision lens, which would want the claimed name filed as a capture and the observed address as something else. ⚠️ FIELD HYGIENE PASS: struck the fabricated `message_ref` identity key — RFC 5321 names no such key, and its example value f2C8D14 appears nowhere in the RFC. Identity here is positional and is not weakened by the loss: this event happens once, inside one session, at the moment that session's server composes its own FROM clause, so the channel is the identity while it lives. Both surviving fields are the RFC's own two halves at 3166-3168 and both are instantiated from the walk scene, which is the whole point of the event — bar.com is what the client said and 203.0.113.20 is what the server saw.
