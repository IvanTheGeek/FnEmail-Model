## Where RFC 5321 says so

| Section | Lines | Text |
|:--|:--|:--|
| §4.1.4 | 2453-2456 | *"An EHLO command MAY be issued by a client later in the session. If it is issued after the session begins and the EHLO command is acceptable to the SMTP server, the SMTP server MUST clear all buffers and reset the state exactly as if a RSET command had been issued."* |
| §4.1.4 | 2456-2459 | *"In other words, the sequence of RSET followed immediately by EHLO is redundant, but not harmful other than in the performance cost of executing unnecessary commands."* |

## Notes

Carried unmerged from the §4.1.1.x sweep. MAY for the client to issue it, MUST for the server to clear on acceptance — and it is paired with GreetingRejected in the sharpest way: acceptance clears, rejection does not. Three commands abort a transaction (RSET, a new greeting, QUIT) and this is the least obvious of them. §4.1.1.5 lines 2093-2095 say the formal semantics of RSET and a reissued greeting are THE SAME, which is the strongest argument in the spec for merging this into BufferCleared; kept apart because the identity is re-declared here and is not on RSET, and because the RFC itself keeps them in separate sections with different actors' intent. Lines 2456-2459 are a fact about a NON-event — RSET-then-EHLO is redundant but harmless — a good example of the spec describing something that changes nothing. Screens: the twelve-slice model has no mid-session re-greeting path, and the one-event-per-command target would fight one command producing both a reinitialization and a transaction abort. FIELD HYGIENE PASS: struck 2 fields. session_id struck — no such key in RFC 5321. discarded_transaction_id struck, and it was fabricated twice over: the RFC supplies no transaction identifier anywhere, and the value 'f2C8D14-t1' was built on this project's own minted queue-id example, which appears nowhere in the source. What identifies the discarded transaction is what was in the buffers at that moment — the reverse-path and the forward-paths, recorded by BufferCleared — so the transaction is named by its content, not by a key. new_claimed_domain survives because it is the only thing this event adds over a plain reset, and it is exactly the reason the event is kept apart from BufferCleared.
