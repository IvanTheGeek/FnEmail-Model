## Notes

Recovered by the re-sweep as the violated arm of a MUST NOT that no inherited candidate carried in either arm. "under any circumstances" (3683) is the most absolute wording in the whole retry subsection — stronger than a bare MUST NOT, with no discretion left anywhere. The honored arm is ErrorNotificationSuppressedToPreventLoop, carried by the §4.5.5 span in the bounce chapter, and this pair belongs cross-referenced. §4.5.5 3787-3795 supplies the mechanism that normally prevents this: notifications carry a null reverse-path, so there is nowhere to send the second error. Rejected name: BounceLoopGenerated. Screens: the condemned status register would object to a compliance verdict as an event; the consumer test G1 would take it too. ⚠️ FIELD HYGIENE PASS: STRUCK triggering_message_id and generated_message_id, both fabricated. f2C8D14 is a queue id and neither of these is a queue entry; a41F09B appears nowhere in RFC 5321 and is not even one of this project's minted values. RFC 5321 supplies no message identifier at all — §4.4's ID clause (rfc5321.txt:3336) admits an Atom or an RFC 5322 msg-id, but that is a receiving server's trace stamp, not a handle the spec gives a queuing strategy. That absence has a real consequence worth marking as a hotspot under rule 12: the pairing that makes this event a LOOP rather than a single send cannot be expressed in RFC 5321's own vocabulary, so the loop is visible only in the stream's ordering. What remains is sent_to, the address the forbidden second error reached, which is enough to say the MUST NOT was broken but not enough to say what it was broken in reply to.
