# `InconsistentMultilineReplyEmitted`

|:--|:--|:--|

## Notes

RECOVERED BY THE RE-SWEEP — the violated arm of the MUST at 2771-2772, which no inherited candidate carried. It matters more than most violations because the RFC explicitly licenses the client to trust the invariant ("It is reasonable for the client to rely on this"), so a client that meets this event has already acted on the wrong code by the time the inconsistency is visible. Strength: MUST on the server side; the client-side consequence is unstated, which is itself the finding — the spec gives no recovery procedure. Rejected alternative names: MultilineReplyCodeMismatchDetected (names the detection, not the state change), MalformedMultilineReplySent. Sibling, deliberately not merged: BareReplyCodeTolerated below is a different wire violation of the same reply — text omitted rather than code varied. Screens that would have killed it: the responsibility-boundary cutoff and the inbound-only scope, since FnEmail as a receiver emits replies and never parses them; this event is only observable from the client side.

FIELD HYGIENE PASS (chapter 14): session_id struck — RFC 5321 names no session, transaction or connection identifier, and f2C8D14 is nowhere in the RFC; identity here is the reply being read, at its position in the session. Both codes KEPT, and the lines that make them data are 2772-2774: "It is reasonable for the client to rely on this, so it can make processing decisions based on the code in any line" — the per-line code is a datum the RFC licenses the client to rely on, and the pair of differing codes IS the violated invariant rather than one decision rendered.
