## Data

**No data.** The method sanctions this: *"If an event has no meaningful payload beyond its identity (e.g., a simple state transition), it is fine to have no fields or just the identity key."* It also warns, of a different case, that *"An event without fields is an opaque label"* — both are recorded here rather than reconciled, because reconciling them is a later step's work, not Brain Storming's.

## Notes

RECOVERED BY THE RE-SWEEP — the sweeps noted the no-mail-data case inside EndOfMailDataIndicated's notes and never made it an event. It is an event boundary that says a zero-length message is not a message: the RFC does not forbid it with a MUST NOT, it declares it non-conforming, which is a third strength category worth naming because a conformance test written from 2119 keywords alone would miss it. The reason given is structural and is why the §2.3.9 citation is carried: content is header section plus body, and neither can be present if nothing was sent, so the trace header fields this specification requires would also be absent. Consequence the RFC leaves open: it never says what the receiver does — accept, or reject at end of data — so this is a hotspot, and the two arms are MessageContentStored and MessageRejectedAtEndOfData respectively. Screens: none kills it; the twelve-slice model simply has no representation for a message that is not there. Rejected alternative names: NoMailDataTransmitted, ZeroLengthContentSent.

FIELD HYGIENE PASS: struck both fields. transaction_id is fabricated — RFC 5321 supplies no transaction key; identity is the channel, and the event is fixed by position (the terminator arrived immediately after the 354). content_octets = 0 is struck twice over: it is a computed measurement, and its value is constant on every instance of this event, so it restates the event's own name. Fieldless is exactly right here — the whole content of the event is that there is no content.
