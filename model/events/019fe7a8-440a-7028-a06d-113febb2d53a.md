# `TraceLinePrepended`

A receiving SMTP server that had taken a message for relaying or final delivery put a Received: line at the very top of the mail data, recording who sent it, who took it, over what protocol, under what local id, and when.

## Notes

MERGE of four inherited candidates naming one state change: TraceLinePrepended (idx 193), TraceRecordInserted (idx 178), TraceHeaderFieldPrepended (idx 298) and TraceInformationAdded (idx 43); ReceivedHeaderFieldAddedByRelay (idx 79) folded in too. Rejected alternative names, kept so the naming research survives: TraceRecordInserted, TraceHeaderFieldPrepended, TraceInformationAdded, ReceivedHeaderFieldAddedByRelay, ReceivedHeaderPrepended. TraceLinePrepended wins because 'prepend' is the RFC's own MUST verb at 3180 and 'line' is the RFC's own noun ('time stamp line'). NOT merged with ReceivedLinePrependedByGateway: §3.7.2 states a separate MUST for an environment crossing and carries facts (direction, foreign environment) this event has no place for — a gateway's stamp is not a relay's, cross-referenced both ways. Strengths, which must not be flattened: inserting trace is MUST (3159); prepending, and never inserting elsewhere, is MUST twice (3180-3182); the FROM clause is MUST-supply but SHOULD-content (3165-3168, split out as FromClauseComposed); the '@' in the ID clause is MAY (3170-3171, formatting only, set aside). Eight fields looks like padding under the kit's warning but each is a distinct clause of the Stamp grammar at 3311-3341; Via and Additional-Registered-Clauses are deliberately left off and carried by ViaClauseRecorded and TraceClauseRegistered. Citation corrections to the inherited set: idx 178 cited 4.1.1.4 '2054-2057' for a phrase that ends on 2055, and idx 43 cited §2.3.10 '810-814' for a sentence whose quoted part ends on 813. Opposite events: ReceivedLineChainAltered, TraceLineInsertedOutOfPosition. FnEmail screens that would have killed it: the four altitude tiers (Protocol vs Domain), and it sits exactly on the responsibility-boundary cutoff; the inbound-only scope would keep it, since an inbound server stamps. ⚠️ FIELD HYGIENE PASS (this pass changed fields and notes only): struck the fabricated `message_ref` identity key. RFC 5321 supplies no message, session, transaction or connection identifier — grepping the archived text for 'session id', 'transaction id' and 'connection id' returns nothing — so what identifies this occurrence is the trace line itself: the FROM/BY pair plus the date-time, which is exactly what the Stamp production at 3311-3315 makes mandatory. The eight fields the note above defends are therefore seven, and the count argument stands unchanged because message_ref was never one of the Stamp clauses it was defending. `trace_id` SURVIVES and is the one legitimate home for f2C8D14 in this chapter: §4.4's ID clause is real and optional (rfc5321.txt:3336, `ID = CFWS "ID" FWS ( Atom / msg-id )`; Opt-info at 3329 makes it optional), and the walk's own stored trace line writes `id` f2C8D14 there. The value itself is still not in the RFC — not in the body, not in Appendix D — it is this project's minted queue id, and example_source now says so. Note the consequence for every other event in this chapter: an identifier exists only where a server chose to write an ID clause, so it is a fact of one hop's line, never a key the message carries between hops.
