## Notes

RECOVERED BY THE RE-SWEEP as the accepting arm of the MAY at 1284; the inherited set carried only the refusing arm inside CrossTypeVerificationRefused. Strength: MAY for the positive response, MAY for the error (1296) — both arms are permissive, so unlike the VRFY-on-a-list case the server has genuinely free choice here and neither answer can be called wrong. That symmetry is the reason to keep both arms as separate events rather than one event with an outcome field. Rejected alternative names: SingleNameExpanded, ExpnOnUserSucceeded, OneMemberListReturned. Sibling and mirror: MailingListVerifiedAsUser, the same fuzziness approached from the VRFY side; both exist only because 1276-1279 says one data structure holds lists and aliases together. Which screen would have killed it: 'one event per command', the guest-viewed-calendar test, the twelve-slice model. Note for a later step: from the wire this is indistinguishable from a genuine one-member list being expanded, so a model that needs to tell them apart needs the directory's kind flag, which the protocol never carries. FIELD HYGIENE PASS: struck reply_code (250). Wire rendering of the positive arm of the MAY at 1295-1297; that the answer was positive is already the event's name. Two fields survive, both quoted from D.4 at 5113-5114 and re-verified in this pass. No invented identity key was present; identity is the name asked about plus the channel, and note that the symmetry argument in the note above — both arms permissive, so keep them as separate events rather than one event with an outcome field — is strengthened rather than weakened by the strike, since the outcome field it warns against is exactly what a retained reply_code would have been.
