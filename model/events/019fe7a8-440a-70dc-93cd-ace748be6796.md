# `PendingTransactionCanceled`

After a premature connection loss the server discarded the transaction in progress while leaving every previously completed transaction in that session untouched.

## Data

**No data.** The method sanctions this: *"If an event has no meaningful payload beyond its identity (e.g., a simple state transition), it is fine to have no fields or just the identity key."* It also warns, of a different case, that *"An event without fields is an opaque label"* — both are recorded here rather than reconciled, because reconciling them is a later step's work, not Brain Storming's.

## Notes

This is the DURABILITY BOUNDARY of the whole protocol and the RFC states it in half a line. Kept separate from MailTransactionAborted on purpose: an abort is commanded, this is a failure — no RSET, no EHLO, no QUIT, nothing on the wire at all — and a timeout is not a QUIT. The MUST-NOT-undo half is as strong as the MUST-cancel half: a message already answered with 250 OK stays accepted even if the connection dies a second later, because responsibility transferred at that reply and nothing after it can claw it back. preserved_transaction_ids is genuinely a List and the rule only has meaning because a session may carry several transactions (2506-2507), so a single-transaction walk can never surface it — which is exactly what the twelve-slice model does, and the screen is named, not applied. The consumer test would also reject an event whose content is largely what did NOT happen. Rejected alternative names: TransactionAbandonedOnConnectionLoss, PendingTransactionDiscarded.

FIELD HYGIENE PASS: struck three fields, leaving the event FIELDLESS — and this is the event where the fabrication mattered most, because its entire content had been expressed through identifiers the specification does not supply. session_id (f2C8D14), canceled_transaction_id (f2C8D14-t2) and preserved_transaction_ids (f2C8D14-t1) all go: grep over docs/rfc/rfc5321.txt for session, transaction or connection identifiers returns nothing, and f2C8D14 appears nowhere in the RFC body or in Appendix D — it is this project's own minted queue-id example from commit 6acfc68. ⚠️ The note above says preserved_transaction_ids 'is genuinely a List and the rule only has meaning because a session may carry several transactions (2506-2507)'. The premise holds and the field does not: 2506-2507 makes many transactions per session explicit and names none of them, which is the finding. What carries the rule instead is the stream's own shape. The canceled transaction is the one opened by the last MAIL and not yet confirmed — position in the session, on a channel that was its identity until it broke. The preserved ones need no field at all: each was already confirmed by its own MailTransactionConfirmed event, and 'MUST not undo' is expressed by the ABSENCE of any compensating event after this one. An event whose content is largely what did not happen is exactly the shape the note predicted, and fieldless is what that shape looks like.
