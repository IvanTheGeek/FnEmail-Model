# `NullReversePathSet`

The reverse-path of a notification message was set to null, so that a failure in delivering the notification cannot itself generate another notification.

## Notes

Inherited from raw candidate NullReversePathSet and strengthened with the §4.4 and §4.5.5 citations. The strength is easy to misread and was checked twice: the TECHNIQUE is introduced permissively — "One way to prevent loops in error reporting" (1506) — but the very next sentence is a flat MUST scoped to notification messages (1508-1509), and §4.4 (3293-3294) and §6.1 (3972-3973) both restate it as MUST. So it is not optional in the way the framing suggests. Three separate paragraphs of the RFC mandate the same thing, which is why the union of refs matters. Rendering caution for whoever writes this up (project rule 5): MAIL FROM:\<> must stay inside a code span or the renderer eats the angle brackets, and MAIL FROM: is not MAIL FROM:\<> — the brackets are path syntax. Rejected alternative names: NotificationEnvelopeSenderEmptied, ReversePathNulled, LoopPreventionApplied. Sibling mechanism, kept separate on purpose: NotificationSuppressedToPreventLoop — the two are independent loop defenses, one structural (nowhere to send a bounce of a bounce) and one by rule (do not send one), and both exist because either alone can fail. Which screen would have killed it: the inbound-only scope; the twelve-slice model has no notification slice at all.
