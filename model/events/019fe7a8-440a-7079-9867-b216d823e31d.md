## Notes

Merged SessionFellBackToHelo (§2 sweep) and HeloFallbackPerformed (§4.1.1.1 sweep). Rejected alternative names: SessionFellBackToHelo, ClientFellBackToHelo, ExtendedGreetingRefused (which is the server-side trigger, a different actor and a different fact). Three strengths in one §2.2.1 paragraph that must not be conflated: servers MUST support EHLO; clients SHOULD prefer EHLO; both MUST support HELO as a fallback. So HELO is not deprecated — it is mandatory, and the FnEmail HELO-only charter is therefore modeling the fallback path as if it were the normal one, which is a scope choice and not a finding. Marked likely rather than certain because the RFC never writes the downgrade sequence out: it says EHLO to a non-extension server will generate an error response, and separately that older clients MAY use HELO. The composition is universal practice but not stated. Screens: the inbound-only scope (entirely client-side) and the HELO-only charter, which starts where this event ends. FIELD HYGIENE PASS: struck 4 fields, the heaviest strike in the chapter. session_id struck — no such key; identity is the channel plus the reissued claim. attempted_verb EHLO and fallback_verb HELO struck — the fallback runs in one direction only, so both values are constants the event name already carries. prior_reply_code 500 struck, and it was fabricated in a second way worth recording: §4.1.1.1 lines 1815-1817 says only that the server 'will generate an error response' and §3.2 lines 996-998 says a 'command not recognized' response, so RFC 5321 never names a code here at all — 500 was supplied by the sweep. claimed_domain survives as the one fact that varies and the thing actually reissued.
