# `TransactionStateDestroyedByDiagnosticCommand`

A server cleared its reverse-path, forward-path or mail data buffer when a VRFY, EXPN, HELP or NOOP arrived, destroying a transaction the diagnostic command was specified not to touch.

## Notes

RECOVERED BY THE RE-SWEEP. The same sentence appears four times in four consecutive sections, once per command in this chapter, and the inherited sweeps used it only as the reason to SET THESE COMMANDS ASIDE — the §4.1 set-aside pile cites it verbatim as the disqualifier for VRFY, EXPN, HELP and NOOP in turn. Read the other way, four repetitions of a no-effect guarantee describe a failure mode the RFC thought worth ruling out four times, and the violated arm is a real, destructive, observable event: an open transaction with a stored sender and two stored recipients is gone because the client asked a question. STRENGTH TRAP, VERIFIED IN THE FILE AND RECORDED SO NOBODY RESTATES IT FROM MEMORY: none of the four sentences contains an RFC 2119 keyword. They are flat declaratives — 'This command has no effect' — not MUST NOTs. Anyone tiering this event on normative strength must read the sentences, not search for keywords, and this is the same trap the §4.1 sweep's span notes flagged for §4.1.1.11 and §4.1.5. Marked doubtful because the RFC never contemplates the violation, names no reply code for it, and gives no example. Rejected alternative names: BuffersClearedByNonTransactionCommand, TransactionLostToDiagnosticCommand, NoEffectGuaranteeBroken. Sibling in the honored direction, deliberately not modeled: the buffers surviving is an anti-event. Which screen would have killed it: all of them — the consumer test, the capture/decision lens, 'one event per command', the twelve-slice model, and the HELO-only charter. FIELD HYGIENE PASS: struck session_id (f2C8D14). What identifies this occurrence is not a session key the RFC never defines but the transaction's own buffers — the reverse-path and forward-path that the four sentences at 2114, 2143, 2157 and 2197 promise are untouched — and the reverse-path is the nearest thing to a transaction handle RFC 5321 supplies. The spec has no transaction identifier at all, verified by grep, and that absence matters more on this record than anywhere else in the chapter, because the event is precisely about a transaction being destroyed and the model has no name for the thing destroyed except the paths it held. A fabricated session_id papered over exactly that. The three surviving fields are the walk scene's own sender and recipients, which the RFC also uses at lines 4893-4899. No reply code was present. Left doubtful.
