## Notes

RECOVERED BY THE RE-SWEEP. §7.6 has two distinct disclosures and the inherited set carried neither as an event — idx 298 mentioned the LAN leak in a note and moved on. This is the rarer kind of event: harm produced by *conformance*, not by violation. The RFC says so explicitly at 4323 ('produced in conformance with this specification'), and its only remedy is a lowercase 'should be aware of it' addressed to site operators, not to implementers — so there is no protocol act that prevents it and no event that closes it. That absence is a 🟥 under rule 12. Sibling: BlindCopyRecipientDisclosedInTraceField, the other half of §7.6. Opposite: none stated; the spec offers no sanitizing or name-suppressing behavior anywhere, and a modeler should not infer one. Real data per rule 8: 192.0.2.10 is the project's standing internal-side address, and giving the host a plausible internal name makes the leak legible in a way that a placeholder cannot. FnEmail screens: all four altitude tiers (this is a site-operations concern), the consumer test, and the inbound-only scope — the disclosing server is upstream. ⚠️ FIELD HYGIENE PASS: struck the fabricated `message_ref` identity key — RFC 5321 names none and f2C8D14 is not in the RFC. The disclosed host and address are what identify this occurrence, which is as it should be: the leak is about the host, not about the message that carried it. Sourcing is now stated plainly and is honestly split — 192.0.2.10 is the walk scene's server address, but mail1.internal.foo.com is invented; the RFC names no host inside a LAN anywhere, which is itself consistent with §7.6 describing a situation rather than a syntax.
