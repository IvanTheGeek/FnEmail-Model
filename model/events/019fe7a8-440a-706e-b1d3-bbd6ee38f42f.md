## Notes

Merged from inherited candidates 49 (MailCollectedFromUser) and 305 (MessageHandedFromUserAgentToMta), which named the collection and the handoff from §2.3.3's single sentence. Rejected alternative names: MailCollectedFromUser, MessageSubmittedToMta, MessageAcceptedFromUserAgent. The merge is deliberate and reversible: 'collect mail to be transmitted from a user and hand it off to an MTA' is one clause with two acts, and a facilitator who wants MailCollectedFromUser as a separate upstream event should cite lines 663-664 alone. Kept in this chapter because it is a responsibility handoff in a §2.3.3 anchor, and because it is the first of the four handoffs the whole chapter is about — UA to MTA, client to server, MTA to store, store to UA. ⚠️ The RFC twice declines to specify the interface (§2.1 367-370 and Appendix B 4725-4726, 'the MTA-UA protocol is a private matter'), which makes this a 🟥 rather than an absence, and §2.3.3 668-671 explicitly warns that the MUA/MTA boundary is fuzzy in practice — do not treat this event as a crisp system boundary. envelope_supplied is the branch that governs Appendix B's whole generation procedure. Screens: inbound-only scope and the responsibility-boundary cutoff. ⚠️ FIELD HYGIENE PASS 2026-08-09 — two fields struck. message_id: RFC 5321 supplies no message identifier, and on this event the spec is doubly silent — §4.4's ID clause (line 3336) is optional and belongs to a receiver's Received: stamp, msg-id is RFC 5322's, and §2.1 367-370 plus Appendix B 4725-4726 put the whole UA-to-MTA interface outside the document. f2C8D14 is this project's minted queue_id value from commit 6acfc68.
