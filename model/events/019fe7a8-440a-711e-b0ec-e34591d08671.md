## Where RFC 5321 says so

| Section | Lines | Text |
|:--|:--|:--|
| §3.7.4 | 1612-1617 | *"The translation algorithm used to convert mail from the Internet protocols to another environment's protocol SHOULD ensure that error messages from the foreign mail environment are delivered to the reverse-path from the SMTP envelope, not to an address in the "From:", "Sender:", or similar header fields of the message."* |
| §4.4 | 3258-3260 | *"The reverse-path address (as copied into the Return-path) MUST be used as the target of any mail containing delivery error messages."* |

## Notes

RECOVERED BY THE RE-SWEEP. The capped sweep recorded it in EnvelopeReturnPathSetAtGateway's notes with the words "Recorded here so it is not lost; it deserves its own card if the gateway timeline is ever modeled properly" — this is that card. It is NOT the same state change as EnvelopeReturnPathSetAtGateway: that one sets an envelope field on the way IN, this one routes an error on the way OUT, in the opposite direction across the same boundary, and the two can occur independently. Strength: SHOULD at 1613 — but §4.4 lines 3258-3260 states the same target as a MUST for delivery error messages generally, so the chapter contains both strengths for what is arguably one obligation; do not average them, cite whichever governs the direction being modeled. This is the envelope-versus-header distinction docs/smtp-path-vs-mailbox.md rests on, stated as an error-routing rule. Opposite event: ForeignErrorRoutedToHeaderOriginator. Rejected alternative names: ForeignErrorReturnedToEnvelopeSender, TranslationErrorRoutingHonored. Which project screen would have killed it: inbound-only scope, responsibility-boundary cutoff.

FIELD HYGIENE PASS: struck message_ref (example f2C8D14) — RFC 5321 supplies no message identifier; here the envelope reverse-path is the identity that matters, which is the whole point of the event. ⚠️ CORRECTED an inverted value: error_destination is typed ReversePath and read \<Jones@foo.com>, but Jones@foo.com is the walk scene's RECIPIENT (forward-path) and Smith@bar.com the sender. Routing an outbound error to the recipient is the opposite of what §3.7.4 lines 1613-1615 requires, so the example contradicted the event it was illustrating. Swapped to \<Smith@bar.com>. This is the second inversion of the same kind in the chapter — see EnvelopeFoldedIntoHeaderSection — and both were invisible until example_source forced the question of where the value came from.
