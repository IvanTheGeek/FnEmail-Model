# `PartialFailureSignaledInDataReply`

## Notes

RECOVERED BY THE RE-SWEEP. The violated arm of the MUST at §4.4 3280-3281 — no inherited candidate carried it, because every sweep that reached this paragraph spent its slots on the honored arm (DeliveryResponsibilityAccepted) and the notification that follows. It is not hypothetical: §3.3 1144-1150 describes servers that defer recipient verification past DATA and then answer 550, and the RFC records the exact damage — the client cannot tell which recipients failed. So the spec both forbids the behavior and documents it happening, which is why this belongs on the wall in Step 1 rather than in an appendix. Sibling in the honored direction is ResponsibilityForMessageAccepted; sibling in the correct-handling direction is UndeliverableMailNotificationSent. Confidence 'likely' rather than 'certain' only because the RFC never names the violation as an occurrence, it names the rule. Screens: the condemned status/phase register and the capture/decision lens would both refuse a violation event; G1 would ask who consumes it, and the answer is the interoperability record, not a slice. ⚠️ FIELD HYGIENE PASS 2026-08-09 — two fields struck. transaction_id: RFC 5321 names no transaction key and f2C8D14-1 is this project's minted value; identity here is the two recipient lists themselves, and the RFC's whole complaint at §3.3 1148-1150 is that the failure reply does NOT carry them — the client 'cannot determine which recipients failed', so the split lists are the fact this event exists to record. reply_code 550: struck as the rendering of the decision, per §4.2 line 758. Recorded so it is not re-derived: §3.3 line 1148 names 550 specifically, in quotation marks and with '(or equivalent)' attached, so a later step that wants the code back has exactly one line to cite and must carry the '(or equivalent)' with it.
