# `SourceRoutedReversePathSent`

A sending system put a list of hosts in front of the sender mailbox in MAIL FROM, which contemporary systems are told not to do.

## Notes

RECOVERED BY THE RE-SWEEP: the VIOLATED ARM of the SHOULD NOT at 1048-1049. The eleven sweeps found source routing only on the FORWARD-path side and only from the receiving server's point of view — SourceRouteIgnored, SourceRouteStripped, SourceRoutedAddressRefused — and the reverse-path twin was named in one candidate's notes as belonging to 'the ORIGINATING system, which the inbound-only scope has no place for'. That is the screen, named, and not applied: a receiving server that never records what it was SENT cannot show that it was sent something deprecated. §4.1.1.2 upgrades the wording from SHOULD NOT to 'now deprecated', which is a second, non-2119 statement of the same thing. Sibling on the other buffer: SourceRoutedForwardPathGenerated. Rejected alternative names: DeprecatedReversePathSourceRouteUsed, SourceRoutedSenderDeclared.

FIELD HYGIENE PASS: struck one field, sending_host (bar.com). MAIL carries no host argument; the sending system's identity on this session comes from the connection itself and from whatever it claimed in EHLO, so the channel carries it and a copy on the event is padding. The RFC attaches no host to a MAIL command anywhere. reverse_path survives as the event's whole content — the deprecated at-domain list in front of the mailbox — but its example is now labeled honestly: relay.bar.com is invented, so the string is illustrative even though the FORM comes straight from the RFC's own source-route example at 1944. RFC 5321's own reverse-path in that example is \<userx@y.foo.org> (1943), which a later step could substitute for a fully sourced value; the substitution is flagged, not taken, because this pass does not rewrite values.
