## Where RFC 5321 says so

| Section | Lines | Text |
|:--|:--|:--|
| §4.1.1.3 | 1923-1925 | *"The forward-path normally consists of the required destination mailbox. Sending systems SHOULD NOT generate the optional list of hosts known as a source route."* |
| §3.3 | 1077-1080 | *"Historically, the \<forward-path> was permitted to contain a source routing list of hosts and the destination mailbox; however, contemporary SMTP clients SHOULD NOT utilize source routes (see Appendix C)."* |
| §3.6.1 | 1427-1428 | *"SMTP clients SHOULD NOT generate explicit source routes except under unusual circumstances."* |

## Notes

RECOVERED BY THE RE-SWEEP: the VIOLATED ARM of a SHOULD NOT stated three separate times (1923-1925, 1077-1080, 1427-1428) and never harvested as an event by any of the eleven sweeps, which saw only what the receiving server does about it afterwards. Every honored/violated pair in this chapter came out the same way — the server's arm was captured and the client's arm was dropped. Note the escape hatch at 1428, 'except under unusual circumstances', which means generating one is not automatically non-conforming; the raw set has an ExplicitSourceRouteGenerated candidate in the relaying chapter covering that legitimate case, and the two should be reconciled by whoever owns relaying rather than merged blind. Sibling on the other buffer: SourceRoutedReversePathSent. Consequences: SourceRouteStripped, SourceRoutedAddressRefused, RecipientRejectedForPolicy. Screens: inbound-only scope (client actor).

FIELD HYGIENE PASS: struck one field, sending_host (bar.com).
