## Notes

RECOVERED BY THE RE-SWEEP. Named as a sibling in the inherited NotificationSuppressedForNullReturnPath notes ('NullAddressEventLoggedLocally is a sibling the RFC declines to forbid but never names') and given no row by any sweep. It deserves one: this is the single place in RFC 5321 where the spec explicitly acknowledges that a site may want an event of its own for something the protocol deliberately makes invisible. In Event Modeling terms the RFC is conceding that a suppressed bounce still leaves a fact worth recording — which is exactly the argument for putting suppression on the wall at all. Strength: permission by non-prohibition, the weakest form in the document, and phrased as 'nothing in this section can or should prohibit' rather than as a MAY. stream_root is Server Configuration because the decision to log is the site's policy, not the message's business; a facilitator who prefers a dedicated Operator Log root should say so and invent it. Screens: every one of them — this is outside the protocol by the RFC's own framing. ⚠️ FIELD HYGIENE PASS 2026-08-09 — two fields struck. original_message_id: RFC 5321 supplies no message identifier — §4.4's ID clause (line 3336) is optional and is the receiver's own trace clause, msg-id is RFC 5322's — and f2C8D14 is this project's minted queue_id value from commit 6acfc68. There is an irony worth recording rather than smoothing over: a local log is the one place where a real implementation certainly DOES have an identifier of its own, precisely because the RFC leaves the local environment unspecified, so the invented field was right about implementations and wrong about the spec. Identity as the RFC has it is the site doing the logging and the recipient whose failure went unreported. logged_at: struck as the event's own occurrence time.

COLLISION RESOLVED — merged from 2 independently brainstormed records. Both records rest on the same sentence, §6.1 3984-3987, and the same actor — a receiving site logging inside the receiver-SMTP's own environment. The divergence was stream root and field hygiene, not state change; the root question is settled by observing that the event is an instance of logging, while the decision to log is a separate configuration fact.

From the duplicate in 12. Non-Delivery Notification: RECOVERED BY THE RE-SWEEP. The raw candidate NotificationSuppressedForNullReturnPath named this sibling in its notes but gave it no slot — a direct casualty of the 32-event cap. It is worth a slot because it is the only place in the whole chapter where the specification explicitly declines to forbid a site from keeping its own record of something the protocol makes invisible, and it is therefore the RFC's own sanction for exactly the kind of event this exercise is generating. Strength: no RFC 2119 keyword at all, and doubly hedged — "can or should" not prohibit, "if that is desired". It is a permission to record, not a requirement to. Confidence is likely rather than certain because the RFC names the act only to say it is not banned, and never says it happens. Scope is tightly drawn and must not be widened: "locally", "as part of the same system environment as the receiver-SMTP" — transmitting the information off-site would be the very notification 3983-3984 forbids. Rejected alternative names: NullPathFailureRecorded, SuppressedNotificationLogged, LocalNullAddressRecordKept. Which screens would have killed it: the four altitude tiers (logging is not Protocol tier), the consumer test (G1), and the responsibility-boundary cutoff.
