# `ResponsibilityForMessageAccepted`

The server issued a success reply to the end-of-mail-data indication and thereby took over the duty to deliver the message or properly report the failure; the client is discharged.

## Notes

THE event of this chapter, and the RFC states it five times in five sections. Merged from six inherited candidates: ResponsibilityForMessageAccepted (span §1-2.4), ResponsibilityForMessageAssumed (§4.1), MessageAcceptedForProcessing (§3.3), DeliveryResponsibilityAccepted (three separate sweeps: §4.2.5, §4.4, §6.1), MessageAcceptedForFurtherProcessing (§4.4). Rejected alternative names, all recorded so the naming research is not lost: ResponsibilityForMessageAssumed, DeliveryResponsibilityAccepted, MessageAcceptedForProcessing, MessageAcceptedForFurtherProcessing, MessageAccepted, CustodyTransferred. Strength: MUST for the OK reply (§4.1.1.4 2040-2041, 'If the processing is successful, the receiver MUST send an OK reply.'); §2.1 424 calls the resulting obligation a protocol requirement. Instant is pinned: the success reply at end of mail data, not DATA acceptance and not the last RCPT. forward_paths is a List because §4.1.1.4 2042-2043 forbids partial failure in this reply — one 250 covers every recipient, so a per-recipient success event here would misrepresent the protocol. The disposition field preserves the distinction §4.4 3158-3159 draws ('for delivery or further processing') and the inherited MessageAcceptedForFurtherProcessing existed only to carry: it is what later decides whether a Return-path line is inserted (3204-3206) or the return path is stripped and rebuilt (3229-3231). Kept as a field rather than as two sibling events; a facilitator who wants MessageAcceptedForDelivery / MessageAcceptedForFurtherProcessing as siblings should split on it. ⚠️ Inherited citation corrected: candidate 38 gave the §2.1 handoff quote as lines 420-424; the sentence 'once the server has issued a success response ... occurs' ends at line 421 and 422-424 is the separate MUST clause, so the refs are split here. Screens that would have killed it: none — but the FnEmail responsibility-boundary cutoff is drawn exactly ON this event, so everything the obligation entails falls outside the model by construction rather than by evidence. The 'one event per command' target would fuse it with the DATA reply and lose the custody fact. ⚠️ FIELD HYGIENE PASS 2026-08-09 — three fields struck. transaction_id: RFC 5321 names no session, transaction or connection key (the grep over docs/rfc/rfc5321.txt returns nothing), and its example f2C8D14-1 is this project's own minted queue_id value from commit 6acfc68, absent from the RFC body and from Appendix D. Identity here is position in the session — there is exactly one success reply to the end-of-mail-data indication per transaction — plus the envelope that reply covers, which is why reverse_path and forward_paths stay: with no key supplied, the paths ARE the key. reply_code 250: struck as the rendering of a decision the event name already states; §4.2 line 758 ('The codes are for use by programs and the text is usually intended for human users') makes the code the wire form, and nothing in RFC 5321 carries it as data past the reply. accepted_at: struck as the event's own occurrence time, which the timeline carries and the payload does not. accepting_server survives because §4.4's trace stamp records the acting host as data — From-domain at line 3317, By-domain at 3319.
