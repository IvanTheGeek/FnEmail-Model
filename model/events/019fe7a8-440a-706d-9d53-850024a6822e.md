## Notes

Inherited candidate 51, kept in this chapter because §2.3.10 is one of its anchors and because it is the exact mirror of FinalDeliveryMade: one event is the message entering the transport environment, the other is it leaving. Drawn as a pair they bracket everything else in the model, which is what makes them worth keeping together even though a submission or origination chapter has an equal claim — flagged here so the roster can resolve the overlap rather than lose it. The four system types §2.3.10 names (originating, delivery, relay, gateway) are ROLES a host plays for a given message, not fixed properties: the same host can be all four across different messages, and a model that treats them as host attributes will get this wrong. transport_environment carries real alternatives — the public Internet, a firewalled intranet, a non-TCP LAN or WAN — not decoration. Screens: inbound-only scope. ⚠️ FIELD HYGIENE PASS 2026-08-09 — two fields struck. message_id: RFC 5321 supplies no message identifier — §4.4's ID clause (line 3336) is optional and is a receiver's trace clause, msg-id is RFC 5322's — and f2C8D14 is this project's minted queue_id value from commit 6acfc68. The absence is at its most pointed on this event, because if any moment could mint a message identity it is this one, the message's first entry into transport, and RFC 5321 says nothing about it: identity here is the originating system and the environment it introduced the message into, nothing more. introduced_at: struck as the event's own occurrence time. transport_environment now carries the RFC's own value at line 246, where §1.1 lists the public Internet, a firewall-isolated TCP/IP Intranet, and other LAN or WAN environments using a non-TCP transport.
