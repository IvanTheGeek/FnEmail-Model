## Notes

MAY, against the paired MUST at 3598-3600. The RFC draws the distinction itself at 3603-3605 — PROHIBITING messages above a size versus merely LIMITING one transaction — and those are different intents with different consequences downstream. site_policy_max_recipients is a stated configuration value, not a computed one; the example uses 500 to stay conforming, because any configured value below 100 makes the configuration itself a stated violation (3537-3539) — see RecipientRejectedBelowMandatoryMinimum. The configuring act is a precondition event rooted in Server Configuration, held over from this chapter (the raw set has RecipientLimitConfigured). Killed by: the condemned status/config register, the altitude tiers, and inbound-only scope.

FIELD HYGIENE PASS: struck two fields. session_id (f2C8D14) goes on both counts — RFC 5321 names no session identifier and the value is this project's own minted queue-id example from commit 6acfc68, absent from the RFC; identity is the channel while the session lives, and this refusal is placed by the RCPT it answers. reply_code (550) goes as the wire rendering of a decision, and its example was a narrowing besides: the RFC says 5yz at 3601-3603, so 550 was the model's pick from a class. site_policy_max_recipients SURVIVES — it is a stated configuration value rather than a computed one, exactly as the note argues, and it is the fact that makes this refusal a policy refusal rather than capacity exhaustion — but its example is now labeled plainly: the RFC establishes that such a limit may exist and never names a number, so 500 is illustrative. Flagged for a later step: the field duplicates state set by a Server Configuration event (the raw set's RecipientLimitConfigured), and whether an event may carry a snapshot of configuration is a question this pass does not decide.

COLLISION RESOLVED — merged from 2 independently brainstormed records. Same section, same MAY, same actor, same stream root, same single surviving identity field. The disagreement is one field and one example value, and both are resolvable against the source: the limit belongs to the configuration event, and Smith@bar.com is a sender.

From the duplicate in 14. Protocol Fault Handling: Inherited from candidate 327; citations re-checked and correct. The pair with RecipientBufferLimitReached is the clearest lifetime distinction in the chapter and the two must not be collapsed into one event with a code field: the difference is invisible to the client except through the first digit, and the client's entire retry decision depends on it. The distinction is also a statement about intent that only the server knows — "if the intent is to prohibit messages with more than a site-specified number of recipients, rather than merely limit the number" — so the choice of code encodes a policy the wire cannot otherwise carry. Strength: MAY. The example uses 500 recipients rather than a small number because any configured site limit below 100 makes the configuration itself non-conforming under 3538-3539, and a placeholder value would have hidden that constraint.

FIELD HYGIENE PASS (chapter 14): three fields struck. session_id struck — RFC 5321 names no session, transaction or connection identifier, and f2C8D14 is nowhere in the RFC; identity here is the transaction plus the forward-path. site_policy_max_recipients struck: the configured limit is RecipientLimitConfigured's fact and is recorded there, sourced to lines 3601-3603, and the inherited note's point about a limit below 100 being non-conforming now attaches to the configuration event, which is where it always belonged. reply_code struck for the same reason — which 5yz this server sends is a configured choice, and the configuration event is where it lives; carrying it again here is a lookup, not a capture. The lifetime distinction from RecipientBufferLimitReached therefore now rests on the two events' names and on limit_kind at configuration time, not on a code field, and the two must still never be merged. rejected_forward_path KEPT.
