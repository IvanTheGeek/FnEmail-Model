# `MessageGatewayedFromHeaderFieldsAlone`

A gateway built an SMTP envelope for a foreign message out of nothing but its To: and Cc: header fields, which the specification forbids.

## Where RFC 5321 says so

| Section | Lines | Text |
|:--|:--|:--|
| §B | 4773-4777 | *"A submission protocol based on Standard RFC 822 information alone MUST NOT be used to gateway a message from a foreign (non-SMTP) mail system into an SMTP environment. Additional information to construct an envelope must come from some source in the other environment, whether supplemental header fields or the foreign system's envelope."* |
| §B | 4779-4784 | *"Attempts to gateway messages using only their header "To" and "Cc" fields have repeatedly caused mail loops and other behavior adverse to the proper functioning of the Internet mail environment. These problems have been especially common when the message originates from an Internet mailing list and is distributed into the foreign environment using envelope information."* |

Line numbers are into [`docs/rfc/rfc5321.txt`](../../docs/rfc/rfc5321.txt), the archived copy. Quotations keep the specification's own words and spellings (AGENTS.md rule 2).

## Notes

RECOVERED BY THE RE-SWEEP: the violated arm of the MUST NOT at 4773-4775. The capped sweep folded the whole failure into MessageGatewayedFromForeignMailSystem's envelope_source field and named the loop case in notes; splitting it out matters because the RFC does not merely forbid this — it reports that the violation "repeatedly caused mail loops" in practice (line 4780), which makes it an observed behavior of real systems, not a hypothetical. The mailing-list origin is the aggravating case and is named at 4782-4784. This is the direct cause of MessageRemailedIntoOriginatingEnvironment, which is kept separate because a bad envelope and a completed loop are different facts separated in time — possibly by many hops. Rejected alternative names: HeaderOnlyEnvelopeConstructed, ToAndCcUsedAsEnvelope. Which project screen would have killed it: inbound-only scope, altitude tiers, responsibility-boundary cutoff.

FIELD HYGIENE PASS: struck message_ref (example f2C8D14) — no message identifier in RFC 5321; the derived paths and the header fields they came from are what identify and condemn this construction. ⚠️ CORRECTED derived_forward_paths, which read \<Smith@bar.com>: that is the walk scene's SENDER, and a forward-path derived from a To: header is a recipient. Set to \<Jones@foo.com>, the walk scene's recipient, which is also the address a To: header would actually carry. Third inversion of this kind in the chapter. derived_from_header_fields verified at line 4779: the RFC's own words are header "To" and "Cc" fields.
