## Notes

CITATION FIX: the inherited candidate cited lines 1972-1975 for the MAY-reject sentence, which actually runs 1973-1975; line 1972 is a different sentence and is cited separately here. Verified by opening §4.1.1.3 (rule 3). MAY, not MUST or SHOULD — the refusal is discretionary, and the RFC parenthesizes the ground as a policy reason, which means a POLICY EXISTS: a precondition event with an administrator as actor, rooted in Server Configuration, outside this chapter. Example values are the RFC's own from lines 1943-1956, so they are real by construction. The 550-at-RCPT case is the clean counterexample to any assumption that policy rejections happen at DATA. Kept distinct from RelayingDeclined, which is the same shape from §3.3 with a different sentence behind it and no stated code — cross-referenced, not merged. Screens: the inbound-only scope keeps the event but hides its cause; the responsibility-boundary cutoff treats relay policy as somebody else's concern.

FIELD HYGIENE PASS: struck three fields. session_id (f2C8D14) goes because RFC 5321 supplies no session identifier and the value is this project's own minted queue-id example from commit 6acfc68, absent from the RFC; the channel is the session's identity while it lives, and this refusal is placed by the RCPT it answers. reply_code (550) goes as the wire rendering of a decision even though 1973-1975 states it — the sentence tells a server which code to put on the wire for a policy refusal, and the policy refusal is what the event's name already says. rejecting_host (xyz.com) goes as ambient: the rejecting host is the server recording the event, so its identity is the connection it is answering on, not a payload field; xyz.com is genuinely the RFC's relay at 1940, which is why the value looked sourced while the field was still padding. forward_path survives with a value taken verbatim from the RFC's own envelope at 1944.
