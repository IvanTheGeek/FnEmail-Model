## Notes

Recovered by the re-sweep as the violated arm of the batching SHOULD; the honored arm is RecipientsGroupedIntoSingleTransaction and no sweep carried the other side. The RFC prints the non-conforming sequence in full at 3763-3764, which makes this the rare violation the spec renders literally. Only a SHOULD, so an implementation doing this is imperfect rather than broken — worth stating, because a model that treats every violated arm as an error overstates the spec. Note it is also what a client MUST fall back to when destinations differ, so the event is not always a violation: same shape, different cause, and the destination_server field is what distinguishes them. Rejected name: MessageTransmittedOncePerRecipient. Screens: inbound-only scope, condemned status register. ⚠️ FIELD HYGIENE PASS: NOTHING STRUCK. destination_server carries real work here rather than repeating the queue entry's destination — the notes above make it the field that tells a violation from a legitimate fallback — and forward_paths is the set that was NOT grouped. Unlike DestinationRetriedWithoutDelay, whose distinguishing field was computed and had to go, this one's distinguishing field is an observed domain, so the event survives the pass intact. No transaction identifier appears and none could: RFC 5321 supplies none, and each transaction here is identified by its own MAIL-to-DATA span on the channel. queue_entry_id kept on §4.4's ID-clause ground (rfc5321.txt:3336); f2C8D14 is this project's minted value, not the RFC's.
