# `HeaderAddressTransformedForInternet`

A gateway transformed the addresses in a message's From:, To: and Cc: header fields so they satisfy Internet mail syntax, use fully-qualified domain names, and can actually be replied to.

## Where RFC 5321 says so

| Section | Lines | Text |
|:--|:--|:--|
| §3.7.4 | 1606-1608 | *"The gateway MUST ensure that all header fields of a message that it forwards into the Internet mail environment meet the requirements for Internet mail."* |
| §3.7.4 | 1608-1612 | *"In particular, all addresses in "From:", "To:", "Cc:", etc., header fields MUST be transformed (if necessary) to satisfy the standard header syntax of RFC 5322 [4], MUST reference only fully-qualified domain names, and MUST be effective and useful for sending replies."* |
| §3.7.3 | 1598-1600 | *"Addresses and header fields generated by gateways MUST conform to applicable standards (including this one and RFC 5322 [4])."* |

## Notes

Three MUSTs on one act, and the third is the strangest requirement in the chapter: addresses "MUST be effective and useful for sending replies" (lines 1611-1612) — a semantic obligation no syntax check can verify and that a gateway generally cannot establish. That is a 🟥 HOTSPOT, not a rule, and it should be marked as one on the wall. §3.7.3's generation rule at 1598-1600 is folded in as a third reference rather than raised as a near-identical GatewayAddressGenerated — that alternative name is recorded here so it is not re-derived. Other rejected alternative names: GatewayHeaderAddressesQualified, HeaderAddressesMadeRfc5322Conformant. The conservative-generation half of the Postel pair whose liberal-acceptance half is NonstandardAddressFormatAccepted. Opposite event: NonconformingHeaderAddressForwardedIntoInternet. Which project screen would have killed it: inbound-only scope, responsibility-boundary cutoff.
