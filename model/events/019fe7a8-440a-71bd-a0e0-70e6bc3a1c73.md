# `ReplyIssued`

## Data

**No data.** The method sanctions this: *"If an event has no meaningful payload beyond its identity (e.g., a simple state transition), it is fine to have no fields or just the identity key."* It also warns, of a different case, that *"An event without fields is an opaque label"* — both are recorded here rather than reconciled, because reconciling them is a later step's work, not Brain Storming's.

## Notes

Inherited from candidate 224 (span §4.2-4.3); its citation of 2551 and 2606-2608 checked and correct, except that the SHOULD sentence ends at 2607 not 2608, so the range is tightened here. Strength: MUST for exactly-one-reply — the strongest invariant in the whole chapter, and what makes every refusal below a recordable fact rather than a rendering of server state; SHOULD for staying inside the documented code list. Both violated arms are real and neither is given its own row: a command that draws NO reply (the client's timeout chapter picks that up as CommandTimeoutExpired, raw candidate 334) and a command that draws TWO. MERGED IN by the re-sweep: MachineReadableReplyTextInterpreted, from lines 2563-2565 — 220, 221, 251, 421 and 551 carry text a machine must parse, which is the standing exception to "An SMTP client MUST determine its actions only by the reply code, not by the text" (2610-2612); the 251/551 arm of that parse is the forwarding chapter's (raw candidates 3, 4, 7, 296) and only the parsing act itself is recorded here. Rejected alternative names from the merge: CommandAnswered, ReplySent, ReplyEmitted. Screens that would have killed it: the "one event per command" design target, which fuses the reply into the command's own outcome event, and the capture/decision two-kinds lens, which calls a reply a decision output rather than a capture.

FIELD HYGIENE PASS (chapter 14): all four fields struck; the event is now fieldless, and it is the only fieldless event in this chapter. session_id goes because RFC 5321 names no session, transaction or connection identifier anywhere — the grep for those three phrases over docs/rfc/rfc5321.txt returns nothing — and its value f2C8D14 appears nowhere in the RFC either; it is this project's own minted queue id. While a session lives the channel is its identity, and the only place the RFC writes that identity down is the TCP-info clause of section 4.4 at line 3325, "Information derived by server from TCP connection". reply_code and reply_text go as the rendering of a decision: lines 2557-2559 say the number "is for use by automata to determine what state to enter next; the text is for the human user", so the RFC itself classifies the text as not-data, and on the emitting side the code is the server's decision written onto the wire — the specific outcome events in this chapter carry what the reply meant. command_verb goes because section 4.3.1 lines 2993-2996 make the dialogue alternating, so the reply's subject is fixed by position: the verb is a positional lookup, not a captured fact. What survives is exactly what the MUST at 2551 is about — that one reply, and only one, happened for this command. Identity here is position in the session.
