## Notes

RECOVERED BY THE RE-SWEEP — no inherited candidate carried the chapter's own entry event. Strength: the sentence is a MUST but the MUST is on the lookup; the identification itself is stated as an accomplished past fact ('Once an SMTP client lexically identifies'), which is exactly the shape Step 1 wants. 'Lexically' is load-bearing: no DNS has happened yet, so this event can carry a name that will turn out not to exist. Rejected alternative names: DeliveryDomainExtracted, DestinationDomainDetermined (the latter reads as a resolution outcome and would collide with MailExchangerAddressResolved). Opposite event: DeliveryRoutedWithoutDnsResolution, where the lookup that this event triggers never happens. Ambiguity worth a 🟥: the RFC's own worked example writes the same domain in two cases — RCPT TO:\<Jones@XYZ.COM> at D.3 line 5010 and 'a DNS lookup on xyz.com' at 5049 — and never says where case folding happens. Which project screen would have killed it: the four altitude tiers (Infrastructure) and the inbound-only scope. ⚠️ FIELD HYGIENE PASS: nothing struck — both fields were already sourced to the RFC's own worked scenario. delivery_domain is retained despite being a lexical split of forward_path because the split IS the state change this event certifies, and the D.3 case-folding gap at 5010 versus 5049 means the result is not mechanically recoverable. RFC 5321 supplies no session, transaction or connection identifier (grep for all three over the file returns nothing), and none was carried here; identity is the forward-path being resolved.
