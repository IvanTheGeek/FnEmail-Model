## Notes

RECOVERED BY THE RE-SWEEP. 551's own text is an instruction — "please try" — and the merged list carried the telling but never the trying, which is the only reason 551 differs from a bare 550. The state change is on the message, not on the address record: this can happen once, for this message, without any stored address ever being rewritten (AddressBookEntryUpdated is the other, independent consequence, and the RFC is explicit that neither may be assumed). Strength: no keyword; the RFC states the reply text and stops. Marked likely. Distinct from MessageRelayedToCorrectedAddress and must not be merged with it: there the SERVER kept custody and forwarded, here the server refused and the CLIENT re-sent — a relay's send is not an originator's. Opposite arm, kept separately: CorrectedAddressFoundUnreachableBySender. Rejected alternative names: MessageRetriedAtSuggestedAddress, ForwardPathFollowedByClient. Screens: responsibility-boundary cutoff, inbound-only scope.

⚠️ FIELD HYGIENE PASS (fields and notes only): struck one field, message (MessageId, f2C8D14) — and this is the event where the §4.4 rescue was tested and REFUSED, which is why it is worth recording rather than just doing. RFC 5321 supplies no message identifier, and the optional ID clause that keeps a queue id alive on MessageRelayedToCorrectedAddress and MessageReturnedAsNonDeliverable does not reach here: a 551 arrives in answer to RCPT, before DATA, so the refusing server never accepted the message, never queued it, and never wrote a Received line. There is no id, from either side — RFC 5321 gives an originating client no identifier for its own message either. The custody distinction the notes above insist on turns out to have a payload consequence the merged record hid behind a shared f2C8D14: the two relay events can carry a queue id and this one cannot. What identifies the resubmission is the pair already on the event, the recipient refused and the one tried instead.
