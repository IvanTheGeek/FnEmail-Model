## Data

**No data.** The method sanctions this: *"If an event has no meaningful payload beyond its identity (e.g., a simple state transition), it is fine to have no fields or just the identity key."* It also warns, of a different case, that *"An event without fields is an opaque label"* — both are recorded here rather than reconciled, because reconciling them is a later step's work, not Brain Storming's.

## Notes

RECOVERED BY THE RE-SWEEP. The §4.1 sweep set NOOP aside as 'the RFC's own definition of a non-event' and the cap prevented reconsideration; it is recovered because this chapter is instructed to keep candidates that only a screen would kill, and because §4.5.1 line 3390 makes NOOP one of the nine commands a conforming receiver MUST support — the spec requires an implementation of a command it defines as doing nothing, which is itself worth a marker. THIS IS THE CHAPTER'S CLEANEST INSTANCE OF THE FIELDLESS-EVENT TENSION AND IT IS RECORDED, NOT RESOLVED. The kit says an event with no meaningful payload beyond its identity is fine and that events must not be padded to reach a count; it also says an event without fields is an opaque label. NoopAcknowledged carries exactly one field, the session it happened in, because there is nothing else true about it — and it is, by the RFC's own words, an opaque label. Both halves of the kit's guidance apply at once here. The one candidate substantive effect is the §4.5.3.2.7 inactivity timer: a NOOP is a command, so its arrival restarts the server's five-minute wait, and a client can hold a session open indefinitely by sending NOOPs. THE RFC NEVER SAYS THIS. It is an inference from 3668-3669, is flagged as a hotspot rather than asserted, and is the only reason to think NOOP changes anything at all. Rejected alternative names: NoopReceived (names the arrival, not the completed exchange), SessionKeptAlive (asserts the inference), NoActionTaken. Which screen would have killed it: the consumer test (G1) flat, the capture/decision lens, the twelve-slice model, and the 'queries are not events' test if a no-op is read as a degenerate query. FIELD HYGIENE PASS: struck session_id (f2C8D14) — the event's ONLY field — AND THIS EVENT IS NOW CORRECTLY FIELDLESS. It is this chapter's answer to the audit's tell. The inherited note above says in as many words that the record 'carries exactly one field, the session it happened in, because there is nothing else true about it'; that field was fabricated. A grep over rfc5321.txt for a session, transaction or connection identifier returns nothing, and a grep for f2C8D14 returns nothing — the value is this project's own minted queue-id example, and a NOOP exchange has no queue and no message. Strip it and nothing remains, which is exactly what the method sanctions: an event with no meaningful payload beyond its identity is fine with no fields. What identifies this occurrence is the channel it happened on and its position in the command sequence; the RFC gives nothing else, and that absence is a genuine finding about SMTP rather than a gap to be filled. The fieldless-event tension the note flagged is not resolved by this pass — it is simply now visible, which was the point of running the pass. Left doubtful.
