## Notes

RECOVERED BY THE RE-SWEEP. The §3.9 sweep considered this under the name HeaderSectionModifiedInViolation and dropped it twice — once into its set-aside pile as "the absence of a change is not a change" (which describes the honored arm, not this one) and once into its overflow as "a violation record rather than a state change". Both reasons are contestable and neither is the method's: a From field that now reads owner-staff@foo.com instead of Smith@bar.com is a completed, irreversible change to a real object, and the reader of the delivered message sees it. Rejected alternative names: HeaderSectionModifiedInViolation, FromFieldRewrittenByList, HeaderSectionAltered. Strength: MUST, with the From field called out by name. Distinguish carefully from MessageModifiedByList (§3.9.2 1743-1744): that is descriptive prose about lists that do more than the permitted substitutions and are therefore reclassified as MUAs, with no violation involved; this is a list still presenting itself as an expander that broke a MUST. Both can be true of the same software on the same message and they are different facts. Screens: the consumer test G1, and the four altitude tiers would file header-field surgery below the protocol tier. FIELD HYGIENE PASS: nothing struck. altered_header_field is the one payload value in this event with a real line behind it — "From" is named at rfc5321.txt:1695 — and replacement_value is the fact the event creates, so both survive the derived-value test. Note what the strike list did NOT contain here: no previous_value field was ever offered, and adding one would have been padding, since the header section is required to be untouched and the prior value is whatever RFC 5322 put there, outside this spec's reach. queue_id kept on the §4.4 ID-clause warrant.
