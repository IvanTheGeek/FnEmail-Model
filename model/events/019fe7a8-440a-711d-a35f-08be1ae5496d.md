# `NonconformingHeaderAddressForwardedIntoInternet`

A gateway forwarded a message into the Internet whose From:, To: or Cc: addresses were still unqualified, syntactically foreign, or not usable as a reply destination.

## Where RFC 5321 says so

| Section | Lines | Text |
|:--|:--|:--|

## Notes

RECOVERED BY THE RE-SWEEP: the violated arm of three MUSTs, carried by no sweep. It is the event with the longest tail in the chapter — an unqualified From: survives into the Internet and every reply to that message fails, days later, at a host that never saw the gateway. "Jones@foo" is a real unqualified form: it is the shape §6.4 line 4135 discusses under Compensating for Irregularities (heading verified at line 4074), which is also the section §3.7.1 licenses the gateway to override, so a gateway may legally decline to fix exactly what §3.7.4 requires it to fix. That collision is worth a hotspot alongside the "useful for sending replies" one. Three distinguishable sub-arms deliberately kept in one event rather than split into three: non-RFC-5322 syntax, non-FQDN, and unreplyable. If a facilitator splits them, UnreplyableAddressGeneratedByGateway is the name for the third and the only one that cannot be checked mechanically. Opposite event: HeaderAddressTransformedForInternet. Which project screen would have killed it: inbound-only scope, responsibility-boundary cutoff.

FIELD HYGIENE PASS: struck message_ref (example f2C8D14) — no message identifier exists in RFC 5321; the offending header field and the value that escaped are what identify this. ⚠️ One preserved claim needed narrowing rather than striking: the note says "Jones@foo" is "a real unqualified form", and the §6.4 citation is correct — line 4135 reads "o  Correction of addresses to proper FQDN format" — but the string Jones@foo does not appear in RFC 5321. The line supports the CLASS of defect, not the literal value, so example_source says illustrative and names the line that supports the class.
