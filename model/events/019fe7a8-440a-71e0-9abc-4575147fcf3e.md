## Notes

RECOVERED BY THE RE-SWEEP as an event in its own right; the inherited set carried only the mechanism events, MailboxExistenceDisclosedViaVrfy and MailingListMembershipDisclosedViaExpn, and the 7.x set-aside pile filed 'EXPN expansion and address harvesting' as a read. It is a read for the server and an acquisition for the attacker: information that was inside foo.com is now outside it and cannot be recalled. Strength: none; 7.3 describes the phenomenon, it does not regulate it. Rejected names: MailingListHarvested, AddressListAcquiredBySpammer, ListContentsHarvested. stream_root is awkward deliberately: the addresses left a SITE, not a session, and no offered root names a site; an invented 'Disclosure' root would fit better. Screens that would have killed it: the consumer test, the capture/decision lens, inbound-only scope. FIELD HYGIENE: nothing struck; one example replaced with better real data. harvested_addresses carried the walk-scene pair and now carries the RFC's own EXPN expansion at lines 1316-1318, which is what an EXPN of Example-People (line 1315) actually returns in this specification, so list and contents now agree (rule 8). method is neither invented nor derived: 4263-4265 gives EXPN and 4275-4277 gives RCPT as routes to the same information, so the field is genuinely two-valued in the source. harvesting_client survives as the one peer identity the spec acknowledges, derived by the server from the TCP connection (4.4 lines 3325-3327); no session, transaction or connection key existed here to fabricate.
