## Notes

MUST twice (1353, 1355). Easy to miss because it reads as a reply-formatting rule, but it is not satisfiable at reply time: if no mailbox name was ever assigned to the program target, the server cannot obey the MUST, so the assignment is a provisioning event that must already have happened. The second citation is kept as a deliberate contrast — 'Paths MUST NOT be returned' from the same paragraph genuinely IS a formatting rule and is set aside, which is what shows the first MUST is not one. Screens: altitude tiers, inbound-only scope, and the responsibility-boundary cutoff, since delivery to a program sits past the boundary the current model draws. FIELD HYGIENE: nothing struck; both fields are essential — the mailbox is the identity the RCPT command will carry, and the target is what makes the assignment necessary at all. The delivery_target example was changed from 'program on 192.0.2.10' to the RFC's own words at line 1355: the IP address was walk-scene data grafted onto a fact the spec states without any host, and it implied a locating detail RFC 5321 does not supply. The mailbox example cannot be sourced to the RFC and is labeled as illustrative rather than dressed up; the spec requires that such a name exist without ever naming one. No session, transaction or connection key was present; identity is the mailbox itself.
