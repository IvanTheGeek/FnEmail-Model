## Notes

Carried from the inherited candidate; the dns_result field is dropped as redundant with the name. Strength: MUST. The decision to queue is here; the retry schedule is §4.5.4.1 (heading verified at line 3685) and belongs to another chapter, along with the over-time siblings RetryAttemptScheduled, RetryScheduleExhausted and QueueLifetimeExpired — the last of which is what finally turns a temporary error into a permanent one, and §5.1 says nothing about where that boundary is: 🟥. Opposite arm carried separately: MessageFailedWithoutQueueingAfterTemporaryError. Rejected alternative names: DeliveryDeferredOnTemporaryDnsError, MessageDeferredForRetry. Which project screen would have killed it: the inbound-only scope and the responsibility-boundary cutoff, both of which put a sending-side queue out of bounds. ⚠️ FIELD HYGIENE PASS: struck message_id (example \<f2C8D14@foo.com>) and queued_at. RFC 5321 supplies no message identifier for routing: §4.4's trace grammar makes the ID clause OPTIONAL (Opt-info = [Via] [With] [ID] [For], line 3329) and defines it as ID = CFWS "ID" FWS ( Atom / msg-id ) at 3336-3337 — an identifier the RECEIVING host writes into its own trace field, not one the sender's queue holds — while §6.4 line 4131 lets an originating server add 'a message-id field when none appears', which proves a message need not have one at all, and D.3's worked relay carries neither a Message-ID header nor an ID clause on its Received line (5064). f2C8D14 appears nowhere in the RFC; it is this project's minted queue-id value from commit 6acfc68. No queue_id was substituted: RFC 5321 defines no queue entry and no identifier for one, and minting a key here would hide precisely the finding that Step 1's stream-root sub-step exists to surface. What carries identity is the queue entry itself; the §4.4 ID clause is the only place the RFC acknowledges such a handle can exist, and it is optional. queued_at struck as event metadata — every event has a time of occurrence — and the retry timing it was reaching for lives in §4.5.4.1, another chapter.
