## Notes

Inherited from candidate 225; its citations checked and correct. MERGED IN by the re-sweep: MultilineReplyStarted — the arrival of the first hyphenated line opens the client's reply buffer and is a genuinely separate state change (the client stops treating each line as a complete reply); it is folded here rather than given a row, and should be split out if reply parsing is ever modeled as its own read side. Only EHLO, EXPN and HELP are expected to be multiline "in normal circumstances" (§4.2 lines 2573-2584) but the last clause permits it for any command, so no slice can assume single-line replies. The RFC's own worked example carries the trap deliberately — 250-234 Text beginning with numbers (lines 2766-2769) — reply text that looks like a reply code, which is exactly the case a naive line splitter gets wrong. Strengths differ inside one paragraph: SHOULD that the server send the \<SP> when no text follows, MUST that the client cope with its omission. stream_root is Reply, invented: none of the offered roots fits, because the thing accumulating across several wire lines is the reply itself, not the session and not the transaction. Screens that would have killed it: the four altitude tiers (Protocol/Infrastructure, below the Domain line) and G1, since nothing drawn consumes a framing event.

FIELD HYGIENE PASS (chapter 14): three of four fields struck. session_id struck — RFC 5321 names no session, transaction or connection identifier, and f2C8D14 appears nowhere in the RFC; identity here is the reply itself, accumulating across wire lines, which is why stream_root was already Reply. line_count struck as a computed value — the RFC never treats the number of lines as data; lines 2751-2753 make the fact the MARKING of the last line, which the event's name already carries. final_line_text struck: "the text is for the human user" (2558-2559). reply_code KEPT, and the line that makes it data is 2610 — "An SMTP client MUST determine its actions only by the reply code, not by the text" — so on the receiving side the code is the one datum the client captures and acts on.
