## Where RFC 5321 says so

| Section | Lines | Text |
|:--|:--|:--|
| §5.1 | 3891-3896 | *"The destination host (perhaps taken from the preferred MX record) may be multihomed, in which case the domain name resolver will return a list of alternative IP addresses. It is the responsibility of the domain name resolver interface to have ordered this list by decreasing preference if necessary, and the SMTP sender MUST try them in the order presented."* |
| §5.1 | 3927-3928 | *"The records are first ordered by preference, with the lowest-numbered records being most preferred."* |

## Notes

RECOVERED BY THE RE-SWEEP — the violated arm of 'the SMTP sender MUST try them in the order presented', which no inherited candidate carried. The ordering *act* is done by the resolver interface outside SMTP and is correctly in the set-aside pile as input rather than an event of ours; what the sender then does with that input is ours, and that is the distinction this event preserves. Strength: MUST. It also covers ignoring the preference sort at 3927-3928, which is the same violation one level up. Honored arm has no separate event — trying in order is the normal path and shows up as DeliveryAttemptFailedForAddress or NextHopChannelEstablished. Rejected alternative names: MultihomedAddressOrderIgnored (too narrow, drops the MX-preference case), ResolverOrderOverridden. Which project screen would have killed it: the inbound-only scope. ⚠️ FIELD HYGIENE PASS: nothing struck; no fabricated identity key was present. Both orders are required — the violation is the difference between them and neither is recoverable from the other, so this is one of the few events in the chapter where two list fields are genuinely essential rather than padding. The two addresses are walk-scene values; exchanger is illustrative because RFC 5321 gives no multihomed instance.
