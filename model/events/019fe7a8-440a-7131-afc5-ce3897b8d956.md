## Notes

CITATION CORRECTED during the merge: the inherited candidate cited §3.9.2 lines 1743-1745 for the "There exist mailing lists" sentence; the sentence ends mid-line 1744 ("...to a message and its envelope.") and line 1745 belongs to the next sentence. Fixed to 1743-1744. The RFC draws a boundary here that the model has no vocabulary for: a list that stays inside the permitted substitutions is a continuation of the same transit, and a list that goes beyond them is a different kind of thing entirely — same software, same message, and the classification flips on what it did to the body. modification genuinely needs a List cardinality: a list typically tags the subject and appends a footer in one pass. No RFC 2119 keyword anywhere in either paragraph; it is descriptive prose that carries a definitional consequence, which is a strength category worth flagging in its own right. Rejected alternative names: ListAppliedExtensiveModifications, MessageRewrittenByList, ListEditedMessage. Distinguish from HeaderSectionModifiedByExpander, which is a MUST broken; this one is permitted behavior that changes what the list is. FIELD HYGIENE PASS: no field struck, but `modification` was retyped from Enum(subject_tag \| footer_added \| header_added \| body_rewritten) to Text. None of those four members appears anywhere in RFC 5321 — the spec offers no taxonomy of list modifications at all, only "additional, sometimes extensive" (1743-1744) — so the enum was a fabricated value set presented as if it were sourced, which is the same defect as a fabricated example one level up. The field itself stays: it is the one fact the event turns on, it is not derivable from anything else, and the classification consequence at 1744-1746 depends on what was done rather than that something was. List cardinality retained for the reason the earlier note gives. queue_id kept on the §4.4 ID-clause warrant.
