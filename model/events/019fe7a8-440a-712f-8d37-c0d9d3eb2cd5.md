## Notes

Whether the copies are real objects or a way of speaking is exactly what Step 1 should not decide. The RFC says "copies", and each one can succeed or fail independently — Green@foo.com bounces while Jones@foo.com is delivered, the §4.4 lines 3275-3283 partial-success case — and that independence is the argument that they are separate objects, which is why stream_root is Queue Entry rather than Message. content_ref reuses the model's forgettable-payload handle: the body is shared across copies while the envelopes differ. Two different notions of copy live in one document and a facilitator should see both: §4.5.4.1 lines 3759-3763 says one copy SHOULD be transmitted when the destination server is the same for several recipients, so "copies" at the queue level need not be copies on the wire. Rejected alternative names: MessageCopiedForRecipient, PerRecipientCopyMaterialized, MessageForked. Cross-reference, deliberately NOT merged: MessageCopyGenerated (Appendix B lines 4737-4739) is a submission MTA making copies for queuing at the originating end — different actor, different moment, different motive, and it belongs to whichever chapter takes Appendix B. Screens: responsibility-boundary cutoff, altitude tiers. FIELD HYGIENE PASS: content_ref struck — 1 field. Two independent reasons, either sufficient. First, its value was f2C8D14, which is a queue id, not a content reference; the walk scene's own content_ref is blob:sha256:9c1e… (docs/paths/WORKING-helo-direct-single-recipient-v2.md line 300), so the value was fabricated by transplanting the neighboring field's example, and rule 8 catches it the moment the field is instantiated with real data — the same handle cannot name both the queue entry and the blob. Second, the field is derived: a copy shares the source entry's content by definition of "copy", and source_queue_id already reaches it. The note above about the shared body is the argument for a read model, not for a field. The two queue ids stay, both labeled minted: RFC 5321 does name the object — §4.5.4.1 line 3692, "A mail queue entry will include not only the message itself but also the envelope information" — but supplies no identifier for it, and §4.4's optional ID clause is stamped once per receiving hop, so it warrants source_queue_id directly and copy_queue_id only by extension. That gap is a genuine finding about the spec and is left visible rather than papered over.
