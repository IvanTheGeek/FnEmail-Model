## Where RFC 5321 says so

| Section | Lines | Text |
|:--|:--|:--|
| §2.3.8 | 765-771 | *"Lines consist of zero or more data characters terminated by the sequence ASCII character "CR" (hex value 0D) followed immediately by ASCII character "LF" (hex value 0A). This termination sequence is denoted as \<CRLF> in this document. Conforming implementations MUST NOT recognize or generate any other character or character sequence as a line terminator."* |
| §2.3.8 | 773-779 | *"the appearance of "bare" "CR" or "LF" characters in text (i.e., either without the other) has a long history of causing problems in mail implementations and applications that use the mail system as a tool. SMTP client implementations MUST NOT transmit these characters except when they are intended as line terminators and then MUST, as indicated above, transmit them only as a \<CRLF> sequence."* |

Line numbers are into [`docs/rfc/rfc5321.txt`](../../docs/rfc/rfc5321.txt), the archived copy. Quotations keep the specification's own words and spellings (AGENTS.md rule 2).

## Notes

Harvested from the §1-2.4 sweep. Strength: two MUST NOTs and one MUST in five lines, and the spec says nothing about what a server does on receipt — the violation is specified and the response is not. That asymmetry is the modelable content: a conforming receiver MUST NOT recognize a bare CR or LF as a terminator (768-770), so the line simply never ends and the transaction hangs rather than erroring. Worth a hotspot wherever it lands. Companion event on the server side, and the reason both are kept: BareLineFeedTerminationAccepted, the non-conforming receiver that does the opposite. Doubtful as an event because it is a non-conforming transmission rather than a sanctioned state change; kept per the include-when-unsure rule. Screens: the altitude tiers (Infrastructure/wire) and the consumer test. Rejected alternative name: BareCrOrLfSent.

FIELD HYGIENE PASS: struck two of three. session_id is fabricated — RFC 5321 names no session identifier; identity is the channel, and for a client-side violation the only party-identifying fact the spec supplies is the domain the client claimed in EHLO or HELO, which is a claim rather than a key. transmitting_client is struck on that account too, but for a second and stronger reason: the claimed domain is a session-level fact established once by the greeting event, so repeating it on every event inside the session is padding. bare_character survives, and its value is quoted exactly from rfc5321.txt:766, which is where the RFC fixes both the character and the notation.
