## Notes

RECOVERED BY THE RE-SWEEP. The ReversePathProvisionallyAccepted candidate names this sibling explicitly and says it was 'not given a slot' — yet calls it 'the only observable consequence and the reason this event has to exist at all'. Restored. The pairing is the point: a provisional acceptance that is never followed by either a report or a successful transaction is invisible, so this event is what makes the deferral falsifiable. triggering_forward_path carries the fact the RFC leaves implicit — it was examining a RECIPIENT that settled the SENDER's fate, which is the one place in the transaction where the two arms cross. Reply code from 1045; 553 is equally normal, so the field has a real range. Rejected alternative names: DeferredReversePathRejected, LateSenderRefusal. Killed by: the twelve-slice model (no slice has a rejection arriving at RCPT time for a MAIL-time cause) and the 'one event per command' target.

FIELD HYGIENE PASS: struck one field, reply_code (550), as the wire rendering of a decision the event's name already carries. ⚠️ The argument above — 'Reply code from 1045; 553 is equally normal, so the field has a real range' — is the strongest case in the chapter for keeping a code, and it still fails the method's test: a range of renderings is still a rendering, and which of 550 or 553 an operator emits is a fact about the reply, not about the state change. It is recorded here instead: rfc5321.txt:1045 reads 'Normally, failures produce 550 or 553 replies.' triggering_forward_path SURVIVES and is the event's real content — the recipient whose examination settled the sender's fate, which is not derivable from any other event in the stream because the RFC never says which forward-path triggered the report. No identity key was present to strike.
