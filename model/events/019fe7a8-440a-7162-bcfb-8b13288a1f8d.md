# `AddressVerificationDeclinedAsUnverifiable`

The server declined to confirm an apparently valid address it could not verify in real time, answering 252 and binding itself to accept a message for it anyway.

## Notes

MERGED from two inherited candidates that named the same state change from different spans: AddressVerificationDeclinedAsUnverifiable (§3.5.3, the condition) and VerificationDeclinedWithDeliveryPromised (§4.2.2, the reply code's own text, which supplies the commitment). Both citations verified; §4.2.2 explicitly cross-references §3.5.3 at line 2821, which is what proves they are one event and not two. The second name is carried here as the rejected alternative, along with UnverifiableAddressDeclined and VerificationDeferred; 'DeliveryPromised' was dropped from the name because the promise is stated only in the code's descriptive text and nowhere normatively — but it is the interesting content and must not be lost, since 252 is listed as a SUCCESS reply for VRFY at 3127 and for EXPN at 3132. Strength: SHOULD (1389-1390). §3.5.2 line 1362-1364 supplies a second route to this same reply — the commands are not required to work across relays — which is why the relay case is cited here rather than given its own event. Line 1390 says these cases parallel the RCPT verification discussion in §2.1 (a pointer, not read for this chapter). Opposite and sibling: VerificationDeclinedAsDisabled is a different 252 with a different cause and a MUST instead of a SHOULD. Which screen would have killed it: 'one event per command', the capture/decision lens, the twelve-slice model. Also relevant: §3.5.3 lines 1394-1396 say implementations SHOULD generally be more aggressive about verification for VRFY than for RCPT, 'even if it takes a little longer' — a policy stance that makes reaching this reply a choice, not only a capability.
