## Notes

Merge of MessageAcceptedForProcessing (§3.3 sweep) and the acceptance half of ResponsibilityForMessageAssumed (§4.1 sweep); rfc_refs unioned. Rejected alternative names: MessageAccepted (the project's existing name), MessageAcceptedForFurtherProcessing, ResponsibilityForMessageAssumed. Strength: MUST (2040-2041). forward_paths is a List and that is load-bearing: 2042-2045 forbids partial failure, so ONE 250 covers every recipient the transaction accumulated, and a per-recipient success event would misrepresent the protocol. Deliberately kept apart from DeliveryResponsibilityAccepted, which is the same wire moment read for a different fact — this event says the transaction succeeded, that one says an obligation was created; §4.2.5 is written entirely about the second and never mentions the first. Whether they are one event or two is a later step's ruling and is exactly the kind the twelve-slice model has already made implicitly. Preceded by MessageContentStored, per the ⚠️ recorded there. Screens: none kills it; this is the event the project's own screens keep.

FIELD HYGIENE PASS: struck four of six; this is the one event in the chapter where an identity key survives, and it is worth being exact about why. transaction_id is fabricated and struck. queue_id is kept, because §4.4 line 3336 gives ID = CFWS "ID" FWS ( Atom / msg-id ) and line 3329 makes the ID clause part of Opt-info — so the receiving server stamping its own identifier on the message it has just accepted is the one identity key RFC 5321 actually licenses, and this is the moment it comes into existence. Two caveats travel with it: the clause is OPTIONAL (Opt-info = [Via] [With] [ID] [For]), so even this key is not guaranteed; and the alternative production msg-id is RFC 5322's, not this spec's, so a message_id field elsewhere in the model would have no RFC 5321 basis. The example value f2C8D14 appears nowhere in rfc5321.txt (grep returns nothing) — it is this project's own minted queue id, traceable to commit 6acfc68, and is labeled as such. reply_code (250) is struck as the rendering of the decision the event names. accepted_at is struck as the event's own occurrence time. reverse_path is struck here as carried by the MAIL event and not what acceptance is about — it stays on DeliveryResponsibilityAccepted, where §4.2.5 lines 2956-2957 give it a job. forward_paths is kept for the reason the note already states: the all-or-nothing rule at 2042-2045 makes the List load-bearing.
