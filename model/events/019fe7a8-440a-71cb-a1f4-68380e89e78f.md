# `CommandSentWithoutAwaitingReply`

A client transmitted a command before the reply it was required to wait for had arrived — either before the opening greeting, or on top of an unanswered command.

## Notes

RECOVERED BY THE RE-SWEEP — §4.3.1's two waiting rules are the alternating-dialogue invariant the whole command-reply chapter rests on, and no inherited candidate carried either arm. Two faults merged into one event with a skipped_wait field because the state change is identical (unanswered command on the wire, dialogue no longer alternating); they are named separately here because operators treat them as different problems and a facilitator may split them: CommandSentBeforeGreeting, the "early talker" that many receivers now use as an abuse signal, and CommandsPipelinedWithoutNegotiation, sending a second command before the first is answered. Their strengths differ, which is the argument for splitting: MUST for waiting between commands (2996-2997), only SHOULD for waiting for the greeting (3000-3001). Both are conditional — "Unless other arrangements are negotiated through service extensions" is precisely what the PIPELINING extension does, so the same wire behavior is a violation in one session and correct in the next, and the event is only a fault relative to what was negotiated. That conditionality is the finding, and it should not be resolved at Step 1. Screens: the inbound-only scope (client actor), though the receiver is the party that observes it.

FIELD HYGIENE PASS (chapter 14): session_id struck — RFC 5321 names no session, transaction or connection identifier, and f2C8D14 is nowhere in the RFC. peer_address KEPT, and it is the RFC's own answer to what carries identity on a channel: section 4.4 line 3325, TCP-info, "Information derived by server from TCP connection". skipped_wait and command_verb KEPT — skipped_wait is the fact that separates the two merged arms, and the verb is the command that arrived early, which nothing else records because it arrived out of turn.
