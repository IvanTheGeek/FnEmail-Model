## Where RFC 5321 says so

| Section | Lines | Text |
|:--|:--|:--|
| §4.1.1.10 | 2212-2214 | *"The sender MUST NOT intentionally close the transmission channel until it sends a QUIT command, and it SHOULD wait until it receives the reply (even if there was an error response to a previous command)."* |
| §4.1.1.10 | 2210-2212 | *"The receiver MUST NOT intentionally close the transmission channel until it receives and replies to a QUIT command (even if there was an error)."* |
| §3.1 | 976-978 | *"A server taking this approach MUST still wait for the client to send a QUIT (see Section 4.1.1.10) before closing the connection"* |
| §4.1.4 | 2530-2531 | *"The last command in a session MUST be the QUIT command."* |

## Notes

RECOVERED BY THE RE-SWEEP. This is the violated arm of a MUST NOT that no inherited candidate raised as an event: the QuitReceived candidate flagged it in its notes as a 🟥 hotspot under the name ClientAbandonedConnectionWithoutQuit and then left it as a note, which is exactly the loss the brief predicts — every MUST has two arms and the violated one is where a capped sweep stops. 🟥 Hotspot preserved: after a 554 refusal the server MUST wait for a QUIT, and the spec bounds that wait by nothing at all, so a client that never sends one holds the connection indefinitely. The only escape §3.8 licenses is the §4.5.3.2 timeout, which makes ServerInactivityTimeoutExpired the event that resolves this one — a dependency invisible from either section alone. Distinct from ConnectionLostWithoutQuit and cross-referenced to it: there the transport fails, here the client simply stops while the channel remains up, and the server cannot tell them apart. Rejected alternative names: ClientAbandonedConnectionWithoutQuit, ChannelClosedWithoutQuit, SessionAbandoned. FIELD HYGIENE PASS: struck 2 fields. session_id struck: no such key in RFC 5321, and the point bites hardest here — the channel is still up, still held, and still unnamed by anything the spec supplies, which is the whole shape of the hotspot above. client_address struck as the channel's, already recorded at TransmissionChannelOpened. last_command_received survives as the fact that says where the client stopped, and it is what distinguishes an abandonment mid-transaction from one after a refusal.
