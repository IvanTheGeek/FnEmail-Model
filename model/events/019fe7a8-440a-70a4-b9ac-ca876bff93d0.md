# `DotStuffingApplied`

A client doubled a leading period on a line of mail text so that user-composed content could not be mistaken for the end-of-mail indicator.

## Notes

Harvested unchanged. Strength: NONE — there is no RFC 2119 keyword anywhere in §4.5.2's transparency procedure; the whole subsection is written as procedure ("the following procedures are used", 3428-3429) and is nonetheless unskippable in practice. That is worth recording rather than smoothing over: a reader grepping for MUSTs would conclude transparency is optional. The two fields hold the same line before and after, which is how the reversibility is checkable — a placeholder teaches nothing here, whereas '.signature follows' becoming '..signature follows' shows the mechanism at a glance (rule 8). Opposite event: DotUnstuffingApplied, its exact inverse, applied by the receiver before anything else sees the content. Interaction worth carrying: the stuffed dot is explicitly NOT counted against the 1000-octet text-line limit (§4.5.3.1.6 line 3513), so this event and TextLineLengthExceeded measure different strings. Screens: the Protocol/Infrastructure altitude tiers and the consumer test — nothing in the model reads a wire line.

FIELD HYGIENE PASS: struck one of three. transaction_id is fabricated — RFC 5321 names no transaction identifier; identity is the channel and the line's position in the content stream. Both surviving fields stay untouched and are the model case for what this pass is protecting: they are a real before and a real after, and the note above already argues rule 8 for them explicitly. Their values are illustrative and labeled so — §4.5.2 states the procedure but never instantiates a stuffed line, so no line number can be given for either.
