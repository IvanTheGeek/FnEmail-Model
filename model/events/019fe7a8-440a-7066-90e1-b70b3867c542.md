## Notes

Merged from five inherited candidates naming one act from five places: UndeliverableMailNotificationSent (§4.4), NonDeliveryNotificationSent (§6.1), SubsequentFailureNotificationReturned (§3.3), DeliveryFailureReportGenerated (§4.1.1.4), NonDeliveryNotificationReturned (§4.2.5). Rejected alternative names: NonDeliveryNotificationSent, NonDeliveryNotificationReturned, SubsequentFailureNotificationReturned, DeliveryFailureReportGenerated, BounceSent, MessageBounced. §6.2 4019-4020 calls the same act 'bounced' — one act, two vocabularies inside one document. SIX MUSTs stack on this event and must not be flattened: compose and send (3281-3283); one grouping form or the other (3285-3287); use the MAIL command (3291-3293); use a null return path (3293-3294 and 3972-3973); recipient equals the envelope return path (3973-3975); the reverse-path is the target of any delivery error mail (3258-3260). The only SHOULD is the preference for the consolidated form, 'For economy of processing by the sender'. Two modeling choices recorded so nobody re-derives them. First, 'compose and send' is one clause but two state changes, and NotificationMessageComposed / NotificationMessageSent is a defensible sibling pair — a composed notification that never sends is a real and common failure. Second, grouping is carried as a field rather than as sibling events NotificationsConsolidated / NotificationsSplitPerFailedRecipient; that is the alternative, and it becomes the right call if the two shapes ever diverge in consequence. envelope_sender is written in the literal wire form MAIL FROM:\<> because under AGENTS.md rule 5 the brackets are path syntax and MAIL FROM: alone is a different thing. DO NOT MERGE with the relay's version: UndeliverableMailNotificationSent at §3.6.3 (inherited candidate 85) is a relay reporting a route it could not complete, with its own SHOULD on DSN format, and belongs to the relaying chapter — a relay's send is not an originator's. Screens: inbound-only scope, decisively; this event sends mail. ⚠️ FIELD HYGIENE PASS 2026-08-09 — two fields struck. original_message_id: RFC 5321 supplies no message identifier, so the notification carries no protocol-level reference back to the message that failed. §4.4's ID clause (line 3336) is optional, is written into a Received: stamp by a receiver, and takes an Atom or an RFC 5322 msg-id; f2C8D14 is this project's own minted queue_id value from commit 6acfc68 and appears nowhere in the RFC. 🟥 What links this notification to the original is only the address it goes to — the envelope return path, mandated at 3973-3975 and 3258-3260 — and the failed_recipients it lists; the correlation a reader expects the field to supply does not exist in the protocol, which is worth marking because it is the reason bounce matching is a practical problem. sent_at: struck as the event's own occurrence time. envelope_sender survives with its example sourced to the RFC's own literal at line 1522: it is a value that genuinely travels in the envelope, not an assertion about it, and its violated arm has its own row as NotificationSentWithNonNullReturnPath.

COLLISION RESOLVED — kept separate and renamed. Different sections, different actors, different normative content: the bias applies squarely. One rests on 4.4 lines 3275-3294 and 6.1 lines 3970-3975, where the sender is the system that accepted responsibility at the 250; the other rests on 3.6.3 lines 1494-1505, where the sender is a relay that accepted the task of relaying. Neither cites the other's section. The chapter 5 record already carried an explicit, reasoned instruction not to merge — a relay's send is not an originator's — and the RFC backs the distinction with content that exists on only one side: the DSN-format SHOULD and the lowercase from-host "must" in 3.6.3, the grouping MUST and the partial-delivery setting in 4.4. Note the deliberate asymmetry with DeliveryFailedAfterAcceptance above, which IS merged: 3.6.3 lines 1503-1505 unify the DETERMINER across roles in one sentence ("the host that first determines that delivery cannot be accomplished"), so the determination is one datable fact, while the SENDING obligations are stated twice, for two roles, with different requirements. If a later pass finds the two send-side obligation sets genuinely identical, these two can be collapsed then — a split loses nothing now, where a wrong merge would bury one record's research.
