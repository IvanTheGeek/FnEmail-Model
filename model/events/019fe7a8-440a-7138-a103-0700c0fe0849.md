## Notes

Everything in this chapter presupposes it — you cannot expand a pseudo-mailbox nobody created, and expansion_kind has to have been decided before a message arrives, because it decides whether the return path gets rewritten. The classification at 1706-1708 is stated as something the RFC does ("We classify"), but it is really something the administrator does at definition time; the RFC only names the two outcomes. §3.5.1 lines 1276-1279 is added in the merge and complicates it usefully: on real hosts the alias/list distinction "is a bit fuzzy" and one data structure holds both, so expansion_kind may not be a clean field at definition time at all — which is a hotspot, not a defect in the event. Rejected alternative names: MailingListCreated, PseudoMailboxDefined, AliasEntryCreated, ExpansionEntryProvisioned. Two sibling candidates from the §3.5 sweep — MailingListCreated and AliasEntryCreated — are the same state change found from the EXPN side and are folded here. Nothing in the twelve slices has an administrator lane; the closest is the undecided operator lane behind ServiceConfigured. Screens: the four altitude tiers (Product/Infrastructure, not Protocol), inbound-only scope, responsibility-boundary cutoff. FIELD HYGIENE PASS: nothing struck. This is the event the chapter's derived values derive FROM, which is why expansion_kind and administrator belong here and were struck elsewhere: ListReturnPathLeftUnchanged.expected_administrator and ListReclassifiedAsFullMua.administrator were both this record's administrator looked up at a later moment. Three fields, no identifier beyond the pseudo-mailbox itself, and none needed — the List stream's identity is the address. Both illustrative values are now labeled: grep for "staff" and for "owner-" over rfc5321.txt returns nothing, so the RFC defines the concept of a list administrator, MUSTs its address into every expanded envelope at line 1692, and never once shows one.
