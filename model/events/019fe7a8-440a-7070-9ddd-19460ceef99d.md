## Notes

Merged two candidates naming one state change: TransmissionChannelEstablished (span §2) and ConnectionOpened (span §3.1). Rejected alternative names carried: TransmissionChannelEstablished, ConnectionOpened, ConnectionAccepted, SessionInitiated. §3.1 makes session initiation a TWO-part fact — client opens AND server responds — so this is only half of it; the other half is ServiceGreetingSent. A facilitator may want a third sticky, SessionInitiated, for the pair; not carried because the kit's quality checklist forbids two events meaning the same thing. Transport is deliberately unfixed: §1.1 says SMTP is independent of the particular transmission subsystem, so do not assume TCP in the payload. Screens that would have killed it: the four altitude tiers (Infrastructure/Protocol, below the Domain cut) and the consumer test G1, since nothing yet reads a connection-opened fact. FnEmail already has the receiving-server twin ConnectionAccepted; the client-side arm has no home in an inbound-only model. FIELD HYGIENE PASS: struck 3 fields. session_id struck — a grep for session, transaction or connection identifier over the whole of rfc5321.txt returns nothing, and the value f2C8D14 appears nowhere in the RFC either; it is this project's own minted queue-id example (commit 6acfc68). This event is where the identity actually comes from: the channel itself is the identity of a live session, and the pair of endpoints kept here is all the RFC gives to name it. Its ABSENCE is a finding, not a gap to fill. opened_at struck as the event's own occurrence time. server_host_name struck — it duplicates server_address as a second name for the same endpoint, and the server's announced name is not known at this instant; §4.3.1 makes announcing it the greeting's job, so it belongs to ServiceGreetingSent.
