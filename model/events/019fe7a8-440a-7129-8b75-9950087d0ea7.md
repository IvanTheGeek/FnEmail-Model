# `PseudoMailboxExpanded`

## Notes

MERGE: this is candidate PseudoMailboxExpanded (§3.9 sweep) united with RecipientAddressExpandedByListExploder (§7 sweep) — same state change, one address becoming many, found from two ends of the document. Rejected alternative names carried here so the naming research is not lost: RecipientAddressExpandedByListExploder, MailingListExpanded, AddressExploded, RecipientSetFannedOut. §7.2's fields exploded_address / resolved_addresses / expander_host were folded into pseudo_mailbox / expanded_addresses; expander_host was dropped as it duplicates the actor. The headline event of §3.9 and the one place in the chapter where a List cardinality is unavoidable rather than convenient. It breaks an assumption the current FnEmail model rests on without stating: that the recipient set is fixed at RCPT time and closed by MessageAccepted{recipients[]}. §4.5.3.2.3 lines 3635-3636 confirms the timing is a live implementation choice, which is why ExpansionDeferredUntilAfterAcceptance is a separate event in this chapter. Strength: the transformation itself carries no RFC 2119 keyword — it is described as "An important mail facility" (line 1698) — while the SHOULD at 1689-1690 obliges the host to support it. Siblings kept separate deliberately: AliasExpanded and ListExpanded are the two kinds, and MailingListExpandedAtSource is the same shape performed by the originator instead. Screens that would have killed it: the responsibility-boundary cutoff (it fires after MessageAccepted), the HELO-only charter, the inbound-only scope, and the twelve-slice model, which has no expander lane at all. §3.9 supplies no worked example of its own, so staff@foo.com is constructed in the RFC's own domain space; Jones, Green and Brown at foo.com are from Appendix D.1 lines 4893-4899. Open and not invented: the RFC never says what happens when an expanded address is itself a pseudo-mailbox — recursive expansion is unaddressed here and §6.3's loop control is the nearest text. FIELD HYGIENE PASS: nothing struck; all four fields survive. queue_id stays on the one warrant RFC 5321 gives — §4.4's optional ID clause, Opt-info = [Via] [With] [ID] [For] (line 3329) with ID = CFWS "ID" FWS ( Atom / msg-id ) (line 3336) — which is the only identifier-shaped thing the spec supplies for a message at a receiving host, and the expander here IS that host, the RFC's "recipient mailer" (line 1712). The value f2C8D14 appears nowhere in the RFC; it is this project's minted example (commit 6acfc68), and docs/paths/WORKING-helo-direct-single-recipient-v2.md already records that queue_id "is manufactured, like session_id was". No session_id, transaction_id or connection_id was present; had one been it would have gone, since grep for those terms over rfc5321.txt returns nothing and while a session lives the channel is its identity.
